#+TITLE: Trader — Architecture North Star
#+SUBTITLE: Simple, understandable Go, validated by working examples
#+STARTUP: overview

* First-Order Goal: Clarity and Simplicity

Trader must have an architecture that is *clear, crisp, small, and
readily understandable by a competent Go developer*.

This is the first-order design goal. Favor straightforward Go code
over an elaborate framework. A developer should be able to follow the
important paths, write a strategy or study, and understand where
behavior lives without tracing through layers of indirection.

- Prefer a few cohesive responsibilities, concrete types, and simple functions.
- Add packages or interfaces only when a real boundary justifies them.
- Remove indirection; do not merely rename or relocate it.
- Keep configuration, plumbing, and transport code out of domain logic.
- Preserve useful implementation and tests rather than rewriting everything.
- Optimize for a single developer's ability to understand, maintain, and extend
  the system.


* Working Method: Validate in Code, Then Migrate Selectively

Issues #571–#575 validated the essential architecture in =examples/design=
using executable Go examples and independently checked tests. This document
now records the *approved prototype baseline*, not a proposal to build a new
framework.

- Keep the working examples and their behavioral regression tests.
- Confirm any shared abstraction *reduces* the caller's complexity.
- Treat #576 as the final consolidation and migration-boundary review.
- After acceptance, move into canonical data, account activity/journaling,
  real backtests and studies, and reporting.
- Preserve useful production implementation and tests when migrating;
  production migration is out of scope for #576.
- Add multi-provider or multi-timeframe trading only for a concrete use case.

* Functional Model

These are *responsibilities*, not a requirement for one package per item.

| Responsibility | Role                                                         |
|----------------+--------------------------------------------------------------|
| MarketData     | Acquire, store, assemble, cache, and deliver market bars.    |
| Strategy       | Consume observations; request transactions with Orders.       |
| Account        | Hold account/position facts; support sizing and risk checks. |
| Broker         | Execute orders; report fills and execution activity.         |
| Trader         | Coordinate orders, account sizing, and broker submission.     |
| Backtest       | Replay historical data with simulated execution.             |
| Study          | Compute and retain research observations and statistics.     |
| Scanner        | Classify/select instruments and interesting conditions.      |

Reporting, journaling, configuration, and logging support these
responsibilities; they are not automatically separate subsystems or
service layers.


* The Essential Execution Paths

The Broker advances existing orders and valuations *before* the Strategy
receives a completed observation. Trader then validates, timestamps and submits
any requested =*order=; the Broker delegates sizing to Account because it
must account for margin reserved by other outstanding orders.

#+begin_src text
Single instrument:
  MarketData.bars -> backtest.run -> trader.onBar
    -> broker.onFrame(single bar): eligible fills, marks, margin
    -> strategy.onBar -> optional *order
    -> trader.handleOrder -> broker.submit -> account.size -> queue

Multiple instruments:
  mergedBars -> frames (fresh bars grouped by availableAt)
    -> trader.onFrame -> broker.onFrame (once per frame)
    -> each instrument's strategy.onBar (deterministic order)
    -> optional orders submitted sequentially, using shared Account margin

Non-trading consumers:
  iter.Seq2[bar,error] -> runATRStudy -> ATR observations
  iter.Seq2[bar,error] -> runEMAScan -> per-instrument trend readings
#+end_src

Studies and scanners own neither Broker nor Account. They do not fabricate
Orders. Trading-specific processing must not leak into their APIs.

The working iterator is =iter.Seq2[bar,error]=; the common observation contract
does not imply that all consumers need one generic Runner or Handler interface.

* Key Architectural Decisions


** Market data owns assembly; consumers see observations

MarketData locates and assembles observations, validates their order and
coverage, and ultimately manages storage, cache and resource lifetime.
Consumers must not need to know which source files hold the bars.

The working prototype uses =marketData.bars(ctx)=, =mergedBars(ctx, sets...)=
and =frames(bars)=. These are concrete, deterministic functions, not a new
package/interface hierarchy. Slices and channels can be considered against
future measured needs; the iterator is the accepted baseline.


** Keep single bars and fresh-only frames

A =bar= represents one genuine instrument OHLCV observation, including its
opening time and =availableAt=. A =frame= groups the bars that become available
at the *same moment*, sorted by instrument. Only newly available bars appear;
missing symbols are absent, never replaced by old or synthetic prices.

=frames= is a general MarketData grouping mechanism. The *trading-run* input
contract is deliberately narrower:

- One provider (or canonical source) per run.
- One configured timeframe and common opening/availability alignment.
- Multiple instruments; they need not all have a bar in every frame.
- Group by =availableAt= and deliver frames chronologically.
- Reject inconsistent alignment, overlapping execution windows or unsupported
  bar timing; do not silently approximate an executable price.

The current Broker validates frame consistency and rejects cross-frame
overlaps. The production Query/Dataset/Run loading boundary must enforce
provider, timeframe and alignment consistently across the dataset.
Mixed providers and mixed timeframes remain deferred.


** Bar timestamp and causal availability

=bar.Time= denotes the interval *opening*. =bar.availableAt= is the earliest
moment its completed OHLCV can be used. =order.decidedAt= records when a
Strategy was allowed to decide, stamped from the delivered observation.
A strategy order cannot fill on a bar whose opening precedes =decidedAt=.

For example, an H1 bar stamped 10:00 is completed at 11:00. A strategy
decision based on it must never fill at 10:30. Observations are fresh-only,
and the Broker rejects unsupported overlapping replay intervals rather than
using a future portfolio mark for earlier fill-time margin admission.

In the design fixtures =availableAt= is constructed by the fixture/CSV loader.
In production it is computed at the *raw-to-canonical conversion* boundary
according to source rules and **persisted in canonical data**. This requires
a schema ADR. Consumers do not recalculate it.


** Strategies request transactions using Orders

A Strategy returns an optional =*order= per delivered bar: =nil= means no
transaction. An Order identifies the instrument, action, direction, order
type, requested entry and stop; the Strategy does not calculate account units
or reserve margin. Signal state is independent of actual Account positions.

The current two-instrument example (=emaxEach=) maintains one EMAX indicator
and signal state per instrument. One frame may therefore produce several
orders, submitted sequentially in deterministic instrument order; each sees
the Account's shared margin and existing reservations.

There is no demonstrated need yet for a Strategy Order slice, a read-only
position snapshot, generic Intent/Hold events or a frame-aware Strategy API.
Introduce these only when a concrete strategy requires them.


** Shared observations, consumer-specific behavior

Backtest, Study and Scanner each have a short, readable iterator loop.
A shared function such as =run(ctx, observations, handle)= is *optional*, not a
design goal: extract it only if direct code comparison proves a net reduction
in complexity and preserves trading order, contextual errors and cancellation.
A documented decision to retain small loops is an acceptable #576 outcome.

Backtest advances a simulated Broker/Account before generating new orders;
ATR Study returns measurements; EMA Scanner returns instrument classifications.
Their results and lifecycle semantics differ intentionally. Do not route
research consumers through Broker or trading-Order machinery.


** Order sizing, lifecycle, and execution boundary

The proven order path is:

#+begin_src text
Strategy -> *Order -> Trader.handleOrder -> Broker.submit
  -> Account.size (including Broker's outstanding margin reservations)
  -> Broker queues Order -> eligible later bar -> Broker fills or rejects
#+end_src

The Account owns balance, positions, equity, margin and risk/sizing arithmetic.
The Broker owns queued orders, fills, cancellation and pending-order margin
reservations. Trader coordinates execution and decisions without duplicating
those responsibilities.

An Order tracks its current state and a timestamped history. The prototype
implements validation, sizing, submission, market/limit/stop execution,
protective stops/targets, cancellation, expiry, trailing behavior, margin
rejection, and completed-trade accounting. It distinguishes expected Order
rejections from fatal run/data failures.

For synchronized frames the Broker marks frame positions at their opening
prices, processes eligible opening executions, then OHLC range executions,
then marks closes and checks portfolio margin once. Trader evaluates each
instrument only *after* the Broker advances the frame. One Broker and one
Account serve every instrument. Margin closeout uses a fresh bar for the
position being closed; stale-position liquidation is deferred. An incomplete
*complete closeout* remains pending over later frames; progressive closeout
re-evaluates margin on each frame.

The OHLC path inside a bar is unknown. Real spread/slippage, partial fills,
asynchronous/live Broker events, quote conversion and some execution-time
accounting are deferred. Do not mistake a historical latest mark for a live,
executable quote.


* Validated Executable Examples

1. *Single-instrument EMAX backtest:* six independent scenarios verify order
   lifecycle, risk and margin sizing, fills and results, including expected
   rejections. =make run= output is a regression baseline.
2. *Two-instrument trading:* EURUSD and GBPUSD use one Trader, Broker and
   Account with independent EMAX state, deterministic order admission,
   missing-bar behavior, fill-time margin and causal =decidedAt= eligibility.
3. *ATR Study:* a non-trading iterator consumer; its result is a measurement,
   not an Order.
4. *EMA Scanner:* per-instrument EMA state and fresh-only trend classifications;
   it reads merged bars without a Broker or Account.

These examples are the approved evidence for migration. They do not require
creating a general-purpose runner, a generic observation handler hierarchy or
additional package layers.


* Results and Journaling: Next Implementation Work

The existing Broker retains completed Orders and timestamped state histories;
the Account retains positions and closed trades; a run can summarize fills,
rejections and P&L. These are *in-memory facts*, not yet a durable journal.

The next implementation phase must make results reproducible and reviewable:

- Account activities/journal: Orders and their transitions, fills, closures,
  positions, realized/unrealized P&L, Account equity and margin.
- Backtest results: strategy, data/query/run provenance, measured performance
  and execution assumptions.
- Study and Scanner results: measurements/classifications with instrument and
  availability timing.
- Reports: derived presentations (including Org) from retained facts, rather
  than reporting code directing core execution.

Avoid premature event sourcing, reporting interfaces, or persistence layers.
Choose durable formats when the real activity and research workflows establish
their requirements.


* #576 Acceptance and Migration Boundary

** Minimal Query / Dataset / Load contract

Prototype an *in-memory* Query/Dataset usage example that specifies:
provider/source, common interval and alignment, instruments, price basis,
half-open [start,end) coverage, and explicit gap/coverage expectations.
A loader owns assembling/validating data and exposes the existing bar/frame
iterators. Do not implement disk/network retrieval or a cache here, and
do not invent an interface merely to make the example mockable. Persisted
=availableAt= is a future canonical schema change with its own ADR.

** Migration inventory

For each relevant existing production capability, label *reuse*, *adapt*,
*replace* or *defer*, with a brief technical reason, before changing it.
Keep the prototype isolated during #576. Its output is an approved boundary,
not a bulk rewrite.

Prioritize:
1. Historical OANDA acquisition and canonical data conversion, including
   persisted =availableAt=, basis, gaps, provenance and coverage.
2. Account activities and journaling.
3. Real historical backtests and Studies using the same observation contract.
4. Reports, comparison and analysis.

** Exit gate

- =make check= passes at repository root and in =examples/design=.
- =make run= still produces the unchanged six EMAX scenario outputs.
- Study, Scanner and multi-instrument regression tests all pass.
- Shared-runner decision and Dataset caller example are documented.
- Migration inventory and first actionable production issue exist.
- No production package refactoring is part of #576.

Then stop architecture prototyping. Reopen a design decision only when
observed usage or a reproducible test demonstrates the need.


* Migration Principle

Selectively adapt tested behavior, not the prototype's private package or
fixture layout. Optimize for *fewer layers, a shorter path from canonical
data to results, and understandable Go APIs*. Existing working production
data acquisition, Broker adapters, and reporting code should be assessed
rather than reflexively replaced.

* Architecture Review Test

Before accepting a significant change, ask:

1. Can a good Go developer quickly understand this without reading the entire
   repository?
2. Does the example caller remain small and natural?
3. Did we remove complexity, or merely move it somewhere else?
4. Is this abstraction demonstrated by working code and a test?
5. Are we solving a present architectural problem, or prematurely polishing a
   future implementation detail?

If an approach fails these tests, simplify it.
