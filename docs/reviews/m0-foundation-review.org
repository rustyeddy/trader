** README

=README.md= describes Trader's purpose, project status, design
principles, documentation index, =Makefile= targets, license, and the
relationship to the legacy repository.  Every claim matches the
repository: the =Makefile= targets listed exist and the license is BSD
2-Clause.

** Documentation Links

All repository-relative references in =README.md=, =AGENTS.md=,
=CLAUDE.md=, =CONTRIBUTING.org=, and =docs/= resolve to existing files.
=docs/arch/package-boundaries.org= was the one non-resolving path, and
was described as planned rather than linked; it now exists and is linked
from both =README.md= and =AGENTS.md=.

** ADR Statuses

=docs/arch/adr-decisions.org= contains ADR-001 through ADR-014.  The
decision index agrees with the =Status= section of every record.  The
eight =Accepted= records (001, 002, 005, 006, 007, 008, 013, 014) are
settled boundary decisions.  The six =Proposed= records (003, 004, 009,
010, 011, 012) correctly cover the areas the architecture document still
lists as open: identifier encoding, exact numeric backing, journal
schema, wire protocol, versioning enforcement, and calendar
representation.  No =Proposed= decision has been prematurely relied upon
by code, because no domain code exists yet.

** Makefile and CI Parity

=make check= runs =fmt-check=, =vet=, =test=, and =race=.  The CI
workflow runs the same four targets through =make=, plus a =go mod tidy=
drift check.  There is no check present in one and absent from the
other.  =make check= passes from a clean checkout of this branch.

** Repository Contents

The Go surface is a single file, =trader.go=, declaring =package trader=
with a one-line doc comment.  There is no speculative package tree, no
partially implemented domain type, and no broker, transport, or
live-session code.  Nothing in the repository can place an order, so the
paper-trading default required by ADR-014 is trivially satisfied.

=go.mod= declares module path =github.com/rustyeddy/trader=, matching the
import paths used throughout the architecture document, and =LICENSE=
contains the BSD 2-Clause text that =README.md= advertises.

* Problems Found

** P1 (high): Issue and pull-request templates were absent

Issue #5 (M0-04 "Add pull-request and issue templates") is closed, but
=.github/= contained only =copilot-instructions.md= and
=workflows/ci.yml=.  There was no =.github/ISSUE_TEMPLATE/= directory and
no =pull_request_template.md=.  =CONTRIBUTING.org= requires every pull
request to explain what changed, why, how it was tested, and which
documentation changed, and defines a Definition of Done that a template
is meant to make visible at authoring time.  That requirement was
unenforced by tooling.  Corrected; see below.

** P2 (high): Package boundaries document was absent

Issue #6 (M0-06 "Document package boundaries and repository rules") is
closed, but =docs/arch/package-boundaries.org= did not exist.  Both
=AGENTS.md= and =README.md= referenced it as planned.  The architecture
document requires dependency direction to be enforced mechanically in
CI; without the boundaries document, neither the rules nor their
enforcement mechanism were specified, and M1 would have begun adding
packages with no written boundary contract.  Corrected; see below.

** P3 (medium): Milestone plan was not in the repository

Issue #7 cites =docs/plans/Trader-M0-TODO.org= as its source, and the
architecture document (Appendix D) cites a companion
=Trader-GitHub-Project-Plan.org=.  Neither file was in the repository, so
the milestone breakdown and per-issue acceptance criteria were not
version-controlled alongside the architecture they implement.  Corrected;
see below.  Because neither source file was ever committed, the plan was
reconstructed from the GitHub issue list and architecture Appendix D
rather than copied.

** P4 (low): Contradictory test-coverage targets

=AGENTS.md= set a coverage target of 85% or greater, while
=docs/workflows/workflows.org= asked for "as close to 100% code coverage
as possible".  Corrected; see below.

** P5 (low): =AGENTS.md= described populated workflow docs as empty

=AGENTS.md= listed both =docs/workflows/workflows.org= and
=docs/workflows/testing.org= as "not yet populated".  =workflows.org= has
content; only =testing.org= remains a stub.  Corrected; see below.

* Deferred Questions

These questions are recorded rather than answered.  None blocks M1.

1. *Default log destination.*  =AGENTS.md= specifies a default log file
   of =/var/log/trader.log=, which is not writable by an unprivileged
   user on a typical Linux host.  Whether the default should fall back to
   stderr, to a user-writable path, or fail loudly is undecided.
2. *Requirements versus ADR-007.*  The requirements document states that
   applications will interact with the broker "through the account".
   ADR-007 splits this into a =broker.Account= handle and an immutable
   =account.Snapshot=.  The architecture document explains the divergence,
   but the requirements document has not been annotated to point at the
   decision that supersedes its phrasing.
3. *Dependency-rule enforcement mechanism.*  The architecture document
   lists =depguard=, =go list=, custom vet analyzers, and =apidiff= as
   candidates.  No mechanism has been selected, and CI runs none of them.
4. *Testify dependency.*  =AGENTS.md= mandates testify, but the module has
   no dependencies and no =go.sum=.  The CI tidy check is written to
   tolerate a missing =go.sum=; that tolerance should be removed once the
   first dependency lands.
5. The open design questions in the architecture document (intent style,
   hedged positions, asset-class scope, multi-account live sessions,
   simulator realism, strategy state ownership, journal durability) remain
   open and are the correct input to M1 and M3 planning.

* Recommendation

*M0 may be closed.*

M0's documentation core is sound: the README, architecture, ADRs, and
contribution guide agree with one another and with the repository, all
links resolve, CI mirrors the =Makefile=, =make check= passes from a
clean checkout, and no premature implementation or live-trading behavior
has been introduced.

The two missing M0 deliverables found by this review have been landed on
this branch: the issue and pull-request templates (M0-04) and the package
boundaries document (M0-06).  Both are guardrails intended to be in place
*before* M1 begins adding packages, and both are now present.  The
milestone plan is also version-controlled, so a future review can detect
a closed issue whose deliverable never landed.

Every M0 exit criterion in =docs/plans/milestones.org= is therefore
satisfied.  M0 may close once this pull request merges; no further review
is required.

The deferred questions above are inputs to M1 planning, not blockers.
The one worth scheduling early is the dependency-rule enforcement
mechanism, because its value decreases as the package tree grows.
