* Purpose

This document defines the remaining work for Trader milestone M0.

M0 establishes the repository foundation, architectural governance, contribution
workflow, CI quality gates, and documentation rules before substantive trading
framework implementation begins.

All tasks in this document are intended to become GitHub issues associated with
milestone =M0=.

Implementation will commonly be performed by an agent. Each task therefore
includes explicit scope, constraints, acceptance criteria, labels, and dependency
notes.

* Current Repository State

The following foundation work is already present:

- The Go module is =github.com/rustyeddy/trader=.
- A Makefile exists with formatting, vet, test, race, and check targets.
- The canonical framework architecture document exists under =docs/arch/=.
- The original framework requirements document exists under =docs/arch/=.
- A single Org ADR document exists at =docs/arch/adr-decisions.org=.
- A minimal root =trader= package exists.
- The repository uses the BSD 2-Clause license.

* Milestone M0 Definition of Done

M0 is complete when:

- The repository clearly explains Trader's purpose and current status.
- Canonical architecture, requirements, ADRs, and package-boundary documents are
  present and internally linked.
- Contribution rules and the project-wide Definition of Done are documented.
- GitHub issue and pull-request templates are installed.
- CI verifies formatting, module tidiness, vetting, tests, and race tests.
- Architecture and dependency rules are clear enough for implementation agents
  to follow without inventing major design decisions.
- No real-money trading behavior is enabled or implied.
- All M0 issues are complete and CI passes on =main=.

** Agent instructions

- A decision index table.
- ADR status definitions:
  - Proposed
  - Accepted
  - Superseded
  - Rejected
- Rules for superseding an accepted ADR.
- A reusable ADR template marked =:noexport:=.

Use this structure for each completed ADR:

#+begin_src org
* ADR-NNN: Decision title

** Status

Accepted

** Context

Describe the forces, constraints, and problem that require a decision.

** Decision

State the architectural decision clearly.

** Consequences

Describe benefits, tradeoffs, restrictions, and follow-on responsibilities.

** Alternatives Considered

Describe credible alternatives and why they were rejected.
#+end_src

Fully document only the architectural decisions already established:

1. Modular monolith before service decomposition.
2. Ports-and-adapters dependency direction.
3. Fresh greenfield repository with controlled legacy code transplant.
4. Strategies emit intents, not broker orders.
5. Execution planning and risk admission are separate stages.
6. Broker account handle is separate from account snapshot.
7. Simulated broker implements the public broker port.
8. Paper trading is the safe default.

Keep less-settled decisions marked =Proposed=, especially:

- detailed external strategy protocol choices
- detailed storage technology choices
- future service decomposition
- synthetic or multi-leg instruments

** Constraints

- Do not silently finalize unsettled architecture.
- Accepted decisions must match the canonical architecture document.
- Do not rewrite the historical meaning of an accepted ADR.
- When a decision changes, mark the old ADR =Superseded= and add a new ADR.

Required checks:

#+begin_src shell
go mod tidy

test -z "$(gofmt -l .)"

go test ./...
go test -race ./...
#+end_src

Review and update the Makefile so that:

- =fmt= modifies files using =go fmt ./...=.
- =fmt-check= detects unformatted files without modifying them.
- =vet= runs =go vet ./...=.

- Do not introduce a large third-party lint suite in M0.

- Use a supported Go version matching =go.mod= or intentionally revise

- Do not commit an unnecessary empty =go.sum=.

** Acceptance criteria

- [ ] CI runs on pushes and pull requests.

- [ ] Incorrect formatting causes CI failure.
- [ ] An untidy module causes CI failure.

* TODO M0-06 Document package boundaries and repository rules
:PROPERTIES:
:LABELS: type:architecture type:documentation area:packages priority:high agent-ready
:MILESTONE: M0
:END:

** Objective

Create a clear package-boundary and dependency-rule document before domain
packages begin to proliferate.

** Agent instructions

Create:

#+begin_example
docs/arch/package-boundaries.org
#+end_example

Document intended dependency direction without creating empty package trees.

Include these rules:

- Domain packages must not import adapters.
- Strategies must not import broker implementations.
- Strategies emit intents and cannot submit orders.
- Risk evaluates proposed exposure and cannot call brokers.
- Execution coordinates approved actions.
- Broker adapters translate external APIs and do not contain trading policy.
- Transport DTOs must not become public domain types.
- Domain behavior must not call =time.Now()= directly.
- Packages must not launch hidden goroutines from =init()=.
- Live trading requires deliberate configuration and cannot be the default.
- New public packages require:
  - a real consumer
  - a documented responsibility
  - a stable reason to be public
- Implementation details should prefer =internal/=.
- Public interfaces should exist at seams where implementations genuinely vary.
- Concrete structs should be preferred for domain values.
- Empty placeholder directories should not be created merely to match a future
  package map.

Include a preliminary directional package map, clearly labeled as non-final.

For example:

#+begin_example
instrument
    ^
marketdata    order    account
    ^          ^         ^
strategy    broker    portfolio
    \          |         /
       application services
               ^
       adapters and commands
#+end_example

Also define a simple package-placement test:

1. Is this type or behavior intended for external framework consumers?
2. Does it have a stable contract?
3. Are multiple implementations expected?
4. Would exposing it constrain internal evolution?

If the answers do not support a public API, prefer =internal/=.

** Constraints

- The package map is directional, not a requirement to create every package now.
- Do not generate empty package directories.
- Do not finalize detailed APIs in this task.
- Keep this document consistent with the canonical architecture and ADRs.

** Acceptance criteria

- [ ] =docs/arch/package-boundaries.org= exists.
- [ ] Dependency-direction rules are explicit.
- [ ] Public versus =internal/= guidance is included.
- [ ] Hidden goroutines and direct =time.Now()= usage are prohibited in domain code.
- [ ] Live trading default-safety rule is documented.
- [ ] Empty placeholder package trees are discouraged.
- [ ] Preliminary package map is labeled non-final.
- [ ] README or canonical architecture links to this document.

** Dependencies

- Should be consistent with M0-02.
- README final links depend on this document.

* Agent Execution Guidance

For every issue generated from this document:

- Work on a dedicated branch.
- Keep scope limited to the issue.
- Read the canonical architecture and relevant ADRs before editing.
- Do not invent unsettled architecture.
- Add or update tests where executable behavior changes.
- Update documentation in the same pull request.
- Run =make check= before opening the pull request.
- Open a draft pull request while work is in progress.
- In the pull request, state:
  - what changed
  - why it changed
  - how it was tested
  - which documentation changed
  - whether an ADR was affected
- Stop and label the issue =needs-design= when requirements conflict or a durable
  architectural decision is missing.
