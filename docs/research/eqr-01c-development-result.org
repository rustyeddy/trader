#+TITLE: EQR-01C: SPY RSI(2)/Regime Forward-Return Study — Development Result
#+STARTUP: overview indent

* Purpose

This document records the first real run of the frozen EQR-01
phenomenon experiment (issue #319, EQR-01C) against SPY D1 development-
partition data, using the EQR-01B (=indicator.RSI=) and this issue's
own new =analysis.RunRSIRegimeEventStudy= capability exactly as
=docs/research/eqr-01-research-protocol.org= specifies. It is a results
record, not a durable architecture decision — it carries no ADR
number.

This document computes evidence. It makes *no* Continue/Reject
decision — that decision is explicitly reserved for EQR-01D, which
must also examine validation-partition results before it can be made.
Nothing below should be read as a recommendation to proceed or not
proceed with strategy work.

** Runner

Unlike the MR-04 precedent (a =research-runs/= throwaway script),
EQR-01C's real-data run lives as a =//go:build fullarchive=-gated Go
test, =marketdata/eqr01c_devrun_test.go=, in the =marketdata_test=
external test package. This is a deliberate deviation from the
=research-runs/= convention, forced by one fact specific to Stooq:
turning Stooq's single-file CSV export into Trader's raw-partition
layout requires =stooq.Import=, which lives under
=marketdata/internal/provider/stooq= — Go restricts that import to
code inside the =marketdata/= directory tree, so an external
=research-runs/= script (outside that tree) cannot call it directly,
the way =research-runs/mr-04= could call OANDA's own already-fetched
raw archive with no import-boundary problem. Placing the runner in
=marketdata_test= (rather than =marketdata='s own internal test
package) avoids an import cycle: =analysis= imports =marketdata=, so
a =package marketdata= test file cannot also import =analysis=.

The test, gated behind the =fullarchive= tag and skipped unless an
operator edits a local, uncommitted path constant, does the following
against the real local Stooq archive (=/srv/trading/data/raw/stooq/spy_us_d.csv=):

1. Filters the source CSV down to development-partition rows only
   (=Date < 2019-01-01=) before it ever reaches the importer, then runs
   =stooq.Import= over that filtered copy into a temporary raw-
   partition root. The filter stops scanning the source file entirely
   at the first row on or after the boundary — relying on (and
   asserting) Stooq's chronologically ascending export order — rather
   than reading the whole file and discarding out-of-range rows
   afterward, so no OHLCV value from any validation or final-holdout
   row is ever parsed or written to the filtered copy, and no line of
   the file after that one boundary-crossing row is even buffered (PR
   #321 review, tightened further on re-review). The boundary-crossing
   row's own line is necessarily read into the scanner's buffer to
   determine its Date, but its OHLCV fields are never parsed or used.
2. Registers SPY as an ETF Listing (=ARCA=, ticker =SPY=, provider
   =stooq=) via =service/marketdata.RegisterETFInstrument=.
3. Builds a =*marketdata.Manager= with a =USEquityCalendar= configured
   via =StandardUSEquityHolidays= for years 2005-2026 — the *full*
   frozen EQR-01 protocol span (development through the frozen final-
   holdout end year), per the protocol's own explicit requirement that
   a narrower configured range is not an equivalent reproducible
   substitute, even though this particular run only ever reads
   development-partition bars (PR #321 review; the calendar
   configuration is a property of the protocol, not of which partition
   one run happens to query).
4. Queries exactly the development partition
   (=[2005-02-25, 2019-01-01)=, half-open) via =Manager.Plan= /
   =Manager.Build= / =Manager.Bars= against that already development-
   only raw archive — validation and final-holdout bars are neither
   ingested, requested, nor read anywhere in this run.
5. Runs =analysis.RunRSIRegimeEventStudy= over the resulting bars with
   the frozen EQR-01 parameters (below) and prints the required
   measurements for both the primary (positive-regime) and secondary
   (all-regime) views.

Invocation used to produce the numbers below (after temporarily
setting =fullArchiveEQR01CSPYCSVPath= to the real local archive path,
then reverting that edit before committing, exactly as
=stooq_fullarchive_test.go='s own established convention requires):

#+BEGIN_SRC sh
go test -tags fullarchive ./marketdata/... -run TestEQR01C_DevelopmentPartition -v
#+END_SRC

Re-running the identical command a second time reproduced every
reported statistic, including every bootstrap confidence interval,
bit-for-bit — confirming the run's determinism per issue #319's own
requirement.

Raw import: the source Stooq export (5,415 total rows, spanning
2005-02-25 through 2026-09-04) was filtered before import by scanning
only as far as the first row on or after 2019-01-01 and stopping —
3,485 rows kept, and no row at or after the boundary was ever parsed
beyond confirming that single row's own out-of-range date. So
=stooq.Import= itself ingested only 3,485 rows (2005-02-25 through
2018-12-31); no validation or final-holdout row's OHLCV data was ever
read by this test, let alone written to the raw-partition archive it
built. The subsequent development-partition query returned those same
3,485 D1 bars. Of those, 3,286 qualify as observations (both RSI(2) and
EMA(200) Ready — EMA(200)'s own 200-bar warmup consumes the partition's
first 199 bars, which is expected and not an ambiguity: the
development partition begins at the archive's own true first day, so
there is no earlier data available to warm up against, exactly as
=docs/research/eqr-01-research-protocol.org= already anticipates
("EMA(200) is undefined during its own warmup and excluded from
observations during that period")). 16,409 forward returns were
computed in total across all five horizons.

No implementation or provenance ambiguity was encountered while
running this experiment; nothing here required stopping to document
an unresolved question.

0.01 = 1%), per the protocol's =R[N] = (Close[t+N]-Close[t])/Close[t]=
definition. "CI" is the 95% bootstrap percentile interval for the
cell's mean return. "Insufficient" marks any cell below the 30-
observation minimum — none occurred in this run; every cell in both
tables below met the threshold.

* Observed Pattern (descriptive only)

The following is a plain, literal restatement of the tables above. It
is descriptive, not evaluative: it draws no Continue/Reject
conclusion, makes no profitability claim, and selects no threshold.
That evaluation is EQR-01D's job, once validation-partition results
also exist.

- Under Regime = Positive, B1's mean return is higher than B5's and
  B6's mean return at every one of the five horizons (for example 1d:
  B1 0.001832 vs. B5 0.000074 vs. B6 0.000217; 10d: B1 0.003768 vs. B5
  0.003641 vs. B6 0.002455).
- B2's mean return under Regime = Positive is likewise higher than
  both B5's and B6's at every one of the five horizons (for example
  1d: B2 0.000902 vs. B5 0.000074 vs. B6 0.000217).
- B3 and B4 (the middle buckets) do not show a consistent ordering
  relative to each other or to B1/B2 — for example B4's 1d and 3d mean
  returns are slightly negative (-0.000047 and -0.000217) while its 5d
  and 10d mean returns are positive and comparable to B3's.
- The bootstrap 95% CI for B1's mean return excludes zero at the 2d
  horizon under Regime = Positive ([0.000855, 0.006984]) but includes
  zero at 1d, 3d, 5d, and 10d.
- The unconditional (secondary) B1 1d mean (0.001484) is lower than
  the positive-regime B1 1d mean (0.001832); the unconditional B6 1d
  mean (-0.000005) is lower than the positive-regime B6 1d mean
  (0.000217).

No claim is made here about statistical significance beyond what the
reported bootstrap intervals literally state, about profitability, or
about which (if any) bucket/horizon combination should inform a future
strategy.
