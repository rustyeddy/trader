#+TITLE: EQR-01D: SPY RSI(2)/Regime Validation Result and Continue/Reject Decision
#+STARTUP: overview indent

* Purpose

This document records the second real run of the frozen EQR-01
phenomenon experiment (issue #320, EQR-01D) — the identical,
unmodified protocol EQR-01C (#319) already ran against development
data, now run against the SPY D1 validation partition — and then
evaluates the frozen Continue/Reject gate from
=docs/research/eqr-01-research-protocol.org= using both the
development and validation results together, exactly as the protocol
requires.

Referenced documents:

- =docs/research/eqr-01-research-protocol.org= — the frozen EQR-01A
  protocol and Continue/Reject gate.
- =docs/research/eqr-01c-development-result.org= — the EQR-01C
  development-partition result this document reuses without
  re-deriving.

No frozen parameter (RSI period, EMA period, bucket boundaries,
horizons, minimum observation count, bootstrap method) was changed
between EQR-01C and this run.

** Revision note

An earlier version of this document (first commit on PR #322) fed only
validation-partition bars (2019-01-01 onward) into the event study,
which restarted RSI(2)/EMA(200) from a cold state at the partition
boundary and discarded validation's own first ~199 sessions to
indicator warmup. Review on PR #322 correctly identified this as
methodologically wrong: partitions separate *evidence*, not
*information* — historical closes before 2019 are legitimate inputs to
=EMA(200)[t]=/=RSI(2)[t]= for an early-2019 observation, and using them
only as indicator context is not validation leakage (no forward-return
label crosses a partition boundary either way). This revision adds an
explicit =ObservationStart= boundary to
=analysis.RSIRegimeEventStudyConfig= (warmup bars still feed the
indicators; only bars at or after =ObservationStart= become
observations) and re-runs validation with development bars supplied as
warmup context. The corrected counts are modestly larger than the
original (development-only-boundary) numbers for the extreme buckets
(B1: 20 -> 26, B2: 15 -> 22) but the substantive finding is unchanged
— see Classification and Decision below.

* Reproduction

** Runner

=marketdata/eqr01d_validationrun_test.go=, a =//go:build fullarchive=-
gated test in the =marketdata_test= external test package, mirroring
=eqr01c_devrun_test.go='s own structure (same reasons for that package
placement apply identically here — see that file's doc comment). It:

1. Filters the source Stooq CSV to rows strictly before 2023-01-01
   (the frozen final-holdout start), stopping the scan entirely at the
   first out-of-range row — the same structural stop-scan mechanism
   PR #321's re-review required for EQR-01C's development boundary. The
   one line straddling the boundary is necessarily read into the
   scanner's buffer to determine its Date, but its OHLCV fields are
   never parsed or used, and no further line is buffered at all.
2. Imports that filtered copy (development + validation rows, 2005-
   02-25 through 2022-12-30) via =stooq.Import=.
3. Registers SPY and builds a =*marketdata.Manager= with
   =USEquityCalendar= + =StandardUSEquityHolidays(2005..2026)= — the
   same full frozen protocol span EQR-01C uses.
4. Queries from the *development* partition's own start
   (2005-02-25) through the validation end (2023-01-01, exclusive) —
   development bars are supplied purely as indicator warmup/context.
   Final holdout remains structurally unreachable: the query's own End
   is still 2023-01-01, and final-holdout rows were never even
   ingested (step 1).
5. Runs =analysis.RunRSIRegimeEventStudy= (the exact, unmodified
   EQR-01C capability, extended only by the new, additive
   =ObservationStart= field) with =ObservationStart= set to
   2019-01-01: RSI(2)/EMA(200) are warmed up on the full development
   history, but only bars at or after 2019-01-01 become observations or
   contribute forward-return evidence. The test asserts directly that
   no reported =Observation= predates =ObservationStart=.
6. Uses a bootstrap seed distinct from EQR-01C's own (=Seed1=320,
   Seed2=2000=, following the same "issue number, resample count"
   mnemonic convention) so the two partitions' resampling draws are
   independent.

Invocation used to produce the numbers below (after temporarily
setting =fullArchiveEQR01DSPYCSVPath= to the real local archive path,
then reverting that edit before committing):

#+BEGIN_SRC sh
go test -tags fullarchive ./marketdata/... -run TestEQR01D_ValidationPartition -v
#+END_SRC

Re-running the identical command a second time reproduced every
reported statistic, including every bootstrap confidence interval,
bit-for-bit.

* Adversarial Review Against the Frozen Continue/Reject Criteria

This section evaluates =docs/research/eqr-01-research-protocol.org='s
own frozen gate, criterion by criterion, using development and
validation together. No criterion or evidence bar is invented or
adjusted after seeing these results.

** Ordered tendency toward higher forward returns as RSI(2) decreases (both partitions independently)

*Development*: B1 and B2 mean returns exceed B5 and B6 at every one of
the five horizons (=docs/research/eqr-01c-development-result.org='s
own "Observed Pattern" section) — a genuine ordered tendency in the
predicted direction.

*Validation*: this does *not* hold for B1. At four of five horizons
(1d, 2d, 3d, 10d) B1's mean return is negative, and at every one of the
five horizons B1's mean return is lower than B5's mean return (for
example 1d: B1 -0.000860 vs. B5 0.000882; 10d: B1 -0.008106 vs. B5
0.004064). B1 is lower than B6 at four of five horizons as well (all
except 5d, where B1 0.001891 narrowly exceeds B6 0.001570). B2 is mixed
— positive at four of five horizons (all except 2d) but exceeding B5's
mean at only two of five horizons (1d, 5d), never clearing B5 or B6 by
a margin distinguishable from noise, and its own confidence intervals
are wide and always include zero.

*Finding*: the required ordered tendency is present in development but
*reversed* at the single most extreme bucket (B1) in validation, at
nearly every horizon. This is exactly the Reject condition the protocol
names explicitly: "a pattern present in one partition but absent or
reversed in the other."

** Extreme buckets (B1/B2) meaningfully stronger than non-extreme (B5/B6), both partitions

Fails in validation for B1 specifically (see above: B1 underperforms
B5 at every horizon and B6 at four of five horizons in validation, the
opposite of "meaningfully stronger"). B2 does not clearly outperform
B5/B6 in validation either — it exceeds B5's mean at only two of five
horizons (1d, 5d) and its confidence intervals never exclude zero.

** Minimum observation-count adequacy (B1/B2 in both partitions)

*Development*: B1 (88) and B2 (91) both comfortably exceed the 30-
observation minimum.

*Validation*: B1 (26) and B2 (22) both remain *below* the 30-
observation minimum and are explicitly marked =Insufficient=true= in
the table above, even after correctly supplying development bars as
indicator warmup (this revision's fix improved the counts from the
original development-only-boundary run's 20/15, but not enough to
clear the threshold). This is a second, independent Reject condition
the protocol names explicitly: "insufficient observation counts
throughout the relevant buckets in either partition." SPY's 2019-2022
window simply produced far fewer extreme-oversold (RSI(2)<10) days
than the 14-year development window did, on a per-observation basis —
a real property of the instrument/period, not an artifact of indicator
warmup.

** Confidence-interval width and distinguishability from zero

Every B1 and B2 confidence interval in validation includes zero — none
show a mean return distinguishable from zero at the 95% level, at any
horizon. This is the opposite of the Continue criterion ("bootstrap CI
excludes zero for at least B1 at the horizon(s) showing the effect, in
both partitions"): development had exactly one horizon (2d) where B1's
CI excluded zero; validation has none, at any bucket among B1/B2, at
any horizon.

** Mean vs. median consistency (outlier sensitivity)

In validation, B1's mean and median diverge substantially and even
disagree in sign at several horizons (for example 1d: mean -0.000860,
median +0.003246; 3d: mean -0.001628, median +0.001978; 10d: mean
-0.008106, median -0.000785 — same sign but very different magnitude).
With only 26 observations, this is consistent with a small sample where
a handful of large negative outliers pull the mean well below the
median — exactly the outlier sensitivity the protocol's own review
checklist asks to be examined rather than accepted at face value. This
makes B1's negative mean in validation *less*, not more, interpretable
as a reliably reversed effect on its own; it does not rescue it as
supporting evidence either — the sample is too small and the mean/median
disagreement too pronounced to draw any conclusion in either direction,
consistent with the independent "insufficient count" finding above.

** Positive-return-rate consistency

B1's positive-return percentage in validation ranges 42.3%-57.7% across
horizons — not clearly above 50% the way development's B1 was
(56.8%-65.9% across horizons). No consistent signal here either.

** Horizon consistency vs. isolated-horizon effect

Development's own effect was concentrated at short-to-medium horizons
(clearest CI-excludes-zero result at 2d). Validation shows no horizon
at which B1 or B2 clears the bar — this is not a case of "the effect
moved to a different horizon"; it is absent at every horizon tested.

** Does positive-regime conditioning add evidence consistent with the hypothesis?

In validation, the primary (positive-regime) and secondary (all-
regime) B1 numbers are not clearly more supportive of the hypothesis
under regime conditioning — for example validation B1 10d is negative
in both views (primary -0.008106, secondary -0.013206), and 1d/2d/3d
are all more positive in the secondary (unconditional) view than in
the primary (positive-regime) view, which is backwards from what the
hypothesis's regime-conditioning rationale would predict. Regime
conditioning does not rescue the extreme-bucket result in validation,
unlike its modest effect in development.

** Secondary (all-regime) comparison

Reported above and not promoted to confirmatory evidence, per the
protocol's own requirement. Its B2 numbers are more consistently
positive than the primary view's (for example 1d: secondary 0.007444
vs. primary 0.002390), which if anything argues the positive-regime
condition is doing *less* work in validation than the protocol's
Continue criterion would want to see, not more.

** Implementation, provenance, calendar, adjustment, and partition-boundary check

- Frozen parameters unchanged from EQR-01C: confirmed by direct
  comparison of =eqr01d_validationrun_test.go='s configuration
  constants against =eqr01c_devrun_test.go='s (same RSI period, EMA
  period, horizons via the same =analysis.EQR01Horizons()= call, same
  minimum observation count, same bootstrap resample count and
  method).
- Calendar: identical =StandardUSEquityHolidays(2005..2026)= full-span
  configuration EQR-01C uses (PR #321's own fix), not a narrower range.
- Adjustment/provider: identical (stooq, split-adjusted).
- Indicator warmup: development bars (2005-02-25 onward) feed
  RSI(2)/EMA(200) continuously through validation, via the new,
  additive =ObservationStart= config field — added specifically by
  this issue's own review, not a pre-existing capability silently
  reused. =ObservationStart= only filters which bars become
  observations; it does not change how bars feed the indicators, and
  it defaults to the zero value (no restriction) everywhere EQR-01C's
  own development run uses the type, so development's already-reported
  result is unaffected by this addition (verified: EQR-01C's config
  never sets the field).
- Partition boundary: every reported =Observation= falls within
  =[2019-01-01, 2023-01-01)= (asserted directly in the test); no
  forward-return label extends past 2022-12-30 (the last queried bar),
  since =RunRSIRegimeEventStudy= never computes a return whose future
  index falls outside the supplied bars, regardless of
  =ObservationStart=. The raw-partition archive this run built never
  had a final-holdout byte read into it at all (structural stop-scan,
  mirroring EQR-01C's own PR #321 re-review fix).
- No leakage, parameter mining, or protocol drift was found: no
  threshold, bucket, horizon, or period was changed between the
  development and validation runs; the only change from the first
  version of this document is fixing an indicator-warmup bug the
  review process itself caught before acceptance.

** No accidental holdout access

Confirmed structurally, not merely by convention:
=filterCSVBeforeFinalHoldout= stops scanning the source CSV the moment
it reaches the first row on or after 2023-01-01. That one boundary
row's line is necessarily read (into the scanner's buffer) to determine
its Date, but no OHLCV value from it — or from any row after it — is
ever parsed or written to the filtered copy, and no further line of the
source file is even buffered. The raw-partition archive this test
built therefore contains no final-holdout row, and the query itself
additionally never requested anything at or after 2023-01-01. Final
holdout was not accessed in the production of this document.

* Classification and Decision

** Classification: Not Supported
