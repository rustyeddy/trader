#+TITLE: ADR-081: OANDA account activity import
#+STARTUP: overview indent

* Status

Accepted. Issue #510; amended by issue #511 (the final fill representation,
below). Builds on ADR-079 (activity model), ADR-080 (store and
checkpoints) and ADR-078 (secrets). ORDER_FILL execution detail beyond what
is listed here is issue #511; the Alpaca source is #516; the CLI is #514.

* Context

OANDA history has to reach the activity ledger safely and repeatably. The
provider-specific part (fetching, paging, normalizing) must be separable from
the part every provider shares (store, checkpoint, retry), so Alpaca can reuse
the latter.

* Decision

** Three pieces

- =accountactivity.Source= (domain port): =Stream()= and =Next(ctx, cursor)=,
  returning a =Page= of normalized activities, the cursor to checkpoint after
  them, and whether it is done. A Source does no storage and keeps no durable
  state; =Next= is a pure function of the cursor and the provider's data, so a
  replay after any failure refetches the same page.
- =internal/service/accountactivity.Sync=: the provider-neutral loop. Read the
  checkpoint, fetch a page, stamp =ImportedAt= from the injected clock, =Apply=
  the batch (activities and cursor together, ADR-080), repeat. It never reads
  the wall clock and never advances a checkpoint except through =Apply=. A
  source that neither advances nor finishes is an error, not a spin.
- =internal/adapters/accountactivity/oanda=: the OANDA Source, with its own
  small read-only client. It cannot reuse the market-data OANDA client, which
  is internal to =internal/marketdata=.

** Paging and cursor

OANDA transaction IDs are per-account sequential integers, so the source pages
by ID range (=idrange=, 500 IDs per page by default, at most 1000). The cursor
is the last ID of the last page. The end of history is the account summary's
=lastTransactionID=, read once per Source, so a run covers a stable range
while the account keeps trading; the next run, with a new Source, picks up
what arrived since. A bounded bootstrap first resolves a time window to an ID
window with the transactions list endpoint, then pages that window. A
checkpoint earlier than the window starts at the window; one past it means
nothing to do.

** Normalization

Amounts, units and prices are decoded as strings and parsed straight into =num=
types, never through binary floating point. Money is in the account home
currency from the summary. Absent fields are unknown; reported zeros are
reported zeros. Every value carries =ReportedFrom= with OANDA's field name.

- ORDER_FILL -> fill: instrument, side from the sign of units, quantity,
  realized P/L, financing, commission, guaranteed-execution fee,
  =halfSpreadCost= (broker-reported), order and batch IDs, =fullVWAP=, the
  =fullPrice= snapshot, and a =TradeEffect= for every trade opened, reduced or
  closed (see "Fill representation").
- DAILY_FINANCING -> financing. TRANSFER_FUNDS -> deposit or withdrawal by the
  sign of the amount (zero is =KindOther=). DIVIDEND_ADJUSTMENT -> dividend.
- Anything else, and a fill in an instrument Trader cannot yet identify, ->
  =KindOther=: ID, time, provider type, order ID, batch ID and the
  provider-native instrument name are kept, no economics are claimed. Nothing is dropped. =KindOther= is added to ADR-079's
  vocabulary for this; it has no required or allowed economic fields.
- A recognized transaction that fails to parse is an error. The page is not
  stored, the checkpoint does not move, and the failure is visible.

** Sign convention

OANDA documents =commission= and =guaranteedExecutionFee= as positive
quantities that reduce the balance. ADR-079 holds money account-centric, so
those two are negated on the way in (a cost is negative). Realized P/L and
financing are already signed and are not changed. =halfSpreadCost= is
different: OANDA defines it as positive or negative, so it is stored with the
sign the broker reported and is the one documented exception to the
account-centric convention; negating it would turn a legitimate negative
into a credit. Tests cover both signs of each. Commission and fee handling
follow the v20 documentation and should be confirmed against a real practice
account before the numbers are relied on.

** Time bounds

A bounded import is half-open, =[From, To)=, like every Trader range. OANDA
treats both =from= and =to= as inclusive and accepts at most 365 days per
list request, so the source asks for the instant before =To=, cuts the window
into spans of at most 365 days (contiguous, never overlapping), and merges
their ID windows (IDs are sequential in time). =From= is required for a
bounded import; a bound with no =To= runs to "now" from an injected clock. A
list that reports matching transactions but links no pages is a bad response,
not an empty window, and an idrange response without a transactions array is
a bad response, not an empty page, so neither can move the checkpoint past
history that was never fetched.

** Instruments and provenance

Only a pair of known fiat currencies becomes an =fx:= instrument. The
standard currency parser accepts any three to five capitals, so a metal,
commodity or index code would otherwise pass as a currency; an explicit list
separates them. Every activity keeps the provider-native instrument name
(=ProviderInstrument=) beside the canonical one, and the broker's batch ID
(=BrokerBatchID=), so an event Trader cannot model today can be re-normalized
later without re-fetching from the provider.

** Credentials and failure

The bearer token comes from a =CredentialProvider= supplied by the
composition root from the environment or a token file (ADR-078); the package
reads no configuration and no error contains the token. HTTP failures are
classified (unauthorized, bad request, rate limited, unavailable) and are not
retried inside the client: the sync is replay-safe, so a failed run is run
again.

** Fill representation (issue #511)

An ORDER_FILL is stored as the broker's execution facts at the finest grain
OANDA supplies, with nothing relabelled as slippage:

- *Per-trade effects.* Each of =tradeOpened=, =tradeReduced= and every
  =tradesClosed= entry becomes a =TradeEffect=: trade ID, role, units, the
  exact price, realized P/L, financing, half-spread cost and guaranteed-
  execution fee, each a reported value with its OANDA field as the source and
  unknown when OANDA omitted it. OANDA documents these embedded prices as the
  exact, official execution prices. Units are sizes; the sign of the fill's
  units is the side.
- *The top-level =price= is not authoritative.* OANDA deprecates it. It is
  kept as the fill-level =Price=, with its source recorded as
  "price (deprecated aggregate)", and is optional when per-trade prices exist
  (a fill needs a price from somewhere). No fill-level canonical VWAP is
  invented; if one is wanted later it is derived from the per-trade prices and
  units and marked Derived with a named method.
- *=fullVWAP= is kept separately, as reported.* It is the price the units
  should have been filled at absent guaranteed-price execution, so it differs
  from the actual price when guaranteed execution applies. It does not replace
  =Price= or any per-trade price.
- *=fullPrice= is kept whole.* The bid and ask ladders with the liquidity at
  each rung, the closeout bid and ask, and the quote time are stored as one
  reported =ExecutionQuote=. The ladders are not cut to the top of the book:
  a fill larger than the first rung walks the ladder, and its cost cannot be
  reproduced later without it. It is a market snapshot and a benchmark
  candidate for #513, which records its own derivation method; deprecated
  status and conversion fields are not carried. It is preserved whole or not
  at all: a snapshot missing its time, either ladder (an explicit empty array
  is valid) or either closeout price is malformed provider data and fails the
  page, as with the list and idrange schemas. Every rung needs a positive price
  and positive liquidity. A quote compares equal to itself however it was
  written (time zone, empty versus absent ladder), so a replay is never a
  false conflict.
- *Slippage needs the fill-level price.* A scalar slippage is measured from a
  scalar execution price. Per-trade prices do not supply one: which trade, or
  what units-weighted aggregate, would be an unstated derivation. A fill is
  valid on per-trade prices alone, but slippage validates only against the
  fill-level =Price=. Deriving a fill-level VWAP from the trade effects, or
  modelling execution quality per effect, is #513's decision.
- *Guaranteed execution* is captured as the per-trade
  =guaranteedExecutionFee= (a positive cost in OANDA's data, negated). No
  boolean is invented from a field the v20 schema does not document, and none
  is inferred from a nonzero fee.
- *Aggregates reconcile, tests say so.* OANDA defines the fill-level half-
  spread cost as the sum of the embedded values; tests check that spread
  cost, realized P/L, financing, the fee and units reconcile with their
  per-trade parts on every fill fixture, including a reversal (closes one trade
  and opens another) and a partial reduce with a multi-trade close. A
  mismatch is visible and the stored data is never corrected.

** Ledger compatibility before the CLI

#510 stored a smaller form of the same provider activities, and ADR-080 makes a
differing record under the same key a conflict. Nothing user-facing writes a
ledger until #514, so #511 is the final canonical v1 form: the file schema is
bumped to 2, a schema-1 ledger is refused with instructions to delete the
stream directory and re-import, and the store keeps its append-only rule
without a quiet "unknown to known" upgrade. Once #514 ships, persisted
compatibility is a stricter matter.

* Consequences

Order create and cancel events are stored as =KindOther= with the order ID, so
later order-history semantics can be added without re-importing. CFD and
metal fills are =KindOther= until instrument mapping exists, which is
visible in the sync result's =Other= count but loses their economics until
then. Wiring to configuration and the command line is #514.
