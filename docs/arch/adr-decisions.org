#+title: Trader Architecture Decision Records
#+startup: overview

* Purpose and Usage

This document is the single-file registry of architecture decision records
(ADRs) for the Trader framework.  An ADR captures one architecturally
significant decision, the context that forced it, and the consequences of
choosing it.

Use this registry to:

- Discover *why* a boundary, contract, or dependency direction exists.
- Determine whether a proposed change conflicts with an accepted decision.
- Record new decisions as the framework evolves.

Guidance for contributors:

- Read the canonical architecture document
  =docs/arch/trader-framework-architecture.org= before proposing or amending an
  ADR.
- Every ADR that violates an architectural invariant listed in the
  architecture document requires an explicit ADR of its own.
- Prefer adding a new ADR over silently editing an accepted one.
- Keep each ADR short: one decision, one page when practical.
- Use the reusable template at the end of this document when adding a new
  ADR.
- When a decision is not yet settled, keep the ADR in =Proposed= status
  rather than promoting it to =Accepted=.

* Status Definitions

Every ADR carries exactly one status.

- =Proposed=: The decision is under consideration.  It may be discussed,
  amended, or withdrawn.  Downstream code must not assume the decision is
  final.
- =Accepted=: The decision is in force.  Code, reviews, and future ADRs must
  respect it.  Amending an accepted ADR is not allowed; supersede it
  instead.
- =Superseded=: The decision was previously accepted but has been replaced
  by a later ADR.  The record is preserved for history and must reference
  the ADR that supersedes it.
- =Rejected=: The decision was considered and explicitly not adopted.  The
  record is preserved so the option is not silently revisited.

* Supersession Rules

An accepted ADR may only be replaced through the following process:

1. Draft a new ADR that clearly states the new decision, its context, and
   the consequences of the change.
2. Reference the ADR being replaced in the new ADR's =Context= section.
3. When the new ADR is =Accepted=, update the superseded ADR by:
   - Changing its status to =Superseded=.
   - Adding a =Superseded by= line naming the replacing ADR.
   - Leaving the original =Context=, =Decision=, =Consequences=, and
     =Alternatives Considered= sections unchanged so historical meaning is
     preserved.
4. Update the decision index below to reflect both status changes.

Never rewrite the decision or context of an accepted ADR to change what it
originally meant.  A superseded ADR remains a record of what Trader
believed at that time.

* Partial Amendment Rules

Full supersession assumes one ADR records one decision.  Some ADRs in
this registry bundle several genuinely separate decisions under one
number (ADR-012, for example, decided the =Interval=/=TimeRange=/
=Calendar= types, =FXCalendar='s D1/W1 rollover alignment, *and* a
UTC-clock alignment rule for sub-day bars, all in one document).  When a
later ADR corrects exactly one such sub-decision and every other
decision in the original ADR remains correct, marking the *entire*
original ADR =Superseded= would misrepresent it: a reader would
reasonably conclude every decision in it was replaced, when most were
not.

A *partial amendment* is the alternative for exactly this case:

1. The amending ADR's =Context= section names the specific sub-decision
   being corrected, quotes or closely paraphrases the exact original
   wording, and explains why it was wrong — the same evidentiary bar a
   full supersession's =Context= already requires.
2. The amending ADR's own =Status= is =Accepted= like any other adopted
   decision.  It does not change the original ADR's =Status=: the
   original stays =Accepted=, because everything in it *except* the
   named sub-decision remains in force exactly as before.
3. The original ADR gains one small, additive line under its own
   =Status= section — =Amended by ADR-NNN: <one-line description of the
   specific sub-decision corrected>= — the same append-only spirit as a
   full supersession's =Superseded by= line.  Nothing else in the
   original ADR's =Status=, =Context=, =Decision=, =Consequences=, or
   =Alternatives Considered= sections is rewritten; the non-rewrite rule
   above applies identically to a partial amendment.
4. Update the decision index below with a note under the original ADR's
   row, the same way ADR-020's own row already carries an explanatory
   note.

Reading =Accepted= on an ADR that carries an =Amended by= line means: in
force, except for the specific sub-decision the amendment names, which is
governed by the amending ADR instead.  A partial amendment is a narrower
tool than full supersession and should be used only when the original
ADR genuinely bundles independent decisions and only one is being
corrected — when in doubt, or when the amendment touches most of what
the original decided, use full supersession instead.

* ADR-001: Modular monolith before service decomposition

** Status

Accepted

** Context

Trader must support several execution modes: user-built applications,
first-party CLIs, backtests, scanning, and live trading.  A distributed
microservice platform would introduce networking, deployment, and
observability complexity before Trader's domain contracts are stable.  At
the same time, Trader must retain the ability to split components (data
service, live manager, strategy host, API gateway) into separate processes
when operational requirements demand it.

** Decision

Trader begins as a single Go module structured as a modular monolith with
clearly delineated packages and =internal/= boundaries.  Process boundaries
are introduced only for operational reasons such as separate failure
domains, differing scale, credential isolation, independent deployment
cadence, language-independent strategies, or a data service shared by many
consumers.

** Consequences

- Fast local development and simple deployment during the =v0= period.
- Composition roots choose deployment shape without touching domain code.
- Package acyclicity and dependency direction must be enforced
  mechanically because the compiler alone will not catch service-shaped
  regressions.
- Any future split requires that existing package boundaries already
  behave as ports, not shared globals.

** Alternatives Considered

- *Microservices from the start.* Rejected because it would freeze
  premature contracts, add operational cost, and slow iteration on the
  domain model.
- *Monolith with no explicit package boundaries.* Rejected because it
  would allow implicit coupling that cannot later be extracted without a
  rewrite.

* ADR-002: Ports and adapters dependency direction

** Status

Accepted

** Context

Trader integrates with multiple brokers, data vendors, storage engines,
and transports.  Coupling domain concepts to any specific vendor SDK,
database schema, or wire protocol would prevent multi-broker support,
deterministic testing, and independent evolution of adapters.

** Decision

Trader follows a ports-and-adapters architecture.  Public domain and
application packages define ports.  Brokers, market-data vendors,
persistence engines, journals, and transports are adapters that depend on
the domain, not the other way around.  Dependencies point inward toward
stable domain concepts.

** Consequences

- Domain packages do not import brokers, databases, transports, or CLI
  frameworks.
- Adapters can be swapped, faked, or mocked without changing domain code.
- Simulated brokers, in-memory data sources, and deterministic clocks are
  first-class implementations of the same ports used in production.
- Contract tests become the primary guarantee that adapters honor their
  ports.
- Dependency direction must be enforced in CI (for example with
  =depguard=, =go list=, or a custom dependency check).

** Alternatives Considered

- *Layered architecture with vendor SDK types leaking into the core.*
  Rejected because it makes multi-broker support and deterministic testing
  impractical.
- *One universal broker/data interface covering every provider capability.*
  Rejected in favor of a small required core plus capability discovery, so
  differing provider feature sets are represented honestly.

* ADR-003: Instrument versus listing identity

** Status

Accepted

** Context

Symbols collide across venues, brokers rename products, and futures
contracts expire.  The architecture proposes distinct concepts for
economic instruments, venue listings, and specific contracts.  Issue #25
(M1-07) required settling the exact identifier scheme, the field split
between =Instrument= and =Listing=, and — the one genuine inconsistency
found during design review — whether a futures =Instrument= denotes a
contract family (e.g. E-mini S&P 500) or one specific expiring contract
(e.g. ES December 2026).

** Decision

=instrument.ID= is canonical and deterministic, never a generated
identifier: two calls to the same per-kind constructor with the same
normalized economic attributes always produce an equal ID, regardless of
which provider symbol spelling produced the inputs.  This is a different
identity scheme from the =id= package's =ID[K]=, which is deliberately
random and regenerated per event; instruments must not receive a fresh
identity every run.  Six initial kinds are supported: =KindCurrencyPair=,
=KindEquity=, =KindETF=, =KindFuture=, =KindContinuousSeries=, and
=KindIndex=.

=Instrument= holds economic identity only: what the thing is, independent
of provider or venue.  =Listing= holds venue-specific trading mechanics:
provider symbol (display-only, never identity), tick size, quantity
increment, contract multiplier, settlement currency, and current
tradability, via a separate =Spec= value embedded in =Listing=.

A futures =Instrument= is one specific expiring contract, not the contract
family: ES December 2026 and ES March 2027 are distinct =Instrument=
values, because expiration is part of what makes them the actual, distinct
orderable economic objects — the same way base/quote defines a currency
pair's identity.  A continuous, back-adjusted research series is not a
flag on a =Listing= of what looks like a tradable contract; it is its own
kind, =KindContinuousSeries=, with its own ID constructor and no single
expiration.  This makes "tradable versus research-only" and "a specific
contract versus its continuous series" decidable from =Kind= alone.

Equity and ETF identity uses exchange+ticker as Trader's =v0= identity
convention, explicitly documented as a convention rather than a claim of
permanent global security identity — corporate actions, ticker reuse, and
venue changes remain a known, deferred concern.

A =Resolver= mapping Trader IDs to provider- or broker-native symbols, and
any persistent registry/catalog beyond this deterministic construction
scheme, remain future, additive concerns and are not part of this
decision.

** Consequences

- Prevents symbol collisions across brokers without a generated identifier
  or a persistent registry.
- Two different provider adapters parsing different spellings of the same
  instrument converge on the same =Instrument= automatically once they
  normalize into typed inputs (=num.Currency=, exchange, ticker) before
  constructing an ID.
- Futures require two kinds rather than one, and a =Listing= is never
  itself the unit that distinguishes a contract from its continuous
  series.
- Equity/ETF identity is acknowledged as provisional; a more durable
  identity scheme is a later, additive change if exchange+ticker proves
  insufficient.
- Multi-leg and synthetic instruments remain an explicit deferred concern,
  mechanically enforced by an architecture test rejecting leg/synthetic
  field names in the =instrument= package.

** Alternatives Considered

- *Single =Symbol= string as identity.* Rejected because it cannot
  represent multi-venue listings or expiring contracts safely.
- *Generated (ULID-style) instrument identity, matching the =id=
  package's other kinds.* Rejected because it would give two
  representations of the same real-world instrument — or the same
  instrument across two runs — different identities, which is exactly
  backwards for something with natural economic identity.
- *Futures =Instrument= as the contract family, with expiration living on
  a =Listing= or a new =Contract= type.* Considered and rejected during
  design review: it required inventing a third top-level concept solely to
  hold what is actually part of a contract's identity, and blurred
  =Listing='s meaning from "how a venue exposes an instrument" into also
  meaning "which specific contract."

* ADR-004: Exact numeric representation

** Status

Accepted

** Context

Prices, quantities, money, balances, fees, and authoritative PnL must be
exact to satisfy accounting and broker validation.  Analytical calculations
such as indicators may safely use floating point.  The specific numeric
backing (decimal library, scaled integers, or Trader-owned types) is not
yet chosen.

** Decision

Introduce distinct exact types for =Price=, =Quantity=, =Money=, =Rate=,
and =Currency=, backed by a signed scaled int64 at a common 1e8 scale
(package =num=, =num/internal/fixed=).  Analytical code may use
=float64= internally and convert to exact values only at order or
accounting boundaries.  =Money= carries a mandatory =Currency= and
rejects cross-currency arithmetic and comparison outright; the one
sanctioned currency-conversion operation is =Money.Convert=, added by
ADR-019 for the =portfolio= package's cross-account aggregation; it
requires an explicit target currency and an explicit rate and performs
only the arithmetic — rate provenance is the caller's responsibility.

** Consequences

- Prevents accidental confusion between prices, quantities, and
  percentages.
- Requires validation against tick size and quantity increment at
  boundaries.
- Increases API surface but improves correctness at the accounting edge.
- Currency conversion is opt-in and explicit rather than an implicit
  side effect of ordinary arithmetic, which keeps every other =Money=
  operation safe from silently crossing currencies.

** Alternatives Considered

- *One generic decimal type for all numeric values.* Rejected because it
  would allow price/quantity/money confusion at compile time.
- *Raw =float64= throughout.* Rejected because it cannot satisfy exact
  broker or accounting semantics.

* ADR-009: Journal and reconciliation model

** Status

Proposed

** Context

Live trading needs durable records of intents, proposals, risk decisions,
broker events, and state transitions.  Reconciliation compares Trader's
local projections against authoritative broker state after restart or
disconnection.  The precise record schema, storage format (JSONL,
SQLite, or other), retention policy, and reconciliation algorithm are not
yet finalized.

** Decision

Adopt a journal-first model in which the journal is more fundamental than
formatted reports and reconciliation produces explicit, journaled
differences rather than silently overwriting local state.  Concrete
schemas, storage adapters, and retention policies will be ratified by
later ADRs.

** Consequences

- Reports and audits derive from the journal.
- Reconciliation is observable and reversible.
- Storage adapters remain replaceable behind a narrow port.

** Alternatives Considered

- *Full event-sourced system.* Deferred; snapshots plus append-only
  records are expected to be sufficient for =v0=.
- *No structured journal, only logs.* Rejected because it prevents replay
  and audit.

* ADR-010: gRPC primary external strategy protocol; MQTT integration transport

** Status

Proposed

** Context

Out-of-process strategies require ordered request/response and streaming
semantics with clear versioning.  MQTT is useful for fan-out but lacks
built-in ordering, deduplication, and acknowledgement suitable for
execution-critical control flow.  The exact protocol shape, schema, and
capability negotiation are still under design.

** Decision

Plan to use gRPC with Protobuf as the primary out-of-process strategy
control-plane protocol, and MQTT as an integration transport for
telemetry, market/event fan-out, dashboards, and alerts.  Specific
message shapes, versioning strategy, and SDK layout remain open.

** Consequences

- External strategies gain ordered, typed, versioned control flow when the
  protocol is ratified.
- MQTT remains available for loosely coupled consumers.
- Transports remain adapters over application services; core packages do
  not import them.

** Alternatives Considered

- *MQTT-only strategy protocol.* Rejected as the sole execution-critical
  path because delivery semantics are too weak without extensive custom
  additions.
- *HTTP polling.* Rejected as the primary control plane because it lacks
  clean streaming semantics for market events.

* ADR-011: Public API and semantic-versioning policy

** Status

Proposed

** Context

Trader must eventually promise stability of a public API.  Central
contracts are still being discovered and users have not yet exercised the
API surface.  Freezing =v1= before real applications exist would either
force premature abstractions or promise stability that cannot be honored.

** Decision

Follow semantic versioning.  Remain at =v0= while central contracts are
being discovered.  Exact deprecation, changelog, and API-diff enforcement
rules will be ratified by a later ADR.

** Consequences

- Users are warned that =v0= APIs may evolve.
- Contract tests and runnable examples are required to demonstrate the
  intended usage of any candidate stable API.
- Adapter authors have a clear signal that ports may still change.

** Alternatives Considered

- *Immediate =v1= release.* Rejected because it would freeze contracts
  before they have been validated.
- *No versioning policy.* Rejected because downstream users need a
  predictable evolution model.

* ADR-012: Trading calendar and bar-alignment semantics

** Status

Accepted

Amended by ADR-021: the sub-day (M1/H1/H4) UTC-clock alignment rule
stated in the Decision section below is corrected — real OANDA H4 data
disagreed with it (issue #99).  Every other decision in this ADR (the
=Interval=/=TimeRange=/=Calendar= types, =FXCalendar='s D1/W1 rollover
alignment, DST handling) remains in force, unchanged.  See the Partial
Amendment Rules above.

** Context

Daily, weekly, and monthly bars must align to trading sessions or named
calendars, not solely to elapsed seconds.  Trader must eventually support
exchange sessions, holidays, early closes, futures session boundaries,
and FX week boundaries.  Issue #27 (M1-09) required settling the initial
=Interval= and calendar vocabulary: how a bar interval is represented
without core string parsing, how daily/weekly bars align to something
other than UTC midnight, how DST transitions are handled, and how closed
markets, holidays, and incomplete bars are made representable — scoped to
a basic FX calendar, with non-FX session calendars, resampling, and
coverage tracking explicitly deferred to M2.

** Decision

=marketdata.Interval= is a typed =Unit= (=UnitMinute=, =UnitHour=,
=UnitDay=, =UnitWeek=) plus a count, constructed via =NewInterval= or one
of five predefined values (=M1=, =H1=, =H4=, =D1=, =W1=).  Intervals are
never parsed from provider-native strings such as ="H4"= in core code;
=Interval.String= exists only for display and is documented as
one-directional.

=marketdata.TimeRange= is the shared half-open range type, =[start,
end)=, used for sessions and bars alike.  =Contains= includes =start= and
excludes =end=; =Elapsed(now)= reports whether a range has finished,
expressing bar completeness without a separate concept.

=marketdata.Calendar= is a small interface — =Status=, =Session=, =Bar= —
kept as an interface rather than a single concrete type because the
architecture document's "Important Missing Requirements" section already
commits M2+ to exchange, futures, and holiday calendars distinct from FX;
a second implementation is a documented near-term certainty, not a
speculative one.  Every =Calendar= method is a pure function of its
=time.Time= argument; no implementation may call =time.Now=.

=marketdata.FXCalendar= is the one =Calendar= implementation this
decision ships, covering spot FX's continuous weekly session: open Sunday
17:00 and closed Friday 17:00 through Sunday 17:00, both in
=America/New_York= civil time, with a daily rollover at 17:00 New York
time on every other day.  =D1= bars align to that daily rollover; =W1=
bars align to the Sunday 17:00 week open.  Minute and hour bars instead
align to the UTC clock, via truncation since the Go zero time — which
falls at 00:00:00 UTC — so =H4= bars land on 00:00/04:00/.../20:00 UTC
regardless of date.  =FXCalendar= only aligns
single-day and single-week bars; multi-day/multi-week counts report an
error rather than inventing an untested grouping convention, since
grouping is a resampling concern this issue explicitly excludes.

DST correctness comes directly from computing rollover instants with
=time.Date= in the =America/New_York= =*time.Location=, which resolves
the correct UTC offset for whichever regime applies on that date — no
manual offset arithmetic.  =FXCalendar= blank-imports =time/tzdata= to
embed the IANA database in the binary, so DST transitions resolve
identically regardless of the host's installed time zone data; this is a
deliberate binary-size tradeoff (roughly 450 KB) made in favor of
deterministic backtests, not an incidental one.

Holidays are representable via an optional =FXCalendarParams.Holidays=
list: each entry's Year/Month/Day fields, read literally regardless of
its own time-of-day or Location, name a New York civil date.  A holiday
closes the entire rollover-to-rollover trading session that ends on that
date — the same session grouping =Session= uses — not just that
calendar day's own clock hours, so =Status= and =Session= always agree:
every instant a returned =Session= contains reports =StatusOpen=.  No
real holiday data ships with this decision — populating an actual
holiday calendar is a data-acquisition concern, deferred along with the
rest of M2.

** Consequences

- Bar alignment can be validated against provider-native session bars.
- Session-aware calendars will be required before non-FX asset classes
  are supported end-to-end; =Calendar= is already shaped to add them
  without disturbing =FXCalendar= or its callers.
- DST transition weeks and days have wall-clock durations other than
  exactly 24h or 7×24h, and callers relying on =TimeRange.Duration= must
  account for that rather than assuming a fixed bar length.
- Multi-day and multi-week bars are not yet representable through
  =FXCalendar=; a caller needing them must wait for the resampling work
  in M2 rather than assuming =Bar= silently groups sessions.

** Alternatives Considered

- *=time.Duration= alone as an interval.* Rejected because it cannot
  represent session-aligned daily, weekly, or monthly bars correctly.
- *A single concrete =FXCalendar= type with no =Calendar= interface.*
  Rejected because the architecture document already commits to a second
  (exchange/holiday) implementation in M2, and package-boundaries.org's
  guidance against interfaces with exactly one implementation applies
  only when a second implementation is speculative, not documented and
  imminent.
- *Deriving DST behavior from a fixed UTC offset table maintained inside
  =marketdata=.* Rejected in favor of the standard library's =time.Date=
  plus =*time.Location= arithmetic, which is already correct and does not
  require Trader to track its own transition rules.
- *Grouping multi-day/multi-week bars via a simple day-count modulus
  anchored at the Unix epoch.* Rejected as an untested, arbitrary
  convention with no real consumer yet; reporting an error keeps the
  decision honest about what is actually implemented.

* ADR-013: Greenfield repository with controlled legacy transplant

** Status

Accepted

** Context

The existing Trader implementation embeds assumptions about global state,
configuration access, transport shape, and broker coupling that conflict
with the new architecture.  Refactoring it in place would allow legacy
structure to dictate the new package layout and vocabulary.

** Decision

Build the new Trader in a fresh repository.  Preserve the existing
implementation beside it as a working reference, behavior oracle, source
of test fixtures, and selective code donor.  For each new capability,
define the new package boundary and contract, write contract or behavior
tests, inspect the legacy code for proven algorithms or edge cases, and
copy only the smallest useful portion.  Adapt or rewrite the copied code
so it obeys the new dependency direction and vocabulary.  The new module
never imports the legacy repository.

** Consequences

- The new architecture is not constrained by legacy package layout,
  global state, or transport assumptions.
- Legacy fixtures and algorithms remain available where they can be
  proven correct against the new contracts.
- Trader remains one repository; nested modules or split repositories are
  considered only if dependency isolation becomes a measured problem.
- The legacy repository must be frozen and eventually archived once the
  replacement gates in the architecture document are met.

** Alternatives Considered

- *In-place refactor of the existing repository.* Rejected because legacy
  structure would define the new architecture rather than the reverse.
- *Blind rewrite with no reference to the legacy code.* Rejected because
  it discards proven algorithms and fixtures.
- *Permanent parallel development of both repositories.* Rejected because
  it doubles maintenance and blurs which implementation is authoritative.

* ADR-014: Paper trading is the safe default

** Status

Accepted

** Context

A misconfigured live session that silently defaults to real-money order
submission is unacceptable.  Trader is designed to run identical strategy
and execution code in simulated, paper, and live modes, so the default
selection is the last line of defense against unintended live orders.

** Decision

The zero or minimally configured live runtime always operates in paper
mode.  Real-money submission requires an explicit mode selection, an
allowed account identity, and an operator-visible startup
acknowledgement.  Live guards are separate from trade-risk rules; a guard
may block all submissions on the basis of system health without
depending on any particular risk configuration.

** Consequences

- New users, examples, and default configurations cannot accidentally
  submit real-money orders.
- Live-money enablement is explicit, account-scoped, and journaled.
- Operators can observe at startup which mode and account the session
  will use.
- Real-money trading is a release gate, not a milestone in its own right.

** Alternatives Considered

- *Real-money by default when broker credentials are present.* Rejected
  because credential presence is not consent to trade.
- *No default mode; require explicit selection every time.* Rejected as a
  default because it complicates simulation and paper workflows without
  additional safety benefit beyond what an explicit enablement decision
  already provides.

* ADR-016: Symbol and listing resolution

** Status

Accepted

** Context

ADR-003 established =Instrument= and =Listing= as distinct concepts but
explicitly deferred the resolver mapping provider-native symbols to them:
"A =Resolver= mapping Trader IDs to provider- or broker-native symbols ...
remain[s] a future, additive concern[] and [is] not part of this
decision."  Issue #26 (M1-08) required settling that resolver: how
provider symbols and aliases resolve to a =Listing= without ever becoming
instrument identity themselves, how ambiguity is detected rather than
silently guessed at, and how registration works without a package-level
global registry.

** Decision

=instrument.Resolver= is a small, read-only interface with two resolution
directions:

- =ResolveSymbol(provider, venue, symbol string) (Listing, error)=
- =ResolveInstrument(instrumentID ID, provider, venue string) (Listing, error)=

Both treat an empty =provider=/=venue=/=symbol= argument as "unconstrained
on this axis," and both resolve to exactly one =Listing= or fail: zero
matches after applying whatever context was supplied reports
=ErrUnknownSymbol=, and more than one reports =ErrAmbiguousSymbol=.  A
=Resolver= never guesses which =Listing= a caller means.  In particular, a
provider is not assumed to expose a given symbol on at most one venue —
=(provider, symbol)= alone is not treated as a globally unique lookup key,
so an unconstrained venue on =ResolveSymbol= is a real, tested source of
ambiguity, not a convenience default that happens to always resolve.

=instrument.MemoryResolver= is the in-memory reference implementation:
a plain value returned by =NewMemoryResolver=, with no package-level
state, so independently configured resolver instances (per environment,
per test) require no special support.  It exposes =Register= (indexes a
constructed =Listing= under its own provider/venue/symbol and its
=InstrumentID=, rejecting an exact provider/venue/symbol duplicate) and
=RegisterAlias= (adds an additional provider/venue/symbol lookup key that
resolves to an existing registration's =Listing=, resolving that canonical
reference through the same zero/one/many logic =ResolveSymbol= uses, so an
underspecified alias target is caught at registration time).  An alias is
never itself indexed as a new =Listing= and never gains its own entry in
the instrument index, and the =Listing= it resolves to is always the
canonical value, unchanged — an alias never becomes identity.
=MemoryResolver= holds a =sync.RWMutex= and is safe for concurrent use.

** Consequences

- Registration/loading strategy (in-memory, a future config-file-backed
  or persistent resolver) can vary behind the same =Resolver= interface
  that consumers (execution, broker adapters) depend on.
- Ambiguity is a first-class, tested outcome distinguishable from
  "unknown," on both resolution directions, via distinct sentinel errors.
- No global mutable registry exists anywhere in the package; every
  =MemoryResolver= is independent by construction.
- Aliases add lookup keys, never new identity: resolving through one
  returns the exact canonical =Listing= value.

** Alternatives Considered

- *=(provider, symbol)= as a globally unique lookup key, ambiguity only on
  the =Instrument= -> =Listing= direction.*  Considered and rejected during
  design review: a provider is not guaranteed to expose a symbol on only
  one venue, and baking that assumption into the public contract would
  have made =ResolveSymbol= unable to express a case =ResolveInstrument=
  already had to handle correctly.
- *A query/options struct (for example =SymbolQuery{Provider, Venue,
  Symbol}=) instead of positional string parameters.*  Rejected for M1 as
  premature: =ResolveSymbol='s three parameters and =ResolveInstrument='s
  three are still few enough to stay readable positionally; the struct is
  the natural next step only if a further resolution axis proves
  necessary.
- *A package-level global registry.*  Rejected per issue #26's explicit
  constraint and Trader's broader avoidance of hidden global state (see
  ADR-002's dependency-direction rules and the architecture document's
  determinism principles).

* ADR-021: FX hour-bar alignment corrected to daily-rollover anchoring

** Status

Accepted

Amends ADR-012 (the sub-day M1/H1/H4 UTC-clock alignment rule only; see
the Partial Amendment Rules above and ADR-012's own =Amended by= line).

** Context

ADR-012 specified that =FXCalendar='s minute and hour bars align to the
UTC clock via truncation since the Go zero time, so that H4 bars land on
00:00/04:00/.../20:00 UTC regardless of date. Issue #81's corpus-scale
validation against the real, preserved OANDA archive — comparing derived
H4 (resampled from raw H1) against OANDA's own native H4 partitions —
found this claim wrong: OANDA's real H4 candles anchor to the FX daily
rollover (17:00 New York, the same instant D1 already uses), landing on
02:00/06:00/10:00/14:00/18:00/22:00 UTC in winter (shifting with DST),
confirmed directly against a raw H4 partition file
(=AUDCAD-2006-11-h4.csv=).

This is not merely a documentation discrepancy. Issue #99 traced it to
an active operational bug: =normalizeOANDASequence= validates every
accepted/incomplete H4 record's alignment via =Calendar.Bar=, so under
ADR-012's UTC-midnight rule, every real OANDA H4 record fails that
check and is classified =recordOutcomeRejected=. =normalizeAndPublish=
aborts the entire partition build — no partial publish — on any
=Rejected= record, so =Manager.Build= for =ActionNormalizeCanonical(H4)=
failed outright against real data. D1 was unaffected (OANDA's native D1
rollover already matches =FXCalendar='s own D1 boundary exactly), and so
was W1, since it derives from D1 and never touches H4 (#81).

** Decision

=FXCalendar.Bar='s =UnitMinute=/=UnitHour= cases now anchor to the FX
daily rollover (=dayStart=, the same anchor D1 already uses) instead of
UTC midnight: the boundary is the most recent whole multiple of the
requested duration past =dayStart(t)=, computed by subtracting the
remainder of elapsed time since that anchor (the same truncation idiom
=time.Duration.Truncate= itself uses), not by truncating since Go's zero
time (=time.Time{}=, year 1 — the previous implementation's actual
reference instant, not the Unix epoch, though both happen to fall at UTC
midnight so the distinction was immaterial to the boundary set produced).

This changes H4's actual landing boundaries to match OANDA's real data.
It changes nothing for M1 or H1: =dayStart= is always a whole-hour UTC
instant (17:00 New York is either 21:00 or 22:00 UTC, depending on DST),
so a 1-minute or 1-hour grid anchored there produces exactly the same
boundary *set* as one anchored at UTC midnight — every instant is
already a 1-minute boundary either way, and every whole-hour instant is
already a 1-hour boundary either way. Only H4's 4-hour grid actually
shifts, since neither 21:00 nor 22:00 UTC is itself a multiple of 4h
from midnight. This equivalence is asserted by a dedicated test
(=TestFXCalendarBarRolloverAlignmentForHourAndMinute=), not merely
claimed.

=Manifest.CalendarVersion= (ADR-020, issue #81) bumps from
=fxcalendar-v1= to =fxcalendar-v2= to name this changed =Bar=
implementation, even though no H4 canonical data had ever successfully
published before this fix (there is no prior H4 dataset to invalidate)
and M1/H1/D1/W1 data is unaffected in substance.

A second design-review finding, surfaced after this ADR's first
revision, identified a further gap even a divisor duration like H4 does
not automatically avoid: =dayStart='s own real length is 23h or 25h on
the two annual US DST-transition days (identical to D1's own variable
=Bar= duration), so the naive anchor-plus-whole-multiples grid could
still produce a final closed-period bucket whose end lands *after* the
next real rollover — straddling from =StatusClosed= into =StatusOpen=,
which =ClassifyInterval= correctly refuses to describe as one
=IntervalState=, breaking any coverage walk that reaches it.
=rolloverAnchoredBar='s computed =end= is therefore additionally clamped
to the containing day's own real end (computed the same
=AddDate=-in-New-York-location way =dayStart= and D1's =Bar= case
already do, inheriting their DST correctness) — producing a shorter
final bucket on a spring-forward day, or an extra short final bucket on
a fall-back day, either way ending exactly at the next day's own start.
This is a no-op on every ordinary day, where the naive end already
equals the day's real end.

This narrowly corrects one sub-decision within ADR-012, which bundles
several unrelated decisions (the =Interval=/=TimeRange=/=Calendar=
types, =FXCalendar='s D1/W1 rollover alignment, DST handling). Recorded
as a *partial amendment* (this registry's own Partial Amendment Rules,
added alongside this ADR): ADR-012 keeps its =Accepted= status and its
Decision section completely unchanged — never rewritten, per this
registry's non-rewrite rule — and gains only the one small =Amended by=
line under its own Status section that the amendment process defines.
=Accepted= on ADR-012 now specifically means "in force, except the named
sub-decision, which this ADR governs instead" — the Partial Amendment
Rules make that meaning explicit rather than leaving two =Accepted= ADRs
in silent, undefined tension over the same boundary. Marking the entire
ADR-012 =Superseded= was considered and rejected — see Alternatives
Considered.

** Consequences

- Real OANDA H4 data now normalizes and publishes successfully;
  =TestNormalizeOANDASequence_H4RealBoundaryAccepted= (#99) is the
  regression proving it, alongside
  =TestNormalizeOANDASequence_H4UTCMidnightNowMisaligned= proving the
  fix actually moved the accepted grid rather than merely widening it.
- Coverage queries spanning a DST-transition weekend no longer fail with
  =ErrIntervalStraddlesBoundary=:
  =TestFXCalendarBarH4ClosedBucketEndsExactlyAtSpringForwardReopen= and
  its fall-back counterpart cover the clamp directly,
  =TestFXCalendarBarH4ClosedBucketNeverStraddlesClassification= covers
  =ClassifyInterval= specifically, and
  =TestCoverage_H4SurvivesSpringForwardWeekend= is the full
  =Manager.Coverage= regression — each confirmed to fail with the exact
  error a design review predicted when the day-end clamp is reverted,
  not just to pass with it applied.
- Re-verified against the real archive after the day-end clamp: re-running
  =TestCorpusH4AgreesWithNative= found the identical 53 disagreements
  across the same 25 partitions as before the clamp, confirming it is a
  no-op for every live data boundary and only changes closed-period
  buckets that never had real data to begin with.
- =rolloverAnchoredBar='s divisor check now runs on =count= before it is
  multiplied into a =time.Duration=, not on the resulting duration — a
  third design-review finding: =NewInterval= has no upper bound on
  count, so a pathologically large one (=NewInterval(UnitHour, 1<<51)=,
  say) would overflow =time.Duration='s int64 nanosecond range when
  multiplied, silently wrapping to an arbitrary value — confirmed to
  wrap to exactly zero for that example, which would have reached the
  divisor check as a =day % duration= divide-by-zero panic rather than
  a normal error. Comparing =count= directly against
  =minutesPerDay=/=hoursPerDay= before any multiplication is immune to
  that overflow by construction.
  =TestFXCalendarBarRejectsHugeCountsWithoutOverflowPanic= is the
  regression, confirmed (the same way as the other findings above) to
  actually panic before this fix, not merely to pass after it.
- =FXCalendar.Bar='s returned =TimeRange= for M1/H1/H4 now carries a New
  York =time.Location= (inherited from =dayStart=), matching D1/W1's
  existing convention, rather than the UTC location =utcBar= previously
  returned. The underlying instants are unchanged for M1/H1 and
  intentionally different for H4; any caller comparing returned
  boundaries must use =time.Time.Equal=, never struct/reflect equality,
  which was already the documented-correct way to compare =time.Time=
  values and is now exercised by a real regression
  (=TestCoverage_GapsMergeContiguousMissingBoundaries= was fixed to use
  it).
- Any future third-party or non-OANDA hour-bar provider must be checked
  against this same rollover-anchored rule, not assumed to share OANDA's
  own alignment convention.
- Because =dayStart= resets fresh every real trading day rather than
  extending one fixed grid indefinitely, =FXCalendar= now rejects any
  sub-day =Interval= whose duration does not evenly divide 24h (an
  arbitrary count such as H5 or M7, constructible via =NewInterval= even
  though no predefined value uses one) — a design-review finding on the
  implementing PR: such a duration can produce two buckets that overlap
  in wall-clock time across the daily reset.
  =TestFXCalendarBarRejectsSubDayIntervalsThatDontDivide24h= and
  =TestFXCalendarBarH5WouldHaveOverlappedAcrossDailyReset= cover the
  rejection and reproduce the exact overlap it prevents. M1, H1, and H4 —
  every predefined sub-day =Interval= — all evenly divide 24h and are
  unaffected.

** Alternatives Considered

- *Special-case only H4, leaving =UnitMinute=/=UnitHour= on two
  divergent code paths.* Rejected: M1/H1 are provably unaffected by
  routing through the same rollover-anchored function (see Decision), so
  a single shared implementation is both simpler and removes the risk of
  the two paths silently drifting apart later.
- *Mark all of ADR-012 =Superseded=.* Rejected: ADR-012 bundles several
  decisions that remain entirely correct and unchanged (the type
  definitions, =Calendar= interface, D1/W1 alignment, DST handling via
  =time.Date=). Superseding the whole document would misleadingly imply
  those parts were also being replaced. Recording this instead as a
  *partial amendment* — a mechanism this ADR's own review added to the
  registry's rules, since none existed for exactly this case — keeps the
  historical record accurate without overclaiming scope, and gives
  ADR-012's continued =Accepted= status a precise, defined meaning
  instead of leaving two =Accepted= ADRs in undefined tension.
- *Allow arbitrary sub-day interval counts by defining a continuous,
  never-resetting rollover-relative grid instead of rejecting
  non-divisors.* Considered, per the same review comment. Rejected for
  this fix: it is materially more design work (a grid that never resets
  needs its own answer for DST weeks, where "24h" itself is not
  constant) for a case no predefined =Interval= or current consumer
  needs; rejecting the unsafe case outright is the smaller, sufficient
  change, and a continuous grid remains available as a future,
  additive =FXCalendar= capability if a real need arises.
- *Silently patch =FXCalendar= without a new ADR.* Rejected: this
  reverses an explicit, Accepted architectural decision (ADR-012's own
  stated H4 boundary) for an interval used throughout =marketdata=; per
  =CONTRIBUTING.org=, that requires a recorded decision, not a quiet
  code change.
