#+TITLE: ADR-090: Raw to canonical bars (stage 4)
#+STARTUP: overview indent

* Status

Proposed, with the owner's answers of 2026-11-14 applied (below), for final
approval. Issue #628; stage 4 of #584. Builds on ADR-020 (historic data: raw is
immutable, canonical is rebuilt from it), ADR-088 (the instrument catalog) and
ADR-089 (layout, OANDA raw store, package boundary). No code is written before this
is approved.

The bar-availability design the owner recorded on #619 (a bar has an opening =Time=
and an =AvailableAt=; no stored close time; zero means not established) is taken as
given.

* Context

Checked read-only on the owner's machine:

- =/srv/data/canonical/oanda= holds 3,722 =canonical-v1= files (2,400 =h1=, 1,322
  =d1=; no =m1= or =h4=): a comment line, one JSON metadata line (=raw_fingerprint=,
  versions, =bar_count=, first and last bar, =revision=), the columns
  =time,open,high,low,close,avg_spread,max_spread,ticks=, then one row per bar
  present. The archived converter took open, high, low and close from the raw
  record's *bid* prices, kept only the mean and the largest of the four corner
  spreads (ask minus bid), and so dropped the ask prices. It reported rejected
  records per record (incomplete, crossed, bad shape, duplicate, out of order,
  misaligned) and dropped nothing silently in memory, but nothing in the file said
  a record had been rejected.
- The live engine reads =design-bars-v1= and derives =availableAt= as open plus a
  fixed duration. That is wrong for OANDA's session day, which opens 17:00 New York
  and lasts 23 or 25 hours across a DST change.
- The raw store (ADR-089) holds, per partition, every bid and ask open, high, low
  and close, the volume and the provider's =complete= flag.

* Decision

** 1. A new schema, canonical-v2

Canonical keeps *everything raw knows about prices* and adds the availability time
the engine needs. A new schema, not the old one: =canonical-v1= could not carry the
ask prices or an availability time, and raw is complete and local, so the existing
files are rebuilt from raw (local, no network) rather than migrated. =canonical-v1=
files are not read by the new code.

#+begin_src go
type OHLC struct {
    Open, High, Low, Close num.Price
}

type Bar struct {
    Time        time.Time // the bar's opening instant, UTC
    AvailableAt time.Time // earliest time the completed bar may be consumed

    Bid OHLC
    Ask OHLC

    Volume int64 // the provider's activity count, not a tradable quantity
}

func (b Bar) Mid() OHLC // exact midpoint of Bid and Ask, field by field
#+end_src

File: a comment line =# schema=canonical-v2 provider=oanda symbol=EURUSD
interval=h1 year=2024 month=01=, one JSON metadata line, any bad-record lines (3
below), the columns

#+begin_example
time,available_at,bid_o,bid_h,bid_l,bid_c,ask_o,ask_h,ask_l,ask_c,volume
#+end_example

and one row per good bar, in ascending time. Prices are exact text with the raw
store's five decimals, never through a float. Times are UTC, RFC 3339.

*Mid is a method, not a column.* =Mid()= returns, for each of open, high, low and
close, the exact midpoint of the bid and ask values (half a pip is representable,
so nothing is rounded). Open and close are preserved on both sides, so mid is
always recomputable from what is stored. Note that a candle's mid high is the
midpoint of the bid high and the ask high, which need not equal the high of a
tick-by-tick mid series; it is the midpoint of the candle values the provider
gives, and the method's comment says so. The spreads of the old format are
derivable (=Ask.x - Bid.x=) and are not stored.

** 2. Availability is stored, modeled, and versioned

=available_at= is written at build time as the bar's scheduled end: the next
interval boundary after the opening time. For =h1= that is the next hour; for =d1=
the next 17:00 America/New_York, so a DST day is 23 or 25 hours. This is a
*modeled* availability under a named policy (=scheduled-close-v1=), never presented
as an observed provider timestamp; the metadata records the policy name. A stored
bar always has a nonzero =available_at= not before =Time=. The raw =complete= flag
stays in raw as the provider's own fact. A change to the policy means a new
policy name and a rebuild, which is cheap because canonical is derived (ADR-020),
and the files built under the old policy say so.

** 3. Bad records are written into the file, never silently lost

The build writes every good row and *also records every record it rejected*, in the
same file, as comment lines before the column header:

#+begin_example
# bad time=2024-01-05T14:00:00Z reason=crossed raw_row=1203
# bad time=2024-01-05T15:00:00Z reason=incomplete raw_row=1204
#+end_example

=reason= is one of =incomplete= (the provider had not closed the candle),
=crossed= (an ask below its bid at some corner), =invalid= (a high or low not
containing open and close, or a non-positive price), =duplicate=, =out-of-order= and
=misaligned= (not on the interval's boundary). =raw_row= is the row's position in
the raw file, so the record can be examined there. The metadata line carries
=bar_count= and =bad_count=. The canonical reader returns the good bars *and* the
bad records, so a later stage (gaps, coverage) can tell "known bad" from "missing"
from "closed market" and a bad month is never mistaken for a quiet one.

A raw row that cannot even be parsed (the raw reader's =ErrMalformedData=) is not a
bad record: the raw file itself is damaged, so that partition's build fails and
writes nothing. A candle the downloader declined to store because it was still
forming never reaches raw, so canonical sees it only as an absent bar; the gaps
stage reports that. Records with the same time keep the first as the good row and
record the later ones as =duplicate=.

Alignment: =h1= on the hour; =d1= at 17:00 America/New_York, using the embedded
time zone database. One small function, tested at the DST and month boundaries; no
=Calendar= interface. A weekend or holiday gap is not an error and nothing is
filled.

** 4. Rebuilds and fingerprints

The metadata records =raw_fingerprint= (the raw partition's bytes), the builder
version and the availability policy. Canonical is derived, so unlike raw it may be
replaced: a build whose three values match the file on disk does nothing;
otherwise the file is rewritten atomically (temporary file, sync, rename) under the
per-partition lock, and the report says it was replaced. A build never touches raw.

** 5. Packages and the command

- =internal/marketdata/canonical=: =OHLC=, =Bar=, =Mid=, the =canonical-v2= reader
  and writer, the bad-record type, validation and the alignment and availability
  rule. It imports =num=, =layout= and the standard library; never a provider.
- =internal/marketdata/oanda=: the mapping from a raw record to a canonical bar or
  a bad record. It imports =canonical=.
- =cmd/trader=: =trader data build=, flags as =download= (=--data-root=,
  =--instrument=, =--interval=, =--from=, =--to=; the same root precedence and
  config file). It needs no token and makes no network call. It prints, per
  partition, built, unchanged, replaced or failed, with the good and bad counts.
- Scope: =h1= and =d1=. =m1= and =h4= wait until a strategy needs them.
- No Manager, plan, registry or service layer.

** 6. Tests and the owner's check

Hermetic: raw fixtures are small files copied from the archive; tests never read
=/srv/data=. Cases: each rejection rule written as a bad line and read back; a file
with good and bad rows; a damaged raw row failing the build; a DST =d1= week and the
New York changes; a month boundary; =Mid()= exact on half-pip values; an unchanged
rebuild; a changed fingerprint; cancellation. A cross-check against the archive:
building a month from its raw fixture must give bid prices and volume equal to the
v1 file's open to close and ticks, and spreads (=Ask - Bid=) whose mean and maximum
equal the v1 file's =avg_spread= and =max_spread=. The owner's check: download a
short range with =trader data download= into a temporary root, run =trader data
build= over it, and read the output.

* Deferred

Gap and coverage policy (stage 5); disk layout checks; the partition cache; loading
canonical bars into the engine's =bar= and frames (a later stage, with the bar
model); =m1=, =h4=, =W1=; other providers; the one-time migration of =raw/oanda= to
=oanda/raw=, after which the existing raw archive is converted by this builder.

* Consequences

- Nothing about prices is lost between raw and canonical, and mid is a method, so
  the basis can be chosen by the consumer.
- The existing =canonical-v1= archive is not reused; it is rebuilt from raw once raw
  is migrated. Raw is complete, so nothing is lost, but the rebuild is a step the
  migration must schedule.
- A bad or incomplete record is visible in the file it affects and in the reader's
  result, not only in a build log.
- Files are larger than v1 (eight prices instead of four plus two spreads).
- Availability policy changes need a rebuild, not a code-only change.

* Owner decisions (2026-11-14)

- New schema with an =available_at= column.
- Write the good rows and record the bad rows in the same file, so bad or incomplete
  records never silently lose that distinction.
- =h1= and =d1= only for now.
- Mid basis, with open and close preserved: the canonical bar keeps bid and ask
  open, high, low and close and the volume, and mid is a method.
