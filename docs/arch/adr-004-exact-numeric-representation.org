#+title: ADR-004 Exact Numeric Representation
#+startup: overview

* Status

Proposed

Parent decision: [[https://github.com/rustyeddy/trader/issues/19][#19 — M1-01 Decide exact numeric representation]]

This working ADR records decisions as the numeric-design sub-issues
are resolved.  It remains =Proposed= until [[https://github.com/rustyeddy/trader/issues/44][#44]] consolidates the
evidence, completes the alternatives and consequences, and marks the
decision =Accepted=.

* Context

Trader must represent authoritative prices, money, quantities, rates,
balances, fees, margin, order values, fill values, and PnL without
relying on binary floating-point approximation.  These values must
round-trip through broker, configuration, storage, journal, and
reporting boundaries while preserving clear domain semantics.

Trader is intended to support more than FX.  The representation must
be validated against equities, ETFs, futures, high-priced assets,
large FX positions, fractional quantities, and small fees or financing
values.

The legacy Trader repository already contains scaled-integer =Price=,
=Money=, =Rate=, accumulators, and fixed-point indicator
implementations.  Under ADR-013, that repository is a selective code
donor and behavior reference, not a dependency of the new Trader.

* Decisions Reached

** Authoritative backing representation

Decision source: [[https://github.com/rustyeddy/trader/issues/19][#19]]

The authoritative foundational numeric types use scaled signed =int64= values.

The initial semantic types are:

- =Price=
- =Money=
- =Quantity=
- =Rate=

=Currency= remains a separate domain concept used with =Money=; the precise
ownership relationship is still open in [[https://github.com/rustyeddy/trader/issues/35][#35]].

The public API must not expose one generic decimal type in place of these
semantic types.  Distinct types prevent accidental substitution of price,
quantity, money, and rate values.

** Price representation versus instrument rules

Decision source: [[https://github.com/rustyeddy/trader/issues/33][#33]]

=Price= will use a fixed internal representation scale.  Instrument-specific
market rules remain separate:

- tick size
- permitted price increment
- display precision
- provider quotation format

The internal representation scale is not itself the instrument tick size.

*** Selected scale: 1e8 (8 decimal places)

The internal =Price= scale is *1e8*: a decimal value =v= is stored as the
=int64= =v * 100_000_000=.

The validation evidence is in =test/internal/numericstudy=, a test-only spike that
parses and formats decimal text directly to and from scaled =int64= without
passing through =float64=.

**** Why 1e8 over 1e9

Intermediate arithmetic decides it.  Margin to the =int64= ceiling for
=Price x Quantity=, using whole unscaled quantities so only one operand
carries a scale and no descaling divide is required:

# BEGIN numericstudy:notional-8v9
| Case            |          Quantity |        1e8 |      1e9 |
|-----------------+-------------------+------------+----------|
| BRK.A block     |            10,000 |        12x |       1x |
| FX 10M notional |        10,000,000 |     8,502x |     850x |
| FX 1B notional  |     1,000,000,000 |        85x |       8x |
| BTC 1k coins    |             1,000 |       614x |      61x |
| SHIB 1e12 units | 1,000,000,000,000 | 9,223,372x | 922,337x |
# END numericstudy:notional-8v9

1e9 leaves the largest realistic notional essentially at the ceiling — a
BRK.A-sized block consumes the entire =int64= range with 1x to spare.  1e8
buys back an order of magnitude at the cost of one decimal place that no
intended asset class needs.  8 decimals is also the natural stopping point:
it is exactly satoshi precision, the widest decimal requirement Trader accepts.

These margins hold only for whole unscaled quantities.  If [[https://github.com/rustyeddy/trader/issues/36][#36]] gives
=Quantity= its own scale, =Price x Quantity= becomes double-scaled exactly
like =Price x Rate=, the margins above no longer apply, and the operation
requires a widened intermediate regardless of price scale.  That would not
change the 1e8 selection — it still beats 1e9 by 10x — but it would move
=Price x Quantity= from "safe in =int64=" to "must use the widened path".

**** Consequences for intermediate arithmetic

Two findings belong to [[https://github.com/rustyeddy/trader/issues/38][#38]] and are recorded here as evidence:

1. *Double-scaled products overflow at every usable scale.*  =Price x Rate=
   scales both operands, so the product carries the scale twice before the
   descaling divide.  At 1e8, realistic pairs such as BRK.A x a financing rate,
   or BTC/USD x a JPY conversion rate, overflow =int64=.  1e9 is worse.  This
   is not fixable by choosing a different scale — it requires a widened
   (128-bit) intermediate, demonstrated in =TestPriceTimesRateWidened=.

2. *Naive accumulation overflows inside a single backtest.*  A plain =int64=
   sum of 750000.00 bars overflows after ~122,978 bars at 1e8 — under three
   months of M1 data.  Rolling sums and averages need a widened accumulator or
   a running-mean formulation, not a raw =int64= total.

# BEGIN numericstudy:rolling-sum
| Scale | Bars of 750000.00 before overflow |
|-------+-----------------------------------|
| 1e5   |                       122,978,293 |
| 1e6   |                        12,297,829 |
| 1e8   |                           122,978 |
| 1e9   |                            12,297 |
# END numericstudy:rolling-sum

**** Tick size stays separate from scale

Instrument tick size is parsed into the same internal scale but remains an
instrument property.  With both in one scale, increment validation is exact
integer modulo (=price % tick == 0=) with no per-scale special cases; this is
asserted in =TestPriceIsMultipleOfTick=.  Display precision is likewise
independent: a value stored at 1e8 renders at whatever precision the
instrument declares.

**** Unsupported quotation formats

These are provider quotation *conventions*, not decimal numbers.  Each must be
normalized to plain decimal text in a provider adapter before reaching =Price=;
the parser rejects all of them.

# BEGIN numericstudy:unsupported
| Format                              | Example      | Normalizes to | Reason                                                    |
|-------------------------------------+--------------+---------------+-----------------------------------------------------------|
| Treasury 32nds (dash)               | =110-16=     |         110.5 | not decimal text; '-' is a fraction separator, not a sign |
| Treasury 32nds plus halves/quarters | =110-16.5=   |    110.515625 | fraction of a 32nd; expands to 64ths, needing 6 decimals  |
| Grain fractions in eighths          | =575'6=      |        575.75 | apostrophe-delimited eighths of a cent                    |
| Scientific notation                 | =1.5e-7=     |    0.00000015 | exponent form is rejected; expand before parsing          |
| Grouped thousands                   | =750,000.00= |     750000.00 | locale grouping is a display concern, not an exact input  |
# END numericstudy:unsupported

All of these are representable once normalized, so no intended instrument is
excluded by the 1e8 choice — the constraint is on the adapter layer, not the
representation.

***** Normalization is necessary but not sufficient

Converting a quotation to plain decimal text does not guarantee the result
satisfies the precision policy.  Values finer than the 1e8 quantum are
syntactically valid but not representable, and are rejected rather than
silently rounded:

# BEGIN numericstudy:subquantum
| Value         | Digits | Note                                         |
|---------------+--------+----------------------------------------------|
| =0.000000015= |      9 | 1.5e-8 expanded; half of the 1e8 quantum     |
| =0.000000001= |      9 | one 1e9 unit; below the 1e8 quantum entirely |
| =1.000000005= |      9 | ordinary price carrying one digit too many   |
# END numericstudy:subquantum

Each is accepted at 1e9, confirming the failure is the precision policy rather
than a parser defect (=TestSubQuantumValuesRejected=).  Whether adapters reject
sub-quantum values or round them explicitly is decided by [[https://github.com/rustyeddy/trader/issues/38][#38]] and [[https://github.com/rustyeddy/trader/issues/39][#39]].

***** Known parser gap: most negative value

=FormatDecimal= renders =math.MinInt64=, but =ParseDecimal= cannot construct
it: parsing builds the magnitude before negating, and that magnitude exceeds
=MaxInt64=, so the guard fires one unit before the true negative bound.  The
gap is exactly one representable value wide
(=TestParseCannotConstructMinInt64=).

[[https://github.com/rustyeddy/trader/issues/39][#39]] must make the negative-range policy explicit: either parsing accepts the
full =int64= range, or the domain range is deliberately symmetric and the most
negative value is not a valid =Price=.

*** Review disposition for #33

Final review of [[https://github.com/rustyeddy/trader/pull/45][PR #45]] confirmed that the executable evidence supports a fixed =Price=
scale of =1e8=.  The original review concerns were addressed, CI passed, and
[[https://github.com/rustyeddy/trader/issues/33][#33]] is complete for purposes of ADR-004.

Three non-blocking cleanup items were raised against the study harness.  They
must not be mistaken for changes to the selected scale, and all three were
corrected in [[https://github.com/rustyeddy/trader/pull/46][PR #46]]:

- Documentation claimed the study used no =float64= at all, while a
  reporting-only margin comparison did.  That comparison is now integer
  arithmetic, and =TestNoFloatingPoint= fails on any float identifier or
  literal anywhere in the package.  The guarantee that matters — exact parsing
  and formatting never passing through binary floating point — held throughout.
- =FormatFixed= could emit negative zero after truncation.  The sign is now
  suppressed when the rendered magnitude is zero.
- The =Scale= documentation described storage as rounding.  It now states that
  a value is accepted only if it scales to an integer exactly, and excess
  precision is rejected.

These items never weakened the =1e8= decision, and the study helpers are safe
to read as implementation references on these three points.  The production
rounding and overflow policy remains [[https://github.com/rustyeddy/trader/issues/38][#38]]'s decision, and the exact parsing
boundary, including the =math.MinInt64= range gap, remains [[https://github.com/rustyeddy/trader/issues/39][#39]]'s.

Related decisions this issue deliberately did not settle: scaled =Quantity=
multiplication semantics remain with [[https://github.com/rustyeddy/trader/issues/36][#36]]; widened intermediates, accumulation,
and rounding remain with [[https://github.com/rustyeddy/trader/issues/38][#38]]; exact parsing boundaries remain with [[https://github.com/rustyeddy/trader/issues/39][#39]].

** Quantity representation and asset constraints

Decision source: [[https://github.com/rustyeddy/trader/issues/36][#36]]

=Quantity= uses a single fixed Trader-wide scale of *1e8*, backed by signed
=int64= — the same scale as =Price=.  A decimal quantity =v= is stored as the
=int64= =v * 100_000_000=.

- smallest representable quantity: =0.00000001= (one satoshi)
- maximum whole-unit quantity: =92,233,720,368= (~92.2 billion)
- quantities above that bound are rejected as out of range, never truncated
- positions in extremely high-supply tokens above the bound are outside the
  initial supported domain

The evidence is in =test/internal/quantitystudy=, a test-only spike that reuses
=test/internal/numericstudy= for exact decimal parsing, table rendering, and
the generated-documentation guard.  Regenerate the tables with:

#+end_src

*** The precision and range frontier

No scaled =int64= holds both extremes of the pressure matrix.  One satoshi
needs 8 fraction digits; a trillion whole units at 8 fraction digits needs
1e20, which is 67 bits against =int64='s 63.

# BEGIN quantitystudy:frontier
| Scale | Smallest unit |   Max whole units | Holds 1 satoshi | Holds 1e12 units |
|-------+---------------+-------------------+-----------------+------------------|
| 1e6   |      0.000001 | 9,223,372,036,854 | no              | yes              |
| 1e7   |     0.0000001 |   922,337,203,685 | no              | no               |
| 1e8   |    0.00000001 |    92,233,720,368 | yes             | no               |
| 1e9   |   0.000000001 |     9,223,372,036 | yes             | no               |
# END quantitystudy:frontier

Only 1e6 holds a trillion units, and it cannot represent a satoshi.  Only 1e8
and 1e9 represent a satoshi, and neither reaches a trillion units.  Trading
range for precision is not a free move — it swaps which asset class is
excluded.

The trillion-unit row is a deliberate range-pressure case, not a requirement.
It is retained in the evidence to mark the boundary rather than removed or
quietly made to pass, and =TestOutOfDomainQuantityIsRejected= asserts it fails
with a range error specifically, so the boundary is visible in behaviour.

*** Why 1e8

Both 1e8 and 1e9 cover every intended asset class exactly.  1e9 spends a ninth
decimal place that nothing in the matrix needs and pays a factor of ten in
supported range for it.  1e8 also matches the =Price= scale fixed by [[https://github.com/rustyeddy/trader/issues/33][#33]],
keeping both scales in one mental model.

Explicitly rejected: per-asset-class quantity scales, and a widened =Quantity=
backing type, adopted solely for the pressure case.  Either would add
substantial complexity to all quantity arithmetic, serialization, and public
APIs for a requirement Trader does not currently have.

If a future concrete broker or supported instrument requires positions above
the bound, this decision reopens with actual provider constraints and usage
evidence.  The likely options then are a widened backing representation or a
specialised asset-unit model — not silent scale variation inside =Quantity=.

*** Representation scale versus instrument rules

The scale says what can be stored; instrument rules say what may be traded.
The study models them separately:

#+begin_src go
type QuantityRules struct {
    Increment    int64 // smallest tradable step
    Minimum      int64 // smallest permitted order size
    Maximum      int64 // largest permitted order size
    IntegralOnly bool  // whole units only, e.g. futures contracts
}
#+end_src

# BEGIN quantitystudy:instrument-rules
| Symbol  |  Increment |  Minimum |   Maximum | Integral only |
|---------+------------+----------+-----------+---------------|
| EUR/USD |          1 |        1 | 100000000 | no            |
| SPY     |   0.000001 | 0.000001 |         — | no            |
| ES      |          1 |        1 |     10000 | yes           |
| BTC     | 0.00000001 |   0.0001 |         — | no            |
| SHIB    |          1 |     1000 |         — | no            |
# END quantitystudy:instrument-rules

Holding quantity and increment in the same scale makes increment validation
exact integer modulo, with no tolerance and no rounding.  Integral-only
instruments are validated the same way against the scale factor.

*** Zero and sign policy

Zero is representable and is a valid =Quantity=: a flat position, a fully
closed lot.  Only order construction rejects it, so instrument conformance and
order validity remain separate questions.

Public order quantities are non-negative.  Direction is never encoded in the
quantity sign; side belongs to the order.  A negative quantity is a programming
error, and the most negative =int64= is rejected as a quantity rather than
mishandled.

*** Consequence for intermediate arithmetic

With =Price= at 1e8 and =Quantity= also scaled, =Price x Quantity= is
double-scaled — the same shape as =Price x Rate= — so the intermediate
overflows =int64= before the descaling divide.

| Case            |           Price |      Quantity |      1e6 |      1e7 |      1e8 |      1e9 |
|-----------------+-----------------+---------------+----------+----------+----------+----------|
| BRK.A block     |       750000.00 |         10000 | OVERFLOW | OVERFLOW | OVERFLOW | OVERFLOW |
| FX 10M notional |         1.08473 |      10000000 | OVERFLOW | OVERFLOW | OVERFLOW | OVERFLOW |

This confirms the caveat recorded above from [[https://github.com/rustyeddy/trader/issues/33][#33]]: scaling =Quantity= is what

path owned by [[https://github.com/rustyeddy/trader/issues/38][#38]].  The same block that is comfortable with a whole unscaled
quantity overflows with a scaled one.

** Exact input and output boundaries

Decision source: [[https://github.com/rustyeddy/trader/issues/39][#39]]

Decimal text and raw scaled integers are the preferred exact construction and
serialization boundaries.  Parsing and formatting should avoid conversion
through binary =float64= whenever practical.

Any =float64= constructor retained for adapter interoperability must be
explicitly named as a rounded or lossy boundary conversion.  It must not be the
preferred path for configuration, broker decimal strings, persistence, or
journal records.

** Indicator arithmetic is not yet globally fixed

Decision source: [[https://github.com/rustyeddy/trader/issues/41][#41]]

The authoritative domain types remain scaled integers regardless of how an
indicator performs internal analytical arithmetic.

The fixed-point versus =float64= choice will be made per indicator
implementation, not per invocation.  Public callers should pass and receive
semantic Trader types where appropriate; callers should not manually perform
representation conversions at every indicator call site.

Alternative fixed-point and floating-point implementations may coexist
internally while evidence is gathered.  Numeric representation should not be
used as the permanent public package boundary unless a later decision finds a
compelling reason.

** Exact parsing and formatting policy

Decision source: [[https://github.com/rustyeddy/trader/issues/39][#39]]

Trader's internal fixed scale is an implementation detail. It is not part of
the ordinary external API contract.

External callers work with semantic values such as =Price=, =Money=,
=Quantity=, and =Rate=. They should not normally construct or exchange raw
scaled integers.

*** Exact decimal input

Decimal text is the preferred exact boundary representation wherever the
transport or provider supports it.

Decimal text is parsed directly into the semantic type's scaled =int64=
representation. Parsing must not use =float64= as an intermediate.

Examples of exact input boundaries include:

- broker APIs that provide decimal strings;
- configuration files;
- command-line input;
- journals;
- CSV fields;
- tests and fixtures;
- external JSON contracts controlled by Trader.

Exact parsers return errors for:

- malformed input;
- excess precision beyond eight decimal places;
- values outside the supported range;
- values that violate the semantic type's construction invariants.

Exact parsing never silently rounds.

*** Raw scaled construction

Construction from raw scaled =int64= values is reserved for:

- trusted internal code;
- persistence reconstruction;
- narrowly scoped low-level packages;
- tests that explicitly exercise representation boundaries.

Such APIs must clearly identify the value as already scaled. Raw scaled
construction is not the normal external integration API.

*** Floating-point boundaries

Some external providers or libraries may require or return binary
floating-point values.

When a =float64= boundary is unavoidable:

- conversion is isolated to the relevant provider or transport adapter;
- the conversion uses an explicit rounding policy;
- NaN is rejected;
- positive and negative infinity are rejected;
- out-of-range values are rejected;
- the conversion is visibly named as rounded or lossy;
- the resulting semantic Trader value is validated before entering the domain.

=float64= must not be used as an unnecessary intermediate when decimal text is
already available.

Conceptually:

#+begin_example
external decimal text
    -> direct exact parse
    -> Trader semantic value
#+end_example

For a provider that requires floating point:

#+begin_example
external float
    -> explicit checked and rounded adapter conversion
    -> Trader semantic value
#+end_example

*** Canonical formatting

Canonical formatting emits normalized plain decimal text directly from the
scaled integer representation.

Canonical output:

- does not use scientific notation;
- does not use thousands separators;
- does not contain unnecessary trailing zeros;
- does not end with a decimal point;
- normalizes negative zero to =0=;
- does not convert through =float64=;
- round-trips to the identical scaled value.

Examples:

#+begin_example
123.45000000 -> 123.45
1.00000000   -> 1
0.00000001   -> 0.00000001
0            -> 0
#+end_example

Fixed-precision, instrument-specific, or user-facing formatting is a separate
presentation operation. It may apply an explicit rounding policy and must not
change the stored authoritative value.

*** Signed range boundary

Exact parsing for signed types must support the full signed =int64=
representation range, including =math.MinInt64=.

The parser must not create an artificial one-value gap by first constructing a
positive magnitude that cannot fit before applying the negative sign.

=Price= and =Quantity= may still reject negative values according to their
domain invariants. =Money= and =Rate= support signed values.

*** Required implementation tests

The eventual parsing and formatting implementation must test:

- zero, positive, and negative values;
- values using all eight decimal places;
- accepted trailing zeros;
- canonical removal of unnecessary trailing zeros;
- malformed input rejection;
- excess-precision rejection;
- out-of-range rejection;
- exact parsing of the full negative boundary for signed types;
- canonical format-and-parse round trips;
- negative-zero normalization;
- rejection of NaN and infinities at floating-point adapter boundaries;
- absence of =float64= conversion in exact decimal parsing and formatting.

** Price Serialization Policy
Trader-controlled public wire formats serialize Price, Quantity, and
Rate as canonical decimal strings. Money is serialized as a structured
value containing a canonical decimal amount and explicit currency. CSV
and configuration use decimal text, with currency in a separate
field. Authoritative internal databases store scaled signed BIGINT
values, with the common 1e8 scale defined by the schema and migration
version; Money stores currency separately and mandatorily. Public
events and external APIs do not expose raw scaled
integers. Provider-required floating-point formats are isolated to
provider adapters. Public schemas are versioned, writers emit
canonical values, readers may accept equivalent exact decimal forms,
and incompatible representation changes require a schema-version
change.

** Is float64 permissable in indicators
Authoritative Trader calculations use exact semantic numeric
types. Binary floating-point values are prohibited from domain,
brokerage, accounting, risk, order, position, portfolio, persistence,
and public API packages. float64 may be used only inside explicitly
approved internal analytical implementations where fixed-point
arithmetic would be impractical or provide no meaningful decision
benefit. Such implementations accept semantic Trader inputs and return
semantic Trader outputs, applying checked quantization at their
boundary. Floating-point values may not be stored in domain objects,
serialized as authoritative values, or passed into execution and
accounting paths. Approved floating-point boundaries are enforced
through package structure and automated architecture checks.

Rate is the foundational exact dimensionless representation. Domain
APIs may introduce semantic wrappers when direction, bounds, or
interpretation would otherwise be ambiguous.  For every type, the
final matrix must specify:

- representation scale
- signedness and zero-value policy
- supported range
- valid and intentionally absent operations
- rounding rules
- overflow behavior
- parsing and formatting
- JSON, text, CSV, configuration, and persistence representation

** Operation boundaries

Valid foundational operations include:

- same-type comparison;
- checked addition and subtraction where semantic units are compatible;
- =Price * Rate -> Price=;
- =Money * Rate -> Money=;
- =Quantity * Rate -> Quantity=;
- division of compatible like values to produce =Rate=;
- =Price * Quantity= only with instrument and currency context.

Intentionally absent operations include:

- implicit arithmetic between unlike semantic types;
- addition or comparison of unlike currencies;
- implicit currency conversion;
- negative public order quantities;
- using quantity sign to encode buy or sell;
- implicit tick-size or quantity-increment rounding.

** Arithmetic, rounding, and overflow policy

Decision source: [[https://github.com/rustyeddy/trader/issues/38][#38]]

All arithmetic on authoritative Trader numeric values is checked.

*** Default rounding

The default rounding mode for arithmetic results that cannot be represented
exactly at the common =1e8= scale is:

#+begin_example
round to nearest, ties to even
#+end_example

Operations that require another rounding policy must select and document that
policy explicitly.

Supported policy names are expected to include:

* round to nearest, ties to even;
* round toward zero;
* round down, toward negative infinity;
* round up, toward positive infinity.

The exact Go API and exported identifiers are implementation details.

Public arithmetic must not rely on implicit integer division or truncation as
an undocumented rounding policy.

*** Overflow and failure behavior

Public arithmetic operations must detect and report:

* overflow;
* underflow;
* division by zero;
* results outside the representable domain;
* results that cannot be represented under the selected rounding policy.

Arithmetic must never silently:

* wrap;
* saturate;
* clamp;
* discard overflow;
* or convert through =float64= to avoid fixed-point range constraints.

Normal public operations return explicit errors.

=Must...= APIs may panic only when used with programmer-controlled constants,
fixtures, tests, or equivalent trusted inputs. They are not appropriate for
broker, configuration, persistence, user, or market-data input.

*** Addition, subtraction, negation, and absolute value

Addition and subtraction use checked =int64= arithmetic.

Negation and absolute value must explicitly reject the =math.MinInt64= boundary,
because its positive counterpart cannot be represented by a signed =int64=.

Failures are reported rather than wrapped or saturated.

*** Scaled multiplication and division

Multiplication and division involving two scaled operands use a widened signed
intermediate before restoring the common =1e8= scale.

This includes operations such as:

* =Price * Quantity=;
* =Price * Rate=;
* =Money * Rate=;
* =Quantity * Rate=;
* =Rate * Rate=;
* and corresponding scaled division operations.

Conceptually:

#+begin_example
result = round((a * b) / scale)
#+end_example

The intermediate product must be evaluated in a representation wider than
=int64=. The production implementation may use =math/bits= or an internal
signed-128 abstraction, but that mechanism is not part of the public numeric
API.

Binary =float64= is not an acceptable overflow escape path.

Arithmetic may be reordered only when the reordered operation is:

* mathematically equivalent;
* exact under the documented rounding policy;
* and proven not to introduce overflow or precision loss.

*** Accumulation

Finite domain totals use checked addition.

Potentially long-running analytical accumulations use either:

* a widened accumulator; or
* a bounded, mathematically equivalent algorithm such as a running mean.

Potentially unbounded series must not use unchecked:

#+begin_src go
sum += value
#+end_src

Overflow must be detected and reported at the operation where it occurs.

*** Required implementation tests

The eventual arithmetic implementation must test at least:

* addition above =math.MaxInt64= fails;
* subtraction below =math.MinInt64= fails;
* negating =math.MinInt64= fails;
* taking the absolute value of =math.MinInt64= fails;
* valid boundary-adjacent operations succeed;
* realistic =Price * Quantity= calculations succeed using the widened path;
* realistic =Price * Rate= calculations succeed using the widened path;
* values below, above, and exactly at a rounding midpoint follow the selected
  rounding mode;
* negative midpoint cases follow the same documented policy;
* division by zero fails;
* long accumulation uses the selected widened or bounded strategy, or fails
  explicitly;
* no arithmetic operation silently wraps.

The arithmetic helpers and their final Go API are implementation work. This
ADR defines their required observable behavior.

* Consequences Identified So Far

- Authoritative financial values do not depend on binary floating-point
  representation.
- Public APIs distinguish price, money, quantity, and rate at compile time.
- Instrument tick size and quantity increment must be validated separately
  from internal numeric scale.
- Multiplication and division require explicit scale restoration, rounding,
  and overflow handling.
- Indicator implementations may choose different internal arithmetic while
  retaining semantic public contracts.
- Legacy fixed-point code and tests can be reused only after multi-asset and
  package-boundary review.

* Alternatives Under Consideration

** Arbitrary-precision or third-party decimal throughout

Not selected as the current direction.  It may simplify some decimal
operations but risks exposing a third-party representation in public APIs and
may add allocation and performance costs.  #43 must record whether any legacy
or third-party helpers are still useful internally.

** Raw float64 throughout

Rejected for authoritative values because it cannot provide exact decimal
broker and accounting semantics.

** One generic decimal domain type

Rejected as the primary public API because it permits accidental interchange
of price, money, quantity, and rate values.

** Fixed-point arithmetic for every indicator

Not yet accepted or rejected.  #41 will determine when fixed-point behavior
provides enough determinism or decision-boundary value to justify its added
complexity.
