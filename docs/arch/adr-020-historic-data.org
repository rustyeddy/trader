* TODO Where does FX holiday data come from?
Refer to trader-first-try for fx-holidays and closed datys.  Need to
retrieve it from source and decide how it is represented here.

Candidate source, located but not yet adopted:
=trader-first-try/market/forex_hours.go=, functions
=isForexMarketClosed= and =isMajorForexHolidayClosed=.  It works in
=America/New_York=, which lines up with ADR-012's 17:00 NY rollover.
The rules are:

- Jan 1, Dec 25, Dec 26 -- closed all day
- Dec 24, Dec 31 -- closed from 13:00 onward
- Sunday evening session stays closed when Sunday itself, or the
  following Monday, is one of the three full-day holidays

Note it is hardcoded rules, not a data file, and it covers only those
five dates -- no Good Friday, and no handling of holidays that shift
when they fall on a weekend.  Decide whether to carry that set forward
as-is or source a real calendar.

** TODO Volume's Go type belongs to the Bar structure work
Deferred to the =marketdata.Bar= decision (issue #72), which is the
right home for it.  Two things for #72 to avoid getting wrong:

- Do not use =num.Quantity=.  It carries exact, 1e8-scaled, tradable
  quantity semantics, and ADR-004 defines no count type.  A tick count
  wants a plain =int64=.
- Pick one name and use it in both trees.  Raw calls the column
  =volume=; the old canonical format calls the same value =ticks=.

** TODO State that raw is authoritative
It is strongly implied by "raw saved separately, pristine" plus
"canonical is rebuilt and reversioned", but never actually written
down.  The entire rebuild story rests on it, so it deserves a
sentence of its own.

** TODO Do not delete the existing candle-v2 tree until it has been diffed
Once the new canonical build exists, diff it against the old
=candle-v2= tree before deleting anything.  Bid OHLC only, tolerance
about one unit at 1e5 scale -- legacy built values through
=types.PriceFromFloat=, so last-digit differences are expected and
byte-for-byte parity is neither achievable nor the goal.

The point is catching gross errors: off-by-one slot indices, DST
drift, wrong instrument mapping, missing months.  It is a 21-year
regression test and it is only available once.  This does not conflict
with the no-retention policy above -- that policy governs superseded
/new-format/ versions, not the one-time legacy comparison.

** TODO Provider-declared incompleteness is separate from gaps
Raw carries OANDA's own =complete= column, and legacy silently skipped
rows where it was false (=datamanager/data_validation.go=).  That is a
different thing from a calendar-derived gap: one is the provider
saying "this bar had not closed yet", the other is Trader inferring
"data should exist here and does not".  Fold the distinction into "How
will gaps and closed market days be handled" so it does not get lost.

** TODO Say that third-party data sources are deferred
"Everything behind DM lives in =internal/=" plus "no other package may
retrieve, build or store data" means an outside user cannot supply a
data source.  The architecture document promises exactly that seam via
=marketdata.HistoricalSource= and =LiveFeed=.  For M2, OandA-only,
deferring it is the right answer -- it just needs to be stated, since
the promise exists elsewhere.

** TODO Resolve W1 alignment before implementation starts
Still correctly open under "Day and week alignment", but it is a short
check against the OandA API rather than a design question: does
=weeklyAlignment= accept Sunday?  ADR-012 defines the FX week as
opening Sunday 17:00 New York, and =weeklyAlignment= is believed to
default to Friday.  The answer decides whether W1 is provider-native
like the other four intervals or the single derived one, which shapes
the interval materialization work.

Related, and already verified: the existing D1 corpus opens at 21:00Z
in July and 22:00Z in January -- both 17:00 America/New_York.  That
matches ADR-012.  But the legacy client sends no alignment parameters
at all, so that boundary came from OandA's request defaults
(=dailyAlignment=17=, =alignmentTimezone=America/New_York=).  The new
downloader should pin them explicitly rather than inherit them.
