** DONE We may keep a manifest
Settled by issue #73 (branch =feature/73-manifest=): =marketdata.Manifest=
is the collection-level identity, provenance, and revision record for a
canonical =BarSet=.  =Bar=/=BarSet= (#72) hold observation-local facts;
=Manifest= holds why the dataset is trustworthy and what produced it,
independently of any filesystem path.

Fields: =Provider= (opaque logical provider name, e.g. ="oanda"=),
=Instrument=, =Interval=, =Span= (half-open partition range), =Basis=;
=SchemaVersion=, =RawFingerprint= (hex-encoded content fingerprint of the
raw source artifact(s)), =BuilderVersion=, =ValidatorVersion=,
=ResamplerVersion= (="none"= when not derived — never left empty, so
empty always means "not yet set"), =CalendarVersion=; =BuiltAt= (from an
injected clock, never =time.Now=); a lightweight coverage summary
(=BarCount=, =FirstBar=, =LastBar=) — not the full Coverage/Gap model,
which stays with #79; and =Parent *ParentRef= for a derived/resampled
dataset, =nil= for a dataset built directly from raw.

=Manifest= has no stored "Revision" or "ID" field a caller could set
inconsistently with the rest of the record.  =Manifest.Revision()
string= computes a deterministic hex-encoded sha256 fingerprint from
every other field on demand: two independently built manifests with
identical inputs always produce the same revision, and changing any one
field except =BuiltAt= — including =Parent= — changes it.  =BuiltAt= is
excluded on purpose: it is Manager's own build-time provenance, not part
of dataset identity, so two datasets built from identical inputs at
different times must still agree.  The hash input is an unambiguous
JSON-encoded struct (fixed field order, no map, every string properly
quoted/escaped) tagged with an explicit encoding version, not a
hand-joined delimited string — a delimited encoding let one field's
content be crafted to collide with an adjacent field's key, which a
design review caught before merge.  A canonical file header or store
records this computed string as the dataset's version identifier,
matching the principle above that the version identifier lives in the
manifest or a file header, never in the path.

=Parent= carries the parent dataset's instrument, interval, and its own
=Revision()= string at build time — not an embedded parent =Manifest= —
so lineage does not force retention of a superseded revision; if the
parent is later rebuilt, the recorded revision simply stops matching the
parent's current one, which is the intended staleness signal.  A
Manifest's =Parent= and =ResamplerVersion= must agree with each other:
=Parent= is nil if and only if =ResamplerVersion= is the literal
=="none"==.  When =Parent= is set, it must name the same instrument as
the child and an interval strictly finer (shorter nominal duration) than
the child's own =Interval= — a resampled dataset only ever derives a
coarser interval from a finer one, so any other relationship is rejected
as impossible lineage rather than merely unverified.

=Manifest.Matches(bs BarSet) error= is the manifest/data pairing check:
instrument, interval, and basis must agree; =Span= must agree;
=BarCount= must equal =len(bs.Bars)=; and — closing a design-review gap
in the first draft — =FirstBar=/=LastBar= must agree with the actual
first and last bar's =Time= in =bs.Bars= (both zero when =bs.Bars= is
empty).  =Manifest.Validate()= checks the manifest's own structural
invariants independently of any =BarSet=: non-zero/non-empty required
fields, a positive =SchemaVersion=, a =RawFingerprint= matching the
required =<algorithm>:<hex digest>= form, a coverage summary consistent
with =BarCount= (empty means a zero range, exactly one bar means
=FirstBar= equals =LastBar=, more than one requires a strictly
increasing range), and the =Parent=/=ResamplerVersion= lineage rules
above.

This issue is the model only.  =marketdata.Manager= has no build/publish
operation to attach a =Manifest= to yet; that is later M2 work.

** DONE Raw-archive inventory and integrity inspection
Settled by issue #75 (branch =feature/75-oanda-inventory=):
=oanda.Inspect(ctx, root) (Inventory, error)= walks a raw OANDA archive
and produces a deterministic, read-only =Inventory= — it never repairs,
renames, deletes, re-downloads, or otherwise modifies anything under
=root=.  It lives in =marketdata/internal/provider/oanda= alongside the
reader (#70), per the boundary the issue's own tracking comment settled
with the owner: the reader parses one partition given a path; inventory
walks the archive tree and inspects what it finds.  =Inspect= reuses the
reader's =Meta=, =Record=, sentinels, and unexported =parsePathMeta= —
resolving instrument/interval/year/month from a file name is exactly
the reader's already-tested logic, not reimplemented.

=Inventory= holds three deterministically sorted slices:

- =Partitions= — one entry per discovered =*.csv= file whose name
  resolves to a known instrument and supported interval.  Each carries a
  =PartitionStatus= (=OK=, =Unreadable=, =Malformed=), row count,
  provider-incomplete row count, any duplicate timestamps found, the
  observed first/last record time, and an algorithm-qualified
  =sha256:<hex>= content fingerprint — exactly the form
  =marketdata.Manifest.RawFingerprint= (#73) expects, so a later build
  step can carry an =Inspect= fingerprint straight into a =Manifest=
  without reformatting it.  A file that fails to open, or whose rows
  fail to parse, is recorded with its status and error rather than
  aborting the walk: one bad file must not hide the rest of the
  inventory.
- =Skipped= — every file Inspect deliberately did not inventory as a
  partition, and why: an out-of-scope instrument (XAUUSD,
  =ErrInstrumentOutOfScope=), an interval the raw corpus does not carry
  (a stray =w1= file, =ErrUnsupportedInterval=), or a file name that does
  not match the =PAIR-YYYY-MM-tf.csv= shape at all
  (=ErrMalformedData=) — all distinguishable via =errors.Is=.
- =Gaps= — a =MonthGap= for every month strictly between an
  (instrument, interval) group's earliest and latest discovered
  partition that has no partition *file* at all.  This needs no trading
  calendar: it is purely a hole in the discovered month sequence, so a
  malformed or unreadable partition still counts as present (the file
  exists) and is not a gap.

*Deliberate non-goal, to keep the package boundary intact*: Inspect does
not attempt to judge whether an individual bar interval *within* a
present partition is missing because the market was closed or because
data is genuinely lost.  That judgment needs #74's =FXCalendar=/
=ClassifyInterval= machinery, and =marketdata/internal/provider/oanda=
deliberately does not import the root =marketdata= package at all (see
that package's own doc comment) — precisely so =marketdata.Manager= can
own and wire it without an import cycle.  Row-interval-level
completeness against calendar knowledge belongs to issue #79's coverage
engine, which operates on canonical data where that knowledge is
already available; #75 only ever reports the calendar-blind, purely
structural =MonthGap=.  This is also how "closed-market periods are not
reported as missing merely because no row exists" is satisfied: Inspect
simply never attempts row-level completeness inference in the first
place, so it cannot mistake a weekend or holiday for lost data.

Backup/save trees that mirror the raw archive's own =PAIR/YYYY/MM=
shape (confirmed to exist in practice, alongside the real archive) can
never be mistaken for it: =Inspect= never searches for =root=, only ever
descending from the exact directory the caller supplies, so a sibling
tree elsewhere on disk is simply never visited.  A design-review comment
on the PR caught a second, subtler version of the same risk: nothing
originally stopped a backup/save subtree *nested inside* =root=, or a
file simply filed under the wrong pair/year/month directory, from being
silently accepted as authoritative — =parsePathMeta= only ever looks at
a file's own name, never where it was actually found.  Fixed by
=verifyPathLayout=: every candidate file's path relative to =root= must
be exactly =SYMBOL/YYYY/MM/<filename>=, with those three directory
components agreeing with what the file name itself resolves to, or the
file is recorded as skipped (=ErrMalformedData=) rather than
inventoried.  Re-run against the real archive after this fix with
identical results (24,960 OK, 0 skipped-by-mistake), confirming it
rejects nothing legitimate.

A second review round (Copilot) found =inspectFile= reading each
partition's bytes twice — once to fingerprint, once via =ReadFile= to
parse — and pointed out that the second read's own OS-level failures
(a file vanishing between the two reads) would be misclassified as
=PartitionStatusMalformed= rather than =PartitionStatusUnreadable=.
Both are fixed together: the reader gained
=newReaderFromBytes(path, data)=, letting =inspectFile= read a
partition's bytes exactly once, fingerprint them directly, and parse
records from that same in-memory copy.  With only one read left, there
is no second filesystem access that could produce the misclassification
at all.

A third review round found one more edge case in that same fix:
=readRecordsFromBytes= can itself return =context.Canceled= or
=context.DeadlineExceeded= from =Reader.Next= when =ctx= is cancelled
while =inspectFile= is actively parsing a file's rows — and that path
was still unconditionally classified =PartitionStatusMalformed=, exactly
the same misclassification bug in a different guise.  This one could not
be caught by =Inspect='s own per-file =ctx.Err()= pre-check in its
=WalkDir= callback, since that check only ever observes cancellation
/between/ files; cancellation arriving while one file is being parsed
has no earlier checkpoint to catch it, and if that file happens to be
the last one =WalkDir= visits, there is no later checkpoint either —
=Inspect= would have returned a superficially successful =Inventory=
containing a bogus =Malformed= partition.  Fixed by giving =inspectFile=
a third, fatal-error return distinct from its =Partition=/=SkippedEntry=
results: a context error is propagated as fatal and aborts the walk,
while every other parse failure remains ordinary archive corruption that
never stops =Inspect=.

Full-archive inspection against a real, multi-decade archive is
operator-run, not part of normal CI: it lives behind the
=fullarchive= build tag
(=marketdata/internal/provider/oanda/inventory_fullarchive_test.go=)
and reads its target from a local =fullArchiveRoot= constant an
operator edits by hand and never commits, skipping itself whenever that
constant is empty (always true for a fresh checkout).  An environment
variable was the first design, but domain code under =marketdata/= may
not read the environment or flags — =config/arch_test.go= enforces this
mechanically across the whole module — and this package's own
=internal/= visibility rule means the test cannot be relocated to the
exempt =test/= tree either, since =oanda.Inspect= is only reachable from
within the =marketdata/= tree.  A hand-edited local constant is the
compliant alternative.  Deterministic, fixture-backed unit tests
covering every =PartitionStatus=, every =SkippedEntry= reason, month-gap
detection (including out-of-order
input and multi-group sort tie-breaks), and fingerprint stability run
in normal CI.

** DONE The boundary is non-negotiable and closed to outside implementation

The rule above is stronger than "consumers should prefer the DM".  No
package outside the =marketdata= hierarchy may implement, supply, or
even name a provider or storage seam.  Stated normatively:

#+BEGIN_QUOTE
The =marketdata= package is the sole public entry point for historical
market data.  No package outside the =marketdata= package hierarchy may
directly access, construct, configure, inject, or depend upon a
market-data provider, storage implementation, data-normalization or
derivation mechanism, cache, or persistence format.  These are private
implementation details owned by =marketdata= and packages beneath its
=internal= boundary.

A consumer may request data through =marketdata.Manager=.  If provider
choice must be exposed, the consumer may select a provider only by an
opaque logical name or identifier -- for example, =oanda=, =alpaca/iex=,
or =alpaca/sip=.  That selection must not expose a provider interface,
concrete provider type, credentials model, transport, or construction
mechanism.

Storage is never selected, supplied, or accessed by a data consumer.
The manager owns all decisions concerning storage, persistence layout,
canonicalization, aggregation/derivation, caching, and retrieval.

This restriction is intentional.  Relaxing it later requires an explicit
architectural decision and refactor; it must not happen incrementally by
exporting implementation seams.
#+END_QUOTE

Consequences:

- =Config= supplied to =marketdata= carries only consumer-level policy
  and selections.  If provider choice must be exposed later, it is an
  opaque logical name -- never a provider or storage implementation, an
  interface, a concrete type, a credentials model, or a construction
  mechanism.
- There is no externally implementable provider or storage injection
  seam.  Any such seam an implementation adds is a violation of this
  boundary, not an extension point.
- The boundary is enforced mechanically where Go's package rules allow
  it (an architecture test forbidding =marketdata= from importing
  provider/storage/vendor packages, and the =internal= boundary keeping
  the implementations un-importable from outside).

** DONE How will gaps and closed market days be handled
Fixed index with dummy data as done in the trader-first-try will not
be supported.

Settled at the =Bar= level by #72: a Bar existing *is* an observation,
so a missing interval is an *absent* Bar -- there is no zero-filled
dummy row and no per-Bar status flag.  Issue #74 adds the vocabulary for
*why* an interval is absent (or present but not final):
=marketdata.IntervalState= — =Present=, =Closed=, =Missing=,
=Incomplete=, =InProgress=, =Unexpected= — and
=ClassifyInterval(cal, span, now, present, providerComplete)=, a pure
classifier over facts a caller already has.  A present Bar during a
calendar closure classifies as =Unexpected=, never silently as
=Closed=: the two are not equivalent, since =Closed= means "the
calendar says no bar belongs here and none is present," while
=Unexpected= means the calendar and the data actively disagree — a
contradiction a design-review comment on the PR caught the first draft
silently collapsing into =Closed=, which would have let
=DatasetComplete= treat a real calendar/data conflict as accepted-absent.
Classification order beyond that is fixed: an interval that has not yet
elapsed is next, ahead of a still-forming Bar that happens to already be
present; only then do presence and the provider's own =complete= flag
decide =Present=/=Missing=/=Incomplete=.
=DatasetComplete(states []IntervalState)= formally defines completeness:
true iff every entry is =Present= or =Closed= — =Unexpected= is
deliberately excluded from that set.

=ClassifyInterval= requires the calendar to report one uniform =Status=
across the *entire* span, not just its start: it samples =Status= at
both =span.Start()= and just before =span.End()=, and, when that status
is =StatusOpen=, additionally requires =cal.Session(span.Start())= to
fully contain =span=.  A span that fails either check — for example a
UTC-aligned H4 bar straddling a 13:00 New York partial-closure threshold
— is rejected with a wrapped =ErrIntervalStraddlesBoundary= rather than
silently classified from its start alone, which a design-review comment
identified as unsafe in the first draft: sampling only =span.Start()=
would have misclassified exactly that straddling case, and would have
kept doing so silently.  Splitting or otherwise resolving a straddling
span is left to the caller (#79's coverage engine, in practice); this
cannot happen for a session-aligned D1/W1 bar, whose span already equals
one =Calendar=-defined session or week.

Walking a real query range, producing a =[]IntervalState= for it, and
reading raw's =complete= flag to populate =providerComplete= during
normalization all remain later work: walking a range is #79's coverage
engine, and populating =providerComplete= from OANDA's raw =complete=
column is #76's normalization stage.  #74 defines the vocabulary and its
classification rules only.

**** One file, not two — a design-review correction
The first draft published manifest and data as two separate files,
relying on =os.Rename='s single-file atomicity plus a documented
ordering (data renamed, then manifest) and =Manifest.Matches= to reject
whatever a reader might observe mid-sequence.  A design review on the
PR identified that this still violated the issue's own acceptance
criterion that failure or cancellation must leave the prior published
revision /intact/: once the data file's rename succeeded, the old data
was already gone, overwritten by the new file's bytes.  =Matches=
failing on the resulting mixed pair meant the corruption was
/detected/, but the previously published dataset was not /loadable/
again until a further publish completed successfully — the regression
test written to demonstrate the mechanism (=PublishCancelledBetweenWrites=)
was, on inspection, codifying exactly that contradictory outcome rather
than proving safety.

The fix is the other option the issue's own scope explicitly allowed
("the dataset manifest or agreed file header"): manifest and data now
share one file, so there is exactly one =os.Rename= — genuinely atomic,
not "atomic per file with a window between two files."  A publish
cancelled or failed before that one rename leaves the previously
published file completely untouched and fully loadable; a publish that
completes it replaces the whole (manifest, data) pair in a single
indivisible step.  There is no intermediate state to reach at all, so
the regression test now asserts what the acceptance criterion actually
requires: cancelling a republish leaves the *original* revision
loadable, not merely a detectably-broken one.

**** Encoding the manifest header as JSON, not key=value lines
A second review finding: the first draft's manifest header used
hand-joined =key=value= lines, but =Manifest.Validate= only requires
its string fields (=Provider=, the version fields, =Parent.Revision=)
to be non-empty — none of them are required to be free of embedded
=\n=/=\r=, so a line-oriented encoding cannot round-trip every
=Manifest= value =Validate= itself accepts.  This is the identical
ambiguity a review already caught and fixed in
=Manifest.Revision()= (#73), which is why that function already hashes
a JSON-encoded struct rather than a delimited string.  The store's
header now does the same: one JSON-encoded line, quoted/escaped by
construction, immune to the field-boundary ambiguity a delimited format
has.

**** Verifying, not just storing, the manifest
Two related review findings hardened what =load= actually checks
against a stored header, beyond =Manifest.Validate=/=Matches=:

- The header's =revision= field (=Manifest.Revision()= at encode time)
  is now recomputed from the decoded =Manifest= and compared against
  the stored value; a mismatch is =errStoreMalformed=.  This is the
  cheapest possible defense against a hand-edited or partially
  corrupted header whose individual fields still happen to parse
  correctly in isolation.
- A derived manifest's =parent.instrument= field is now cross-checked
  against the caller-supplied expected instrument (the same check
  already applied to the manifest's own top-level instrument) rather
  than being silently discarded and overwritten — the first draft threw
  the stored value away entirely and always substituted the expected
  instrument, which meant a manifest whose parent stanza actually named
  a *different* instrument than expected would still validate.

**** Partition-key/manifest agreement and path safety
Two further review findings, both about =publish= accepting input that
should never have been accepted in the first place:

- =publish= now calls =checkKeyMatchesManifest=, verifying =key='s
  instrument, provider, and interval agree with =m= before writing
  anything, and that =m.Span= *overlaps* — not necessarily falls
  entirely within — the calendar month =key.year=/=key.month= name.
  Overlap rather than exact containment is deliberate: a session-aligned
  D1 span can legitimately open in the closing hours of the previous UTC
  day, occasionally the previous UTC month, while still correctly
  belonging to the calendar month a caller filed it under.  Without this
  check, =publish= could succeed while writing a partition that could
  never subsequently be loaded (a zero or mismatched instrument) or that
  landed under the wrong provider/interval directory entirely.
- =partitionKey.provider= and =partitionKey.symbol= are now validated as
  safe, single path components (non-empty, not =.=/=..=, free of any
  path separator) before any filesystem operation, with a defense-in-depth
  check that the resolved path still falls beneath the configured root.
  Both values are name-based and originate outside the storage
  implementation (a provider identifier, an instrument's display
  symbol); even though this store is internal, nothing before this fix
  stopped a value containing =..= from escaping the intended
  provider/symbol partition.

**** Cancellation checked all the way to the commit point
A second review round on the single-file redesign above found the fix
still had a gap: =publish= only checked =ctx.Err()= twice, both before
any writing began, so a cancellation arriving while =encodePartition=
was actively writing a large partition's rows — real work already
under way — went unnoticed until the write, flush, sync, and rename had
*all* already succeeded, silently replacing the prior revision anyway.
=writeFileAtomic= now takes =ctx= and checks it once more immediately
before =os.Rename= — nothing after that check can leave a torn or
unexpectedly-replaced file, so this is the genuine commit point.
=encodePartition= additionally checks =ctx.Err()= on every bar row, so
cancellation on a large (M1-scale) partition is caught promptly rather
than only at the end. Three regression tests, using a custom
=context.Context= whose =Err()= returns nil a controlled number of
times before reporting cancellation, pin down exactly where in the
sequence — before the write starts, mid-loop after real work has begun,
and immediately before the rename — cancellation lands, confirming the
original revision remains fully loadable in every case.

* DONE Where does FX holiday data come from?
Settled by issue #74: adopted, unchanged, from
=trader-first-try/market/forex_hours.go='s =isMajorForexHolidayClosed= —
the one holiday source Trader had already exercised against real OANDA
data, and the source this note originally pointed at.  It is exposed as
=marketdata.StandardFXHolidays(years ...int) FXCalendarParams=, Trader's
accepted M2 rule set:

- Jan 1, Dec 25, Dec 26 — closed all day.
- Dec 24, Dec 31 — closed from 13:00 New York time onward (not fully
  closed; the market is open earlier that day).  =FXCalendar= gained a
  new =PartialClosure= concept for exactly this: a session that is
  truncated early rather than not opening at all.
- Sunday evening stays closed when *that Sunday itself* is one of the
  three full-day holidays — implemented as one additional rule in
  =FXCalendar.Status=, since the existing session-labeled-by-ending-date
  model does not otherwise cover it (the following Monday is not itself
  a holiday date in that scenario).  The "following Monday is a holiday"
  half of the old rule needs no special case at all: it is already
  covered by the ordinary ending-date holiday check, since the session
  opening Sunday evening is labeled by the Monday it ends on.

=FXCalendar.Status= and =FXCalendar.Session= are computed by one shared,
unexported =classify= method rather than independently, specifically
because a partial closure or the Sunday-holiday rule can *truncate* a
session rather than remove it outright — a design-review comment on the
PR caught the first draft computing them separately, which let =Session=
keep returning the full nominal rollover-to-rollover range even where
=Status= reported the tail (or, for the Sunday case, the head) of that
same range as closed, violating =FXCalendar='s own documented invariant
that every instant a returned =Session= contains reports the same
=Status=.  With one shared implementation, =Session= now returns the
truncated open window directly (for example, ending at 13:00 on Dec 24
rather than 17:00, or starting at the following New York midnight rather
than the nominal Sunday 17:00 rollover when that Sunday is a holiday),
so the two methods cannot drift apart again.  =Bar= is unaffected by
truncation on purpose: its nominal, calendar-aligned D1/W1 range answers
a different question ("what interval does this instant belong to") than
=Session= ("when was trading actually open"), and truncating it would
conflate the two.

This is still deliberately narrow, unchanged from the source: no Good
Friday, no in-lieu observance when a holiday falls on a weekend, and no
non-FX venue calendars.  Extending it is a separate, later decision, not
a silent addition made while implementing #74.  =FXCalendar= itself
remains a pure calendar with no holiday data of its own —
=StandardFXHolidays= is a caller-supplied params builder, not a change to
what =FXCalendar= assumes by default.

** DONE Normalize and validate OANDA records into canonical Bars
Settled by issue #76 (branch =feature/76-normalize-oanda-bars=):
=normalizeOANDARecord= and =normalizeOANDASequence=, unexported
functions living directly in the =marketdata= package (not a new
=marketdata/internal/...= package — see below for why), convert
=oanda.Record= values into =Bar= candidates and classify each into one
of four =recordOutcome= values (also unexported — see the review note
below for why):

- =recordOutcomeAccepted= — a valid, provider-complete, correctly
  ordered and interval-aligned =Bar=.
- =recordOutcomeIncomplete= — a structurally valid =Bar=, but OANDA's
  own =complete= flag was false; never treated as final and never
  persisted as a canonical =Bar= (see the note above).
- =recordOutcomeSuspicious= — an ask below its corresponding bid at some
  OHLC corner, caught by =num.Price.Sub= reporting =num.ErrNegative=
  before a candidate =Bar= can even be built.  A crossed market is a
  real data anomaly the raw CSV format does not rule out on its own,
  distinct from an otherwise-well-formed =Bar= shape that fails
  validation, and distinct from a spread computation that fails for any
  other reason (checked-arithmetic overflow, say) — a design-review
  comment on the PR caught the first draft classifying every
  =spreadSummary= error =Suspicious=, which would have mislabeled a pure
  computation failure as a market anomaly.  =spreadSummary= now reports
  whether a failure was specifically a crossed corner, and only that
  case is =Suspicious=; anything else is =Rejected=.
- =recordOutcomeRejected= — an impossible =Bar= shape (=Bar.Validate=,
  from #72, reused as-is — not reimplemented), a non-crossed spread
  computation failure, a timestamp that duplicates *any* earlier record
  in the same sequence (not only the immediately preceding one — another
  review fix; the first draft's =prevTime=-only comparison missed a
  timestamp repeating an older, non-adjacent record) or precedes the
  previous record, or a timestamp that does not land on
  =Calendar.Bar='s computed interval boundary.

=normalizeOANDASequence= processes one partition's records in file
order and returns exactly one =normalizedRecord= per input record, in
that order: nothing is silently dropped, repaired, or coalesced, and a
rejected record never breaks validation of the records after it — each
record's ordering/duplicate check compares against every record seen so
far in the actual input sequence, not just the previously accepted
ones.  A =Calendar.Bar= failure while checking alignment is treated as
its own kind of problem, not folded into =errRecordMisaligned=: a
review comment pointed out that a calendar unable to evaluate a
boundary is not evidence the timestamp is misaligned, so
=normalizeOANDASequence= now aborts with that error directly (a
sequence-level failure) rather than misclassifying the record.

*Why =recordOutcome=/=normalizedRecord=/the sentinels are unexported*:
a review comment on the PR flagged that exporting them would expand and
stabilize the public =marketdata= API for values no external caller can
currently obtain, since both normalization entry points are themselves
unexported.  Should =Manager= later need an operator-facing
normalization report, that is the right time to design a deliberate,
provider-neutral public result contract — not to promote these internal
types as-is.

*Why this lives directly in the =marketdata= package*: the normalizer
must both consume =oanda.Record=/=oanda.RawInterval= (importable only
from within the =marketdata/= tree) and produce =marketdata.Bar=
values.  =oanda= deliberately never imports =marketdata= (documented,
so =Manager= can wire it without a cycle); if the normalizer instead
lived in its own =marketdata/internal/normalize= package that imported
root =marketdata= for =Bar=, wiring it into =Manager= later would
recreate exactly that cycle.  Living directly in package =marketdata= —
where =Bar=, =BarSet=, =Interval=, =Calendar=, and =Manifest= already
live — avoids this: =marketdata= may already import its own
=internal/= subtree, one-directionally.  Both functions stay
unexported, reachable only from within =marketdata=, the same boundary
#75's archive inventory already established.

*Non-goals, deferred on purpose*: assembling a full =BarSet=/=Manifest=
from a normalized partition (span computation, dataset publishing) is
later canonical-build work, not record-level normalization; and no gap
or coverage reasoning happens here at all — #76 only ever sees the
records actually present in one partition, exactly as #74 and #75 already
scoped their own calendar- and file-level concerns away from each
other's.
