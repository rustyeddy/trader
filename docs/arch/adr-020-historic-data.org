** DONE We may keep a manifest
Settled by issue #73 (branch =feature/73-manifest=): =marketdata.Manifest=
is the collection-level identity, provenance, and revision record for a
canonical =BarSet=.  =Bar=/=BarSet= (#72) hold observation-local facts;
=Manifest= holds why the dataset is trustworthy and what produced it,
independently of any filesystem path.

Fields: =Provider= (opaque logical provider name, e.g. ="oanda"=),
=Instrument=, =Interval=, =Span= (half-open partition range), =Basis=;
=SchemaVersion=, =RawFingerprint= (hex-encoded content fingerprint of the
raw source artifact(s)), =BuilderVersion=, =ValidatorVersion=,
=ResamplerVersion= (="none"= when not derived — never left empty, so
empty always means "not yet set"), =CalendarVersion=; =BuiltAt= (from an
injected clock, never =time.Now=); a lightweight coverage summary
(=BarCount=, =FirstBar=, =LastBar=) — not the full Coverage/Gap model,
which stays with #79; and =Parent *ParentRef= for a derived/resampled
dataset, =nil= for a dataset built directly from raw.

=Manifest= has no stored "Revision" or "ID" field a caller could set
inconsistently with the rest of the record.  =Manifest.Revision()
string= computes a deterministic hex-encoded sha256 fingerprint from
every other field on demand: two independently built manifests with
identical inputs always produce the same revision, and changing any one
field except =BuiltAt= — including =Parent= — changes it.  =BuiltAt= is
excluded on purpose: it is Manager's own build-time provenance, not part
of dataset identity, so two datasets built from identical inputs at
different times must still agree.  The hash input is an unambiguous
JSON-encoded struct (fixed field order, no map, every string properly
quoted/escaped) tagged with an explicit encoding version, not a
hand-joined delimited string — a delimited encoding let one field's
content be crafted to collide with an adjacent field's key, which a
design review caught before merge.  A canonical file header or store
records this computed string as the dataset's version identifier,
matching the principle above that the version identifier lives in the
manifest or a file header, never in the path.

=Parent= carries the parent dataset's instrument, interval, and its own
=Revision()= string at build time — not an embedded parent =Manifest= —
so lineage does not force retention of a superseded revision; if the
parent is later rebuilt, the recorded revision simply stops matching the
parent's current one, which is the intended staleness signal.  A
Manifest's =Parent= and =ResamplerVersion= must agree with each other:
=Parent= is nil if and only if =ResamplerVersion= is the literal
=="none"==.  When =Parent= is set, it must name the same instrument as
the child and an interval strictly finer (shorter nominal duration) than
the child's own =Interval= — a resampled dataset only ever derives a
coarser interval from a finer one, so any other relationship is rejected
as impossible lineage rather than merely unverified.

=Manifest.Matches(bs BarSet) error= is the manifest/data pairing check:
instrument, interval, and basis must agree; =Span= must agree;
=BarCount= must equal =len(bs.Bars)=; and — closing a design-review gap
in the first draft — =FirstBar=/=LastBar= must agree with the actual
first and last bar's =Time= in =bs.Bars= (both zero when =bs.Bars= is
empty).  =Manifest.Validate()= checks the manifest's own structural
invariants independently of any =BarSet=: non-zero/non-empty required
fields, a positive =SchemaVersion=, a =RawFingerprint= matching the
required =<algorithm>:<hex digest>= form, a coverage summary consistent
with =BarCount= (empty means a zero range, exactly one bar means
=FirstBar= equals =LastBar=, more than one requires a strictly
increasing range), and the =Parent=/=ResamplerVersion= lineage rules
above.

This issue is the model only.  =marketdata.Manager= has no build/publish
operation to attach a =Manifest= to yet; that is later M2 work.

** DONE Day and week alignment needs to be resolved.
Settled by issue #74 (branch =feature/74-fx-calendar-completeness=),
building on ADR-012's already-accepted =FXCalendar= day/week boundaries
(17:00 New York rollover for D1, Sunday 17:00 New York open for W1; both
DST-safe via =time.Date= in =America/New_York=, never fixed-duration
arithmetic).  What #74 adds:

- *OANDA alignment parameters*: any future live/download synchronization
  must pin =dailyAlignment=17= and =alignmentTimezone=America/New_York=
  explicitly, documented in
  =marketdata/internal/provider/oanda/doc.go=.  The preserved raw
  archive's own D1 opens already match this rollover, but only because
  the legacy client happened to inherit OANDA's undocumented defaults —
  not because it requested them (see =trader-first-try/types/time.go= and
  =docs/Archive/candle-store-timestamp-fix.org= in that repo).  A pinned
  request survives a provider default changing without Trader silently
  mis-aligning new data against the old archive.
- *W1 native versus derived*: decided as *derived*.  The preserved raw
  archive has no OANDA-native weekly partition at all — see
  =oanda.RawInterval=, which has no =RawW1= token and reports
  =ErrUnsupportedInterval= for one — so there is nothing to synchronize
  weekly alignment against for M2.  This decision has not been verified
  against OANDA's live =weeklyAlignment= API parameter (no live network
  access was available to check it); it is recorded as M2's scope
  decision, not a verified API fact, and should be revisited when live
  synchronization is actually built.  W1 bars are produced by resampling
  canonical D1 — see the =Manifest.Parent=/=ResamplerVersion= lineage
  model (#73) built for exactly this relationship.

** DONE The boundary is non-negotiable and closed to outside implementation

The rule above is stronger than "consumers should prefer the DM".  No
package outside the =marketdata= hierarchy may implement, supply, or
even name a provider or storage seam.  Stated normatively:

#+BEGIN_QUOTE
The =marketdata= package is the sole public entry point for historical
market data.  No package outside the =marketdata= package hierarchy may
directly access, construct, configure, inject, or depend upon a
market-data provider, storage implementation, data-normalization or
derivation mechanism, cache, or persistence format.  These are private
implementation details owned by =marketdata= and packages beneath its
=internal= boundary.

A consumer may request data through =marketdata.Manager=.  If provider
choice must be exposed, the consumer may select a provider only by an
opaque logical name or identifier -- for example, =oanda=, =alpaca/iex=,
or =alpaca/sip=.  That selection must not expose a provider interface,
concrete provider type, credentials model, transport, or construction
mechanism.

Storage is never selected, supplied, or accessed by a data consumer.
The manager owns all decisions concerning storage, persistence layout,
canonicalization, aggregation/derivation, caching, and retrieval.

This restriction is intentional.  Relaxing it later requires an explicit
architectural decision and refactor; it must not happen incrementally by
exporting implementation seams.
#+END_QUOTE

Consequences:

- =Config= supplied to =marketdata= carries only consumer-level policy
  and selections.  If provider choice must be exposed later, it is an
  opaque logical name -- never a provider or storage implementation, an
  interface, a concrete type, a credentials model, or a construction
  mechanism.
- There is no externally implementable provider or storage injection
  seam.  Any such seam an implementation adds is a violation of this
  boundary, not an extension point.
- The boundary is enforced mechanically where Go's package rules allow
  it (an architecture test forbidding =marketdata= from importing
  provider/storage/vendor packages, and the =internal= boundary keeping
  the implementations un-importable from outside).

* DONE Determine the marketdata.Bar structure
Settled by issue #72 (branch =feature/72-marketdata-bar=).

Two levels, as anticipated:

- =marketdata.Bar= (per observation): =Time= (authoritative observed
  open, stored verbatim, never index-reconstructed -- the #179 DST
  lesson), bid-basis =Open/High/Low/Close= (=num.Price=), =AvgSpread=,
  =MaxSpread= (=num.Price=), and =Ticks= (plain =int64=, not
  =num.Quantity= -- ADR-004 defines no count type).
- =marketdata.BarSet= (collection): the homogeneous metadata shared by
  every bar -- =Instrument=, =Interval=, =Span= (half-open =TimeRange=),
  and =Basis= (=PriceBasis=) -- so it is never repeated per Bar.

Both are plain records with exported fields, validated via =Validate()=
at the normalization/store boundary rather than through a constructor,
per the architecture document's "plain data transfer structs may remain
literals" convention. =Mid()= and =Range(interval, calendar)= are
derived getters; mid and the half-open range are computed, not stored.

Dataset revision/provenance stays with the manifest (#73) and
coverage/gap detail with coverage (#79); =BarSet= references those
levels rather than absorbing them.

** DONE How will gaps and closed market days be handled
Fixed index with dummy data as done in the trader-first-try will not
be supported.

Settled at the =Bar= level by #72: a Bar existing *is* an observation,
so a missing interval is an *absent* Bar -- there is no zero-filled
dummy row and no per-Bar status flag.  Issue #74 adds the vocabulary for
*why* an interval is absent (or present but not final):
=marketdata.IntervalState= — =Present=, =Closed=, =Missing=,
=Incomplete=, =InProgress=, =Unexpected= — and
=ClassifyInterval(cal, span, now, present, providerComplete)=, a pure
classifier over facts a caller already has.  A present Bar during a
calendar closure classifies as =Unexpected=, never silently as
=Closed=: the two are not equivalent, since =Closed= means "the
calendar says no bar belongs here and none is present," while
=Unexpected= means the calendar and the data actively disagree — a
contradiction a design-review comment on the PR caught the first draft
silently collapsing into =Closed=, which would have let
=DatasetComplete= treat a real calendar/data conflict as accepted-absent.
Classification order beyond that is fixed: an interval that has not yet
elapsed is next, ahead of a still-forming Bar that happens to already be
present; only then do presence and the provider's own =complete= flag
decide =Present=/=Missing=/=Incomplete=.
=DatasetComplete(states []IntervalState)= formally defines completeness:
true iff every entry is =Present= or =Closed= — =Unexpected= is
deliberately excluded from that set.

=ClassifyInterval= requires the calendar to report one uniform =Status=
across the *entire* span, not just its start: it samples =Status= at
both =span.Start()= and just before =span.End()=, and, when that status
is =StatusOpen=, additionally requires =cal.Session(span.Start())= to
fully contain =span=.  A span that fails either check — for example a
UTC-aligned H4 bar straddling a 13:00 New York partial-closure threshold
— is rejected with a wrapped =ErrIntervalStraddlesBoundary= rather than
silently classified from its start alone, which a design-review comment
identified as unsafe in the first draft: sampling only =span.Start()=
would have misclassified exactly that straddling case, and would have
kept doing so silently.  Splitting or otherwise resolving a straddling
span is left to the caller (#79's coverage engine, in practice); this
cannot happen for a session-aligned D1/W1 bar, whose span already equals
one =Calendar=-defined session or week.

Walking a real query range, producing a =[]IntervalState= for it, and
reading raw's =complete= flag to populate =providerComplete= during
normalization all remain later work: walking a range is #79's coverage
engine, and populating =providerComplete= from OANDA's raw =complete=
column is #76's normalization stage.  #74 defines the vocabulary and its
classification rules only.

* DONE Where does FX holiday data come from?
Settled by issue #74: adopted, unchanged, from
=trader-first-try/market/forex_hours.go='s =isMajorForexHolidayClosed= —
the one holiday source Trader had already exercised against real OANDA
data, and the source this note originally pointed at.  It is exposed as
=marketdata.StandardFXHolidays(years ...int) FXCalendarParams=, Trader's
accepted M2 rule set:

- Jan 1, Dec 25, Dec 26 — closed all day.
- Dec 24, Dec 31 — closed from 13:00 New York time onward (not fully
  closed; the market is open earlier that day).  =FXCalendar= gained a
  new =PartialClosure= concept for exactly this: a session that is
  truncated early rather than not opening at all.
- Sunday evening stays closed when *that Sunday itself* is one of the
  three full-day holidays — implemented as one additional rule in
  =FXCalendar.Status=, since the existing session-labeled-by-ending-date
  model does not otherwise cover it (the following Monday is not itself
  a holiday date in that scenario).  The "following Monday is a holiday"
  half of the old rule needs no special case at all: it is already
  covered by the ordinary ending-date holiday check, since the session
  opening Sunday evening is labeled by the Monday it ends on.

=FXCalendar.Status= and =FXCalendar.Session= are computed by one shared,
unexported =classify= method rather than independently, specifically
because a partial closure or the Sunday-holiday rule can *truncate* a
session rather than remove it outright — a design-review comment on the
PR caught the first draft computing them separately, which let =Session=
keep returning the full nominal rollover-to-rollover range even where
=Status= reported the tail (or, for the Sunday case, the head) of that
same range as closed, violating =FXCalendar='s own documented invariant
that every instant a returned =Session= contains reports the same
=Status=.  With one shared implementation, =Session= now returns the
truncated open window directly (for example, ending at 13:00 on Dec 24
rather than 17:00, or starting at the following New York midnight rather
than the nominal Sunday 17:00 rollover when that Sunday is a holiday),
so the two methods cannot drift apart again.  =Bar= is unaffected by
truncation on purpose: its nominal, calendar-aligned D1/W1 range answers
a different question ("what interval does this instant belong to") than
=Session= ("when was trading actually open"), and truncating it would
conflate the two.

This is still deliberately narrow, unchanged from the source: no Good
Friday, no in-lieu observance when a holiday falls on a weekend, and no
non-FX venue calendars.  Extending it is a separate, later decision, not
a silent addition made while implementing #74.  =FXCalendar= itself
remains a pure calendar with no holiday data of its own —
=StandardFXHolidays= is a caller-supplied params builder, not a change to
what =FXCalendar= assumes by default.
