** DONE We may keep a manifest
Settled by issue #73 (branch =feature/73-manifest=): =marketdata.Manifest=
is the collection-level identity, provenance, and revision record for a
canonical =BarSet=.  =Bar=/=BarSet= (#72) hold observation-local facts;
=Manifest= holds why the dataset is trustworthy and what produced it,
independently of any filesystem path.

Fields: =Provider= (opaque logical provider name, e.g. ="oanda"=),
=Instrument=, =Interval=, =Span= (half-open partition range), =Basis=;
=SchemaVersion=, =RawFingerprint= (hex-encoded content fingerprint of the
raw source artifact(s)), =BuilderVersion=, =ValidatorVersion=,
=ResamplerVersion= (="none"= when not derived — never left empty, so
empty always means "not yet set"), =CalendarVersion=; =BuiltAt= (from an
injected clock, never =time.Now=); a lightweight coverage summary
(=BarCount=, =FirstBar=, =LastBar=) — not the full Coverage/Gap model,
which stays with #79; and =Parent *ParentRef= for a derived/resampled
dataset, =nil= for a dataset built directly from raw.

=Manifest= has no stored "Revision" or "ID" field a caller could set
inconsistently with the rest of the record.  =Manifest.Revision()
string= computes a deterministic hex-encoded sha256 fingerprint from
every other field on demand: two independently built manifests with
identical inputs always produce the same revision, and changing any one
field except =BuiltAt= — including =Parent= — changes it.  =BuiltAt= is
excluded on purpose: it is Manager's own build-time provenance, not part
of dataset identity, so two datasets built from identical inputs at
different times must still agree.  The hash input is an unambiguous
JSON-encoded struct (fixed field order, no map, every string properly
quoted/escaped) tagged with an explicit encoding version, not a
hand-joined delimited string — a delimited encoding let one field's
content be crafted to collide with an adjacent field's key, which a
design review caught before merge.  A canonical file header or store
records this computed string as the dataset's version identifier,
matching the principle above that the version identifier lives in the
manifest or a file header, never in the path.

=Parent= carries the parent dataset's instrument, interval, and its own
=Revision()= string at build time — not an embedded parent =Manifest= —
so lineage does not force retention of a superseded revision; if the
parent is later rebuilt, the recorded revision simply stops matching the
parent's current one, which is the intended staleness signal.  A
Manifest's =Parent= and =ResamplerVersion= must agree with each other:
=Parent= is nil if and only if =ResamplerVersion= is the literal
=="none"==.  When =Parent= is set, it must name the same instrument as
the child and an interval strictly finer (shorter nominal duration) than
the child's own =Interval= — a resampled dataset only ever derives a
coarser interval from a finer one, so any other relationship is rejected
as impossible lineage rather than merely unverified.

=Manifest.Matches(bs BarSet) error= is the manifest/data pairing check:
instrument, interval, and basis must agree; =Span= must agree;
=BarCount= must equal =len(bs.Bars)=; and — closing a design-review gap
in the first draft — =FirstBar=/=LastBar= must agree with the actual
first and last bar's =Time= in =bs.Bars= (both zero when =bs.Bars= is
empty).  =Manifest.Validate()= checks the manifest's own structural
invariants independently of any =BarSet=: non-zero/non-empty required
fields, a positive =SchemaVersion=, a =RawFingerprint= matching the
required =<algorithm>:<hex digest>= form, a coverage summary consistent
with =BarCount= (empty means a zero range, exactly one bar means
=FirstBar= equals =LastBar=, more than one requires a strictly
increasing range), and the =Parent=/=ResamplerVersion= lineage rules
above.

This issue is the model only.  =marketdata.Manager= has no build/publish
operation to attach a =Manifest= to yet; that is later M2 work.

** DONE Raw-archive inventory and integrity inspection
Settled by issue #75 (branch =feature/75-oanda-inventory=):
=oanda.Inspect(ctx, root) (Inventory, error)= walks a raw OANDA archive
and produces a deterministic, read-only =Inventory= — it never repairs,
renames, deletes, re-downloads, or otherwise modifies anything under
=root=.  It lives in =marketdata/internal/provider/oanda= alongside the
reader (#70), per the boundary the issue's own tracking comment settled
with the owner: the reader parses one partition given a path; inventory
walks the archive tree and inspects what it finds.  =Inspect= reuses the
reader's =Meta=, =Record=, sentinels, and unexported =parsePathMeta= —
resolving instrument/interval/year/month from a file name is exactly
the reader's already-tested logic, not reimplemented.

=Inventory= holds three deterministically sorted slices:

- =Partitions= — one entry per discovered =*.csv= file whose name
  resolves to a known instrument and supported interval.  Each carries a
  =PartitionStatus= (=OK=, =Unreadable=, =Malformed=), row count,
  provider-incomplete row count, any duplicate timestamps found, the
  observed first/last record time, and an algorithm-qualified
  =sha256:<hex>= content fingerprint — exactly the form
  =marketdata.Manifest.RawFingerprint= (#73) expects, so a later build
  step can carry an =Inspect= fingerprint straight into a =Manifest=
  without reformatting it.  A file that fails to open, or whose rows
  fail to parse, is recorded with its status and error rather than
  aborting the walk: one bad file must not hide the rest of the
  inventory.
- =Skipped= — every file Inspect deliberately did not inventory as a
  partition, and why: an out-of-scope instrument (XAUUSD,
  =ErrInstrumentOutOfScope=), an interval the raw corpus does not carry
  (a stray =w1= file, =ErrUnsupportedInterval=), or a file name that does
  not match the =PAIR-YYYY-MM-tf.csv= shape at all
  (=ErrMalformedData=) — all distinguishable via =errors.Is=.
- =Gaps= — a =MonthGap= for every month strictly between an
  (instrument, interval) group's earliest and latest discovered
  partition that has no partition *file* at all.  This needs no trading
  calendar: it is purely a hole in the discovered month sequence, so a
  malformed or unreadable partition still counts as present (the file
  exists) and is not a gap.

*Deliberate non-goal, to keep the package boundary intact*: Inspect does
not attempt to judge whether an individual bar interval *within* a
present partition is missing because the market was closed or because
data is genuinely lost.  That judgment needs #74's =FXCalendar=/
=ClassifyInterval= machinery, and =marketdata/internal/provider/oanda=
deliberately does not import the root =marketdata= package at all (see
that package's own doc comment) — precisely so =marketdata.Manager= can
own and wire it without an import cycle.  Row-interval-level
completeness against calendar knowledge belongs to issue #79's coverage
engine, which operates on canonical data where that knowledge is
already available; #75 only ever reports the calendar-blind, purely
structural =MonthGap=.  This is also how "closed-market periods are not
reported as missing merely because no row exists" is satisfied: Inspect
simply never attempts row-level completeness inference in the first
place, so it cannot mistake a weekend or holiday for lost data.

Backup/save trees that mirror the raw archive's own =PAIR/YYYY/MM=
shape (confirmed to exist in practice, alongside the real archive) can
never be mistaken for it: =Inspect= never searches for =root=, only ever
descending from the exact directory the caller supplies, so a sibling
tree elsewhere on disk is simply never visited.  A design-review comment
on the PR caught a second, subtler version of the same risk: nothing
originally stopped a backup/save subtree *nested inside* =root=, or a
file simply filed under the wrong pair/year/month directory, from being
silently accepted as authoritative — =parsePathMeta= only ever looks at
a file's own name, never where it was actually found.  Fixed by
=verifyPathLayout=: every candidate file's path relative to =root= must
be exactly =SYMBOL/YYYY/MM/<filename>=, with those three directory
components agreeing with what the file name itself resolves to, or the
file is recorded as skipped (=ErrMalformedData=) rather than
inventoried.  Re-run against the real archive after this fix with
identical results (24,960 OK, 0 skipped-by-mistake), confirming it
rejects nothing legitimate.

A second review round (Copilot) found =inspectFile= reading each
partition's bytes twice — once to fingerprint, once via =ReadFile= to
parse — and pointed out that the second read's own OS-level failures
(a file vanishing between the two reads) would be misclassified as
=PartitionStatusMalformed= rather than =PartitionStatusUnreadable=.
Both are fixed together: the reader gained
=newReaderFromBytes(path, data)=, letting =inspectFile= read a
partition's bytes exactly once, fingerprint them directly, and parse
records from that same in-memory copy.  With only one read left, there
is no second filesystem access that could produce the misclassification
at all.

A third review round found one more edge case in that same fix:
=readRecordsFromBytes= can itself return =context.Canceled= or
=context.DeadlineExceeded= from =Reader.Next= when =ctx= is cancelled
while =inspectFile= is actively parsing a file's rows — and that path
was still unconditionally classified =PartitionStatusMalformed=, exactly
the same misclassification bug in a different guise.  This one could not
be caught by =Inspect='s own per-file =ctx.Err()= pre-check in its
=WalkDir= callback, since that check only ever observes cancellation
/between/ files; cancellation arriving while one file is being parsed
has no earlier checkpoint to catch it, and if that file happens to be
the last one =WalkDir= visits, there is no later checkpoint either —
=Inspect= would have returned a superficially successful =Inventory=
containing a bogus =Malformed= partition.  Fixed by giving =inspectFile=
a third, fatal-error return distinct from its =Partition=/=SkippedEntry=
results: a context error is propagated as fatal and aborts the walk,
while every other parse failure remains ordinary archive corruption that
never stops =Inspect=.

Full-archive inspection against a real, multi-decade archive is
operator-run, not part of normal CI: it lives behind the
=fullarchive= build tag
(=marketdata/internal/provider/oanda/inventory_fullarchive_test.go=)
and reads its target from a local =fullArchiveRoot= constant an
operator edits by hand and never commits, skipping itself whenever that
constant is empty (always true for a fresh checkout).  An environment
variable was the first design, but domain code under =marketdata/= may
not read the environment or flags — =config/arch_test.go= enforces this
mechanically across the whole module — and this package's own
=internal/= visibility rule means the test cannot be relocated to the
exempt =test/= tree either, since =oanda.Inspect= is only reachable from
within the =marketdata/= tree.  A hand-edited local constant is the
compliant alternative.  Deterministic, fixture-backed unit tests
covering every =PartitionStatus=, every =SkippedEntry= reason, month-gap
detection (including out-of-order
input and multi-group sort tie-breaks), and fingerprint stability run
in normal CI.

** DONE The boundary is non-negotiable and closed to outside implementation

The rule above is stronger than "consumers should prefer the DM".  No
package outside the =marketdata= hierarchy may implement, supply, or
even name a provider or storage seam.  Stated normatively:

#+BEGIN_QUOTE
The =marketdata= package is the sole public entry point for historical
market data.  No package outside the =marketdata= package hierarchy may
directly access, construct, configure, inject, or depend upon a
market-data provider, storage implementation, data-normalization or
derivation mechanism, cache, or persistence format.  These are private
implementation details owned by =marketdata= and packages beneath its
=internal= boundary.

A consumer may request data through =marketdata.Manager=.  If provider
choice must be exposed, the consumer may select a provider only by an
opaque logical name or identifier -- for example, =oanda=, =alpaca/iex=,
or =alpaca/sip=.  That selection must not expose a provider interface,
concrete provider type, credentials model, transport, or construction
mechanism.

Storage is never selected, supplied, or accessed by a data consumer.
The manager owns all decisions concerning storage, persistence layout,
canonicalization, aggregation/derivation, caching, and retrieval.

This restriction is intentional.  Relaxing it later requires an explicit
architectural decision and refactor; it must not happen incrementally by
exporting implementation seams.
#+END_QUOTE

Consequences:

- =Config= supplied to =marketdata= carries only consumer-level policy
  and selections.  If provider choice must be exposed later, it is an
  opaque logical name -- never a provider or storage implementation, an
  interface, a concrete type, a credentials model, or a construction
  mechanism.
- There is no externally implementable provider or storage injection
  seam.  Any such seam an implementation adds is a violation of this
  boundary, not an extension point.
- The boundary is enforced mechanically where Go's package rules allow
  it (an architecture test forbidding =marketdata= from importing
  provider/storage/vendor packages, and the =internal= boundary keeping
  the implementations un-importable from outside).

** DONE How will gaps and closed market days be handled

Settled at the =Bar= level by #72: a Bar existing *is* an observation,
so a missing interval is an *absent* Bar -- there is no zero-filled
dummy row and no per-Bar status flag.  Issue #74 adds the vocabulary for
*why* an interval is absent (or present but not final):
=marketdata.IntervalState= — =Present=, =Closed=, =Missing=,
=Incomplete=, =InProgress=, =Unexpected= — and
=ClassifyInterval(cal, span, now, present, providerComplete)=, a pure
classifier over facts a caller already has.  A present Bar during a
calendar closure classifies as =Unexpected=, never silently as
=Closed=: the two are not equivalent, since =Closed= means "the
calendar says no bar belongs here and none is present," while
=Unexpected= means the calendar and the data actively disagree — a
contradiction a design-review comment on the PR caught the first draft
silently collapsing into =Closed=, which would have let
=DatasetComplete= treat a real calendar/data conflict as accepted-absent.
Classification order beyond that is fixed: an interval that has not yet
elapsed is next, ahead of a still-forming Bar that happens to already be
present; only then do presence and the provider's own =complete= flag
decide =Present=/=Missing=/=Incomplete=.
=DatasetComplete(states []IntervalState)= formally defines completeness:
true iff every entry is =Present= or =Closed= — =Unexpected= is
deliberately excluded from that set.

=ClassifyInterval= requires the calendar to report one uniform =Status=
across the *entire* span, not just its start: it samples =Status= at
both =span.Start()= and just before =span.End()=, and, when that status
is =StatusOpen=, additionally requires =cal.Session(span.Start())= to
fully contain =span=.  A span that fails either check — for example a
UTC-aligned H4 bar straddling a 13:00 New York partial-closure threshold
— is rejected with a wrapped =ErrIntervalStraddlesBoundary= rather than
silently classified from its start alone, which a design-review comment
identified as unsafe in the first draft: sampling only =span.Start()=
would have misclassified exactly that straddling case, and would have
kept doing so silently.  Splitting or otherwise resolving a straddling
span is left to the caller (#79's coverage engine, in practice); this
cannot happen for a session-aligned D1/W1 bar, whose span already equals
one =Calendar=-defined session or week.

Walking a real query range, producing a =[]IntervalState= for it, and
reading raw's =complete= flag to populate =providerComplete= during
normalization all remain later work: walking a range is #79's coverage
engine, and populating =providerComplete= from OANDA's raw =complete=
column is #76's normalization stage.  #74 defines the vocabulary and its
classification rules only.

*Correction (issue #79):* the claim above that a straddle "cannot happen
for a session-aligned D1/W1 bar" is wrong for W1.  Building #79's
coverage engine found that =FXCalendar.Bar='s W1 span is a full
seven-day week — it always contains the Friday-to-Sunday closure within
it, so it is never uniformly one =Status= throughout, and
=ClassifyInterval='s straddle check rejects every genuine W1 span with
=ErrIntervalStraddlesBoundary=.  The claim holds for D1 (one session) but
not W1 (a week, which spans multiple sessions and the closure between
them by construction).  #79's coverage engine does not call
=ClassifyInterval= for W1 at all — see its own section below.

**** One file, not two — a design-review correction
The first draft published manifest and data as two separate files,
relying on =os.Rename='s single-file atomicity plus a documented
ordering (data renamed, then manifest) and =Manifest.Matches= to reject
whatever a reader might observe mid-sequence.  A design review on the
PR identified that this still violated the issue's own acceptance
criterion that failure or cancellation must leave the prior published
revision /intact/: once the data file's rename succeeded, the old data
was already gone, overwritten by the new file's bytes.  =Matches=
failing on the resulting mixed pair meant the corruption was
/detected/, but the previously published dataset was not /loadable/
again until a further publish completed successfully — the regression
test written to demonstrate the mechanism (=PublishCancelledBetweenWrites=)
was, on inspection, codifying exactly that contradictory outcome rather
than proving safety.

The fix is the other option the issue's own scope explicitly allowed
("the dataset manifest or agreed file header"): manifest and data now
share one file, so there is exactly one =os.Rename= — genuinely atomic,
not "atomic per file with a window between two files."  A publish
cancelled or failed before that one rename leaves the previously
published file completely untouched and fully loadable; a publish that
completes it replaces the whole (manifest, data) pair in a single
indivisible step.  There is no intermediate state to reach at all, so
the regression test now asserts what the acceptance criterion actually
requires: cancelling a republish leaves the *original* revision
loadable, not merely a detectably-broken one.

**** Encoding the manifest header as JSON, not key=value lines
A second review finding: the first draft's manifest header used
hand-joined =key=value= lines, but =Manifest.Validate= only requires
its string fields (=Provider=, the version fields, =Parent.Revision=)
to be non-empty — none of them are required to be free of embedded
=\n=/=\r=, so a line-oriented encoding cannot round-trip every
=Manifest= value =Validate= itself accepts.  This is the identical
ambiguity a review already caught and fixed in
=Manifest.Revision()= (#73), which is why that function already hashes
a JSON-encoded struct rather than a delimited string.  The store's
header now does the same: one JSON-encoded line, quoted/escaped by
construction, immune to the field-boundary ambiguity a delimited format
has.

**** Verifying, not just storing, the manifest
Two related review findings hardened what =load= actually checks
against a stored header, beyond =Manifest.Validate=/=Matches=:

- The header's =revision= field (=Manifest.Revision()= at encode time)
  is now recomputed from the decoded =Manifest= and compared against
  the stored value; a mismatch is =errStoreMalformed=.  This is the
  cheapest possible defense against a hand-edited or partially
  corrupted header whose individual fields still happen to parse
  correctly in isolation.
- A derived manifest's =parent.instrument= field is now cross-checked
  against the caller-supplied expected instrument (the same check
  already applied to the manifest's own top-level instrument) rather
  than being silently discarded and overwritten — the first draft threw
  the stored value away entirely and always substituted the expected
  instrument, which meant a manifest whose parent stanza actually named
  a *different* instrument than expected would still validate.

**** Partition-key/manifest agreement and path safety
Two further review findings, both about =publish= accepting input that
should never have been accepted in the first place:

- =publish= now calls =checkKeyMatchesManifest=, verifying =key='s
  instrument, provider, and interval agree with =m= before writing
  anything, and that =m.Span= *overlaps* — not necessarily falls
  entirely within — the calendar month =key.year=/=key.month= name.
  Overlap rather than exact containment is deliberate: a session-aligned
  D1 span can legitimately open in the closing hours of the previous UTC
  day, occasionally the previous UTC month, while still correctly
  belonging to the calendar month a caller filed it under.  Without this
  check, =publish= could succeed while writing a partition that could
  never subsequently be loaded (a zero or mismatched instrument) or that
  landed under the wrong provider/interval directory entirely.
- =partitionKey.provider= and =partitionKey.symbol= are now validated as
  safe, single path components (non-empty, not =.=/=..=, free of any
  path separator) before any filesystem operation, with a defense-in-depth
  check that the resolved path still falls beneath the configured root.
  Both values are name-based and originate outside the storage
  implementation (a provider identifier, an instrument's display
  symbol); even though this store is internal, nothing before this fix
  stopped a value containing =..= from escaping the intended
  provider/symbol partition.

**** Cancellation checked all the way to the commit point
A second review round on the single-file redesign above found the fix
still had a gap: =publish= only checked =ctx.Err()= twice, both before
any writing began, so a cancellation arriving while =encodePartition=
was actively writing a large partition's rows — real work already
under way — went unnoticed until the write, flush, sync, and rename had
*all* already succeeded, silently replacing the prior revision anyway.
=writeFileAtomic= now takes =ctx= and checks it once more immediately
before =os.Rename= — nothing after that check can leave a torn or
unexpectedly-replaced file, so this is the genuine commit point.
=encodePartition= additionally checks =ctx.Err()= on every bar row, so
cancellation on a large (M1-scale) partition is caught promptly rather
than only at the end. Three regression tests, using a custom
=context.Context= whose =Err()= returns nil a controlled number of
times before reporting cancellation, pin down exactly where in the
sequence — before the write starts, mid-loop after real work has begun,
and immediately before the rename — cancellation lands, confirming the
original revision remains fully loadable in every case.

**** Non-goals
Building or resampling a =BarSet=/=Manifest= from raw records is #76's
job; this issue only ever persists and re-reads an already-valid pair.
Coverage/gap reasoning over what a store *should* contain remains #79's.

** DONE Bar queries and Manager-owned memory cache
Settled by issue #78 (branch =feature/78-bar-queries-cache=): the
read-only historical =Bar= retrieval path through public
=marketdata.Manager=, backed by the internal canonical store (#77) and a
new =Manager=-owned memory cache.

- =BarQuery{Instrument, Interval, Range}= names the data a caller wants
  — an instrument, an interval, a half-open =[Start, End)= range — never
  how to fetch it. Its own =validate= method reports a wrapped
  =ErrInvalidQuery= for a zero instrument, an invalid interval, or a
  malformed range.
- =Manager.Bars(ctx, query)= resolves =query.Instrument= to this
  Manager's provider-native =Listing= through the configured
  =instrument.Resolver= (ADR-016), loads every partition that could
  plausibly hold data for the query (see "Proving coverage" below),
  filters every returned =Bar= back down to the query's exact range,
  and returns a =*BarReader=. It never downloads, builds, or republishes
  anything — strictly read-only, matching this issue's own "important
  constraint."
- =BarReader= is a fully materialized, in-memory iterator:
  =Next(ctx) (Bar, io.EOF)=, =Manifests() []Manifest= (one entry per
  partition the result was assembled from, disclosing provenance), and
  an idempotent =Close()=. Because =Bars= already loaded and validated
  every partition before returning, =Next= never itself does I/O; only
  =Bars= can be slow or fail on missing data. A =nil= =*BarReader= and a
  =*BarReader= after =Close= both behave as an already-exhausted,
  closed reader rather than panicking.
- A query range =Bars= cannot prove full coverage for reports a wrapped
  =ErrDataUnavailable= naming the uncovered sub-range, and no reader is
  returned at all — never a reader over a silently partial result. A
  different load failure (a malformed or corrupted partition file) is
  deliberately /not/ classified as =ErrDataUnavailable=: the two are
  different failures — "we have never built this data" versus "the data
  we have is broken" — and a caller must be able to tell them apart
  rather than treating both as "go acquire the missing data."

**** The store stays fully private to =marketdata=
This issue also closed a real gap the M2-03 skeleton left open: because
=Config.store= is unexported, no composition root outside this package
could ever set it, so before this issue =New= simply passed that
always-nil field through, and =Manager= had no way to reach real data in
production. =New= now builds its own =canonicalCSVStore= from
=Config.StoreRoot= internally whenever =cfg.store= is unset (the normal
case for every caller outside this package); =cfg.store= remains
purely an in-package test seam. No =Config= field, accessor, or return
value ever exposes the store type, an implementation, or a handle to
one — the only door in or out of published canonical =Bar= data is
=Manager.Bars=, for exactly the reason the boundary section above
already states. =Config.StoreRoot= itself is not new and is not this
issue's exception to that rule: it is a bare filesystem path string
supplied at construction, the same category of configuration as
=Clock=, and it was already documented as "an internal storage concern
... never exposed through a Manager operation" before this issue.

**** =Config= grows two more required fields
=Bars= cannot resolve an instrument to a provider symbol without a
resolver, and cannot know which provider's data it serves without a
name, so =Config= gains =Resolver instrument.Resolver= and
=ProviderName string=, both required (empty/nil is a wrapped
=ErrInvalidConfig=, matching =Clock=/=StoreRoot='s existing pattern).
=CacheCapacity int= is also added, optional: non-positive selects a
package-defined default (32 partitions).

**** =barCache=: bounded, FIFO, revision-aware, concurrency-safe
=barCache= lives in its own file (=cache.go=), unexported, and is
reachable only as =Manager='s own private field — nothing in =Config=
can inject or replace it, and no =Manager= method returns it, the same
invisibility the store itself has. It keys cached
=(Manifest, BarSet)= pairs by =partitionKey= and evicts the single
oldest entry once a =put= exceeds capacity — plain FIFO by insertion
order, not LRU/adaptive: this issue's own non-goals explicitly excluded
"sophisticated adaptive cache eviction," and refreshing an already-cached
key's value does not move it to the back of the eviction queue, so a
frequently-read partition gets no special exemption from eviction. A
=nil= =*barCache= behaves as an always-miss, no-op cache rather than
panicking, mirroring =BarReader='s nil-safety.

Revision-awareness is a forward-looking hook, not yet wired to a live
write path: =invalidate(key)= evicts one key's cached entry, so that
once =Manager= gains a canonical-build/publish operation, publishing a
new revision under a key can evict any older revision already sitting in
memory. No such publish operation exists yet — every operation this
issue adds is read-only — so =invalidate= is exercised directly by
tests today; it is the seam that operation will need, not dead code.

A design review on the PR found =barCache='s map and =container/list=
were entirely unsynchronized, even though =Manager.Bars= is an
application-service entry point with no documented single-goroutine
restriction. Every method (=get=/=put=/=invalidate=/=len=) now locks a
=sync.Mutex= around its state; =TestBarCacheConcurrentAccess= and
=TestManagerBars_ConcurrentQueries= are the =-race= regressions proving
it.

The same review found a second hazard one level up: =Manifest.Parent= is
a pointer, so returning a =Manifest= by value out of =get= (or storing
one via =put=) shared that pointer between the cache and whatever the
caller held — a caller mutating =Parent.Revision= on a =Manifest= handed
back by one query could silently corrupt what a later query, hitting the
same cached entry, would receive. =cloneManifest= (also in =cache.go=)
deep-copies =Parent= and is now applied at every ownership boundary that
crosses out of or into the cache: =barCache.get=, =barCache.put=, and
=BarReader.Manifests=. =TestBarCacheGetReturnsIndependentManifestClone=,
=TestBarCachePutClonesManifestFromCaller=, and the end-to-end
=TestManagerBars_ManifestMutationDoesNotPoisonSubsequentQuery= pin this
down at all three layers.

**** Proving coverage, not just loading files
The first draft derived partition keys solely from the UTC calendar
months a query's range overlaps (=monthPartitionKeys=) and treated
"every one of those files loaded without error" as proof the query was
satisfiable. A design review identified two related correctness holes in
that assumption, both now fixed by the same mechanism:

1. *Silent partial-range success.* Loading a partition file proves
   nothing about how much of the query's range it actually covers — a
   manifest's own =Span= can be far narrower than the calendar month it
   is filed under. The original multi-month test was, on inspection,
   itself codifying this bug: it asked for a range through April 1 while
   its March partition's =Span= covered only four hours, and the query
   still "succeeded," silently returning less data than was requested.
2. *D1/W1 partition-routing.* The canonical store's own
   =checkKeyMatchesManifest= (#77) permits a partition's =Manifest.Span=
   to merely /overlap/, not be contained by, the calendar month it is
   filed under — deliberately, to allow a session-aligned D1/W1 bar
   whose session opens in the closing hours of the previous UTC month.
   That means a bar's observed =Time= can legitimately live in a
   partition filed under an /adjacent/ calendar month from the one
   =monthPartitionKeys= would compute for it, and a query entirely
   within that adjacent month — with no partition file of its own —
   would previously report =ErrDataUnavailable= even though the data
   exists, findable only by looking at the neighboring key.

Both are fixed together: =Bars= now loads the core months
=monthPartitionKeys= identifies /plus/ =boundaryProbeKeys= — the one
calendar month immediately before the first core month and immediately
after the last. Every key, core or probe alike, is loaded the same
tolerant way: a missing file (=os.ErrNotExist=) is not itself an error,
since most month boundaries have nothing filed at the adjacent key, but
a file that exists and fails to load (malformed, cancelled context)
still fails the query immediately. What actually decides success is the
new =coverageGap= helper: the union of every =Manifest.Span= that was
found, clipped to the query's range, must cover that range with no gap;
=coverageGap= reports the first uncovered sub-range otherwise, which
=Bars= surfaces directly in its =ErrDataUnavailable=. Bars gathered from
every loaded partition are deduplicated by =Time= and sorted before
being returned, since a boundary-spillover bar could in principle be
reachable through more than one loaded partition and the merge across
files is not otherwise guaranteed sorted.

=TestManagerBars_GapInCoverageReportsErrDataUnavailable= and
=TestManagerBars_BoundarySpilloverIsFoundViaProbe= (the latter
reproducing the exact D1 scenario above: a partition filed under April
whose two bars are dated the last two days of March, queried through a
range entirely inside March with no March partition ever published) are
the regression tests for each finding; =TestCoverageGap_*= and
=TestBoundaryProbeKeys_*=/=TestShiftPartitionKeyMonth_*= test the
helpers directly.

This remains deliberately narrow — a "does the query's own range have
proof of coverage" check, not the general coverage/gap catalog issue #79
owns — and does not attempt session-calendar-aware routing beyond the
one-month blast radius a D1/W1 bar can plausibly spill across.

**** Conflicting duplicates across overlapping partitions
Loading both a core and a boundary-probe partition (or, in general, any
two partitions whose overlap-permitted =Span=s cross) means =Bars= can
legitimately encounter the same bar =Time= twice. A second review round
on the boundary-probing fix above caught that the first version resolved
this the wrong way: deduplicating on =Time= alone silently kept whichever
partition happened to be processed first, so two partitions disagreeing
about the same instant's OHLC/spread/tick values — a broken publication
invariant, not a benign duplicate — would produce a result that
depended on key iteration order instead of failing loudly.

=Bars= now accepts a repeated =Time= only when the second occurrence is
byte-for-byte identical to the first (the new =barsEqual= helper,
comparing every field via =num.Price.Equal= rather than Go's =\=\== so
it does not depend on =Price='s internal representation being unique per
value); a repeated =Time= with any differing field is reported as a
wrapped =ErrInconsistentData= naming the conflicting instant, and the
query fails outright rather than picking a side.
=TestManagerBars_IdenticalOverlapDuplicateIsAccepted= and
=TestManagerBars_ConflictingOverlapDuplicateReportsError= cover both
outcomes against two genuinely overlapping March/April partitions;
=TestBarsEqual= tests the comparison directly.

=ExampleManager_Bars= (external =marketdata_test= package,
=example_test.go=) reads a small checked-in EUR/USD H1 partition under
=marketdata/testdata/=, generated once with the real
=canonicalCSVStore= (so its bytes, including the manifest header's

** DONE Coverage, gap detection, and data-build planning
Settled by issue #79 (M2-11, branch =feature/79-coverage-and-plan=):
Manager-owned coverage analysis plus a deterministic, non-mutating plan
describing what raw downloads and canonical builds would be required —
never performing any of them. Two new files, =coverage.go= and =plan.go=,
both public.

**** =Manager.Coverage=
=Coverage(ctx, query BarQuery) (Coverage, error)= reuses =BarQuery='s
exact shape (no separate =CoverageQuery= type — the extra type would add
nothing over reusing what #78 already defined) and reports, per UTC
calendar month touched:

- =PartitionCoverageStatus= (=Missing=, =Invalid=, =Stale=, =Current=):
  one canonical partition *file's* own standing — does it exist, can it
  be trusted, is it current — deliberately orthogonal to =IntervalState=
  (#74), which classifies individual bar intervals *within* a partition
  that already exists and can be trusted. Conflating the two would have
  made a genuinely different kind of fact ("this file is stale") look
  like a bar-level state ("this hour is missing"), which it is not.
- =Gap{State IntervalState, Span TimeRange}=: consecutive
  non-Present/non-Closed boundaries merged into one entry each, computed
  only within =Current= partitions — a =Missing=/=Invalid=/=Stale=
  partition's own =PartitionCoverageStatus= already says everything a Gap
  would say, less precisely, so no Gaps are produced for it.

**** Staleness: two self-contained mechanisms, no speculative "current version" config
- Raw-built intervals (M1/H1/H4/D1): =Manifest.RawFingerprint= against
  the current raw partition's fingerprint from
  =marketdata/internal/provider/oanda.Inspect=.
- W1 (derived from D1, ADR-012's one-hop resampling model):
  =Manifest.Parent.Revision= against the D1 partition filed under the
  *same* (year, month) key, recomputing its =Revision()= live — exactly
  the mechanism #73's own =Parent= documentation already described
  ("the recorded revision simply stops matching the parent's current
  one, which is the intended staleness signal"), now actually exercised.

Deliberately *not* implemented: builder/validator/calendar *code*-version
staleness. No build/normalize-to-manifest operation exists anywhere in
this codebase yet to define "the current version," and inventing =Config=
fields for a comparison with no real producer would be speculative. Any
canonical partition whose raw or parent counterpart cannot itself be
found or trusted is conservatively judged *not* stale by =isStale= — that
condition already surfaces separately (via =RawIncompleteCount= or a
=Plan= download/normalize action), rather than making an unrelated axis
say "stale" for a fact it cannot actually verify.

**** "Incomplete" is observable raw-side only
=marketdata.Bar= carries no provider-completeness flag (#72/#73), so a
published canonical Bar's original OANDA =complete= flag is not
recoverable from canonical data alone — =Coverage='s bar-level walk
always passes =providerComplete=true= to =ClassifyInterval= for a
present canonical Bar. =IntervalStateIncomplete= remains part of the
vocabulary (forward-compatible; a future build step could still choose
to preserve the signal) but is not currently producible by =Coverage=
over canonical data. What *is* observable today:
=PartitionCoverage.RawIncompleteCount=, sourced directly from
=oanda.Partition.IncompleteCount=.

**** W1 cannot reuse =ClassifyInterval= — a genuine #74 correction
See the correction note added to #74's section above:
=FXCalendar.Bar='s W1 span is a full seven-day week that always contains
the Friday-to-Sunday closure within it, so =ClassifyInterval='s
=uniformStatus= straddle check rejects every real W1 span. Coverage
therefore classifies W1 weeks with a separate, direct walk
(=gapsForWeeklyPartition=): =InProgress= if the week has not elapsed,
=Present= if a bar exists at the week's start, =Missing= otherwise — a
week is never itself "calendar-closed" the way a single day or hour can
be, so that branch of =IntervalState= does not apply at the week level.
Both walks share one merge helper (=gapAccumulator=) so "consecutive
same-state boundaries merge into one Gap" is implemented exactly once.

**** A real map-key bug caught by the W1 tests
The bar-presence lookup was originally =map[time.Time]bool=, keyed by
=Bar.Time= and looked up via a boundary's =span.Start()=. This is unsafe:
a loaded =Bar.Time= is always UTC-located (=parseBarRow= calls =.UTC()=),
but =FXCalendar.Bar='s D1/W1 boundaries are New York-located — the same
*instant* represented by two =time.Time= values with different internal
representations, which Go's map-key equality (structural, not
=.Equal()=) treats as different keys. A W1 test publishing a bar at
=dayBoundary.Start()= and then failing to find it present is what
surfaced this. Fixed by keying on =b.Time.UTC().UnixNano()= throughout —
an =int64=, immune to =Location=-sensitivity — rather than the
=time.Time= value itself.

**** =Manager.Plan= and gated scheduling
=Plan(ctx, query BarQuery) (Plan, error)= calls the same coverage
analysis =Coverage= does (factored into an unexported =coverage= method
so a =Plan= call performs exactly one raw-archive =Inspect=, not two),
then derives =[]Action= (=ActionDownloadRaw=, =ActionNormalizeCanonical=,
=ActionDeriveCanonical=), ordered download, then normalize, then derive
— each bucket internally chronological.

Governing rule, "gated scheduling": an action for one stage is only
produced once that stage's own input is already satisfiable —
=ActionNormalizeCanonical= is never produced for a month whose raw
partition is missing or failed integrity checks (only
=ActionDownloadRaw= is, for that month); =ActionDeriveCanonical= is never
produced for a W1 month whose underlying D1 range is not itself complete
(=DatasetComplete=-equivalent: every =PartitionCoverage= =Current= and no
Gaps). This reproduces the legacy planner's =Inventory -> WantList ->
Plan -> Download/Build= dependency-aware scheduling (mined from the
documented behavior in the M2 issue-breakdown proposal, not transplanted
code — no legacy repository was available in this session to mine
directly) without coupling to legacy structure.

=ActionDownloadRaw= with reason ="extend"= additionally covers the most
recently touched month when the calendar reports an open interval past
the raw partition's own =LastTime=, walked forward to
=min(now, query.Range.End)= via =Manager='s own clock — never
=time.Now= directly, the same determinism contract every other Manager
operation honors. An OK but empty raw partition (=LastTime= zero) falls
back to the start of its own filed month rather than an arbitrarily
distant past instant, bounding the walk to at most one month's worth of
boundaries. When "extend" is needed, a normalize action is also emitted
(reason ="extend: rebuild once raw catches up"=) even though the current
=PartitionCoverageStatus= might otherwise be =Current=, since raw is
about to change under it.

**** Two more optional =Config= fields
- =RawRoot string=: the raw archive location. Unlike =StoreRoot=, not
  required by =New= — =Bars= never reads raw data, so a query-only
  Manager need not configure it. =Coverage=/=Plan= report a wrapped
  =ErrInvalidConfig= if it is empty when actually needed (any interval
  except W1, which has no raw side at all).
- =Calendar Calendar=: defaults to
  =NewFXCalendar(FXCalendarParams{})= in =New= when unset — the same
  "build a real internal default when not overridden" pattern the

A general resampling-dependency graph (W1's D1 dependency is hard-coded,

**** Two PR-review fixes
A design review on the PR found two further problems, both in cursor
handling:

- *Cursor seeding could start before the query range.*
  =gapsForPartition=/=gapsForWeeklyPartition= originally seeded their
  walk from =calendar.Bar(clipStart, interval).Start()= directly. D1/W1
  are not UTC-clock-aligned, so a =clipStart= that does not land exactly
  on a boundary edge — routine, not an edge case — resolves to a
  boundary whose own start is *before* =clipStart=. Reporting a Gap for
  that boundary is misleading: a bar dated before the query's own
  =Range.Start= would never be returned by =Bars= anyway
  (=TimeRange.Contains= excludes it), so it must not be reported as
  "missing from this query" either. Tracing the fix further surfaced a
  second, more important symptom: for a multi-month query, the *next*
  month's walk would independently recompute the *same* straddling
  boundary (its own =clipStart= — that month's start — also falls inside
  it) and process it again, producing the same Gap twice as two
  overlapping =Span= values. New =firstBoundaryAtOrAfter= fixes both by
  advancing to the boundary's =End()= whenever its computed =Start()=
  precedes the requested =at=, so each straddling boundary is owned by
  exactly the one month whose own clip window it actually starts in.
  =TestCoverage_GapNeverStartsBeforeQueryRange= and
  =TestCoverage_StraddlingMonthBoundaryNotDoubleCounted= are the
  regressions; both were confirmed to fail against the pre-fix code
  before being kept.
- *=Plan(W1)= required =RawRoot= it never needed.* =deriveActionsW1='s
  D1-completeness prerequisite check went through the public =Coverage=
  method, which requires =RawRoot= for D1 (a raw-built interval) — even
  though a =Manager= used only for W1 planning has no reason to ever
  configure =RawRoot= at all, since W1 itself has no raw side. Fixed by
  calling the unexported =coverage= directly with a =nil= raw lookup for
  this one internal check; =isStale='s existing "cannot verify, don't
  judge stale" default already handles a =nil= map safely, so the D1
  prerequisite check simply cannot detect D1's own raw-fingerprint
  staleness from inside a W1 plan — a narrower question than a direct
  =Plan=/=Coverage= call for D1 itself would answer, not a silent
  correctness gap.  =TestPlan_DeriveW1WorksWithoutRawRootConfigured= is
  the regression.

**** =CredentialProvider= and =Client=
=CredentialProvider= (=credential.go=) is a one-method interface,
=Token(ctx) (string, error)=, called before every request — including
each page and each retry — rather than cached, so an implementation may
rotate a token transparently. =StaticCredential= is the trivial fixed-
token implementation for composition roots and tests that do not need
rotation.

=Client= (=client.go=) is the only network-facing type in this package.
Its transport is =HTTPDoer= (exported — =Do(*http.Request)
(*http.Response, error)=, satisfied by =*http.Client=), injected via
=ClientConfig.HTTPClient=; every =Client= test in this package supplies
a fake, so none makes a real network call. =HTTPDoer= is exported
specifically so =marketdata.Manager='s own construction — and
=marketdata='s own =Sync= tests — can build a real =*oanda.Client=
wired to a fake transport from outside this package, without this
package needing a broader public testing surface than that one
interface.

**** Retry, rate limiting, and error classification
A request is retried (fixed attempt limit, doubling backoff, timed
through a =clock.Clock= rather than =time.Sleep= so tests stay
deterministic with =clock.Simulated=) only when it is classified
transient: a network-level failure, HTTP 429
(=ErrRateLimited=), or 5xx (=ErrProviderUnavailable=). A permanent
failure — 401/403 (=ErrUnauthorized=), 400/404 (=ErrBadRequest=) — is
never retried, since retrying cannot change the outcome. Every attempt
still exhausted reports the wrapped =ErrRetriesExhausted= sentinel.
Rate-limit pacing (=fixedIntervalLimiter=, also =clock=-driven) is a
separate, optional concern from retry backoff — =Client.Wait='s call
happens immediately before every attempt, so the two compose rather
than race.

The bearer token is placed on exactly one outgoing request header and
nowhere else: =classifyStatus= builds its diagnostic error text from
the response body only, never a request header, so the token
structurally cannot leak into an error message — tested directly
(=TestFetchCandles_TokenNeverAppearsInError=).

**** Missing versus extend, decided operationally
=marketdata.Manager.Sync= (=sync.go=, the parent package) does not
trust an =Action='s =Reason= text to decide how to write a partition —
=Reason= is diagnostic, not a machine dispatch key. For each
=ActionDownloadRaw= entry, =Sync= checks whether a raw partition file
already exists for that (instrument, interval, year, month):

- No file: the whole calendar month (or through now, whichever is
  earlier) is fetched and written as a brand-new file
  (=WritePartition='s =mustNotExist=), which returns
  =ErrPartitionAlreadyExists= rather than silently overwriting anything
  that unexpectedly appeared between the check and the write.
- An existing, readable file: only the range from its last record
  forward (through now or month's end, whichever is earlier) is
  fetched, merged with the existing records, and the file is atomically
  replaced with the merged result — never a bulk redownload of already-
  preserved history.
- An existing but unreadable/malformed file: =Sync= fails loudly for
  that =Action= rather than guessing. Repairing a corrupted raw
  partition remains a distinct, explicitly-authorized future operation,
  not something an ordinary sync performs automatically.

=Sync= only ever executes =ActionDownloadRaw= entries — every other
=ActionKind= in the supplied =Plan= is reported in
=SyncResult.Skipped=, not executed and not silently dropped, keeping
this issue's scope exactly "fill missing raw partitions and extend
recent history" and nothing more.

**** Two more optional =Config= fields, required together
=OANDACredential oanda.CredentialProvider= and =OANDABaseURL string=
are both optional — =Bars=/=Coverage=/=Plan= never need either — but
=New= rejects one supplied without the other, since a half-configured
client (a token with no endpoint, or vice versa) is a silent footgun
rather than a usable partial configuration. =OANDABaseURL= is a full
URL, not a "practice"/"live" enum =Manager= would parse itself:
environment selection is the composition root's own typed
configuration decision. =Manager= also gains an unexported
=Config.oandaClient= test seam, mirroring the existing
=store=/=provider= pattern, so this package's own =Sync= tests can
inject a =*oanda.Client= built against a fake =HTTPDoer= without
widening =Config='s public surface.

**** Non-goals

Repairing a corrupted existing raw partition — a distinct, explicitly-

**** Four PR-review fixes
A design review on the PR found four further problems, all real:

- *=fixedIntervalLimiter= raced under concurrent use.* =last= was read
  and written with no synchronization, and neither =Client= nor
  =Manager.Sync= documented a single-goroutine restriction — a =Client=
  is shared state, and concurrent =FetchCandles= calls against it are a
  real, intended use, not a misuse. Fixed with a =sync.Mutex= guarding
  both the read/write of =last= and the wait itself, so two concurrent
  callers are paced *against each other*, not just against whichever one
  last happened to update the timestamp.
  =TestFixedIntervalLimiter_ConcurrentWaitIsRaceFree= is the =-race=
  regression.
- *=mustNotExist= was not actually atomic.* The original implementation
  checked =os.Stat= first, then wrote a temp file, then called
  =os.Rename= — but on Unix, =Rename= silently replaces an existing
  destination regardless of what an earlier =Stat= saw, leaving a real
  window in which a file created by a concurrent writer would be
  silently overwritten: precisely the "accidental replacement" this
  parameter exists to prevent. Fixed by replacing the Stat-then-Rename
  sequence with =os.Link= for the =mustNotExist= case specifically:
  =link(2)= atomically fails with =EEXIST= if the destination already
  exists, with no separate check-then-act window at all. The extend
  case (=mustNotExist= false) still uses =Rename=, the correct primitive
  there, since replacing an existing file is exactly what an authorized
  extend means to do.
  =TestWritePartition_ConcurrentMustNotExistIsRaceFree= spawns eight
  concurrent writers at the same path and asserts exactly one succeeds.
- *=syncOne= assumed a pre-existing raw file was already Time-ordered.*
  =ReadPartitionRecords= returns rows in file order, and nothing on the
  read path validates that order — a hand-edited or otherwise
  irregular file could still parse cleanly while being out of order, in
  which case trusting the last *row* as the extend point could
  duplicate or skip candles. Fixed by sorting the read-back records by
  Time before computing the extend point, not only ever sorting on
  write. =TestSync_ExtendUsesActualLastRecordEvenIfFileOutOfOrder=
  writes a fixture with rows deliberately out of position and confirms
  the correct (chronologically last) record is used.
- *An incomplete tail candle was frozen forever.* The original extend
  logic always resumed from =last.Time + 1ns=, regardless of whether
  =last= was itself still provider-incomplete. Since =Client= preserves
  incomplete candles (by design — #76-style provider-declared metadata
  is not discarded), a newly-created current-month file could hit this
  immediately, and its provisional OHLC/volume would never be
  refreshed even after OANDA finalized the real values. Fixed three
  ways together: =oanda.Partition= gains a new =LastComplete= field
  (set from whichever record's =Time= is the partition's =LastTime=
  specifically, not just any record — =TestInspect_
  LastCompleteReflectsTheLatestRecordSpecifically= covers the
  distinction); =needsExtend= now also schedules an extend when
  =!p.LastComplete=, independent of what the calendar reports
  (=TestPlan_ExtendsWhenLastRawRecordIsIncomplete=); and =syncOne=
  resumes from the incomplete record's own =Time= (not past it) and
  merges the refetch back in by =Time= (new =mergeRecordsByTime=, keyed
  by UTC =UnixNano= the same way #79's coverage-gap work already
  established as the correct way to compare a stored and a freshly-
  computed =time.Time= as a map key), so the refreshed, now-complete
  record replaces the stale provisional one instead of duplicating it.
  =TestSync_RefetchesIncompleteTailRecordInstead= is the end-to-end
  regression.

* DONE Where does FX holiday data come from?
Settled by issue #74: adopted, unchanged, from
=trader-first-try/market/forex_hours.go='s =isMajorForexHolidayClosed= —
the one holiday source Trader had already exercised against real OANDA
data, and the source this note originally pointed at.  It is exposed as
=marketdata.StandardFXHolidays(years ...int) FXCalendarParams=, Trader's
accepted M2 rule set:

- Jan 1, Dec 25, Dec 26 — closed all day.
- Dec 24, Dec 31 — closed from 13:00 New York time onward (not fully
  closed; the market is open earlier that day).  =FXCalendar= gained a
  new =PartialClosure= concept for exactly this: a session that is
  truncated early rather than not opening at all.
- Sunday evening stays closed when *that Sunday itself* is one of the
  three full-day holidays — implemented as one additional rule in
  =FXCalendar.Status=, since the existing session-labeled-by-ending-date
  model does not otherwise cover it (the following Monday is not itself
  a holiday date in that scenario).  The "following Monday is a holiday"
  half of the old rule needs no special case at all: it is already
  covered by the ordinary ending-date holiday check, since the session
  opening Sunday evening is labeled by the Monday it ends on.

=FXCalendar.Status= and =FXCalendar.Session= are computed by one shared,
unexported =classify= method rather than independently, specifically
because a partial closure or the Sunday-holiday rule can *truncate* a
session rather than remove it outright — a design-review comment on the
PR caught the first draft computing them separately, which let =Session=
keep returning the full nominal rollover-to-rollover range even where
=Status= reported the tail (or, for the Sunday case, the head) of that
same range as closed, violating =FXCalendar='s own documented invariant
that every instant a returned =Session= contains reports the same
=Status=.  With one shared implementation, =Session= now returns the
truncated open window directly (for example, ending at 13:00 on Dec 24
rather than 17:00, or starting at the following New York midnight rather
than the nominal Sunday 17:00 rollover when that Sunday is a holiday),
so the two methods cannot drift apart again.  =Bar= is unaffected by
truncation on purpose: its nominal, calendar-aligned D1/W1 range answers
a different question ("what interval does this instant belong to") than
=Session= ("when was trading actually open"), and truncating it would
conflate the two.

This is still deliberately narrow, unchanged from the source: no Good
Friday, no in-lieu observance when a holiday falls on a weekend, and no
non-FX venue calendars.  Extending it is a separate, later decision, not
a silent addition made while implementing #74.  =FXCalendar= itself
remains a pure calendar with no holiday data of its own —
=StandardFXHolidays= is a caller-supplied params builder, not a change to
what =FXCalendar= assumes by default.

**** Two build paths, two different failure postures
=normalizeAndPublish= (=build_normalize.go=) and =deriveAndPublish=
(=resample.go=) share the same publish/manifest/cache-invalidate tail
(=publishCanonicalMonth=, =build.go=) but diverge deliberately on how
they treat a bad or not-yet-ready input:

  in a partition (#76) fails the whole =normalizeAndPublish= call
  before any store write happens; =recordOutcomeIncomplete= records are
  silently excluded (matching #76/#79's own finding that canonical

  anomalous raw record is treated as a hard normalization failure, not
  a gap.

  month still is by the time =Build= actually runs). An unready week is

**** =Bars= requires full coverage; =Coverage= does not — this shaped the loop
=deriveAndPublish= originally called =m.Bars= once for the whole target
month to fetch its D1 input, and failed immediately whenever any week
of that month was not yet ready, since =Bars= (#78) refuses to return

two calls apart: =m.coverage= (unexported, #79) is called once for the
whole month — it never requires full coverage, only reports on it — to
answer =weekIsD1Ready= for every week cheaply, while the new

unexported since a streaming =Reader= remains the right public shape
for =Bars= itself) is called once *per ready week only*. Each ready
week's own span is, by definition, fully coverable, so this succeeds
where the single whole-month call did not.

**** The aggregation formula, mined from legacy
=aggregateBars= (=resample.go=) folds a week's D1 bars into one W1 bar
per the formula in
=~/src/trader-first-try/datamanager/candle_agg.go='s own
=aggregateWindow=: Open is the first bar's Open, High/Low are the
max/min across the window, Close is the last bar's Close, =Ticks= is
summed, =MaxSpread= is the max, and =AvgSpread= is the tick-weighted
mean, falling back to zero when total ticks is 0 (legacy's own guard,
not a new fallback invented here). Legacy never actually built W1 — its
own =dailyAligned= only ever covered D1/H4 — so this is the formula
applied to a genuinely new resampling target, not transplanted code;
only the aggregation math itself is mined. =AvgSpread <= MaxSpread=
holds on the output by construction (every input's own =AvgSpread= is
at most that input's =MaxSpread=, itself at most the aggregate
=MaxSpread=), so a tick-weighted average of values each bounded by the
aggregate maximum cannot exceed it — verified directly by
=TestAggregateBars_ResultValidates=.

=num= has no direct Price-by-=int64=/scalar-divide operation, so the
weighted mean is computed by converting each bar's tick count to a
=num.Rate= (=strconv.FormatInt= + =num.MustParseRate=), weighting via
=Price.MulRate=, summing via =Price.Add=, and finally multiplying by
the reciprocal total-tick =Rate= (via =Rate.DivRate=) rather than
dividing directly — composing existing =num= operations (ADR-004)
instead of adding a new one for this issue's narrow need.

A W1 partition's =Manifest.Parent= always names the D1 partition filed

  =deriveActionsW1='s own documented "works with no =RawRoot=" support.
  The check moved from =Build= into =normalizeAndPublish= itself, so a
  W1-only =Plan=, or a =Plan= whose only raw-dependent entries are
  =ActionDownloadRaw=/=ActionRepairRaw= (both reported in =Skipped=,
  never executed by =Build=), no longer fails before those entries can
  even be reported.
- =normalizeAndPublish= called =oanda.ReadPartitionRecords= and
  =oanda.FingerprintPartition= as two separate file opens, admitting a
  window in which =Sync= atomically replaces the raw partition in
  between — pairing one revision's parsed records with a different
  revision's recorded fingerprint. =oanda= gained
  =ReadPartitionSnapshot=, a single =os.ReadFile= that both fingerprints
  and parses the identical in-memory bytes;
  =TestReadPartitionSnapshot_ConsistentUnderConcurrentReplace= races a
  writer against it under =-race= and asserts every observed snapshot's
  record count and fingerprint always describe the same file revision.
- The D1 coverage check inside =deriveAndPublish= originally queried
  only =[monthStart, monthEnd)=, so it could not see a missing, invalid,
  or stale *next*-month D1 partition that a final boundary week's data
  actually spills into (only the final week in a month can ever do so —
  see =w1SpansNextMonth='s own doc comment for why). A missing spillover
  partition was wrongly declared "ready," and =readAllBars= then failed
  the whole build trying to read data =Coverage= never reported absent.
  Fixed by having the new =weekSpansForMonth= compute the full union of
  week spans up front, so the coverage query's range already covers any
  spillover before =weekIsD1Ready= is ever asked about it.
- =Manifest.Parent= recorded only the same-month D1 manifest's own
  =Revision=/=RawFingerprint=, even when a boundary week's bars actually
  came from two D1 partitions (this month's and the next's) — so
  rebuilding the *next*-month partition would never mark the resulting
  W1 partition stale. =combineParentLineage= now folds every actually-
  contributing D1 manifest (still exactly one in the common,
  non-boundary-spanning case, where its output is byte-identical to the
  single-parent design) into one composite =sha256:= value for both
  fields. =coverage.go='s =isStale= recomputes the identical composite
  from a stored =Manifest='s own =LastBar=/=Span= via the same
  =w1SpansNextMonth= rule =deriveAndPublish= used to decide what to
  record, so the two can never disagree about which case applies to a
  given W1 partition.
